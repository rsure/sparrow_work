# 架构层改造方案 —— 模型 Provider / 设置 / 工作区 / 会话持久化 / 上下文管理 / 插话打断 / 子 agent 预留

> 对应总计划里程碑 **M1**（ARCH-1/2/3）与 **M3**（ARCH-4/5）。
> 另含两个「改造前必须定稿」的增补模块：**ARCH-6 执行中插话与打断**（M2 前冻结 SSE 协议）、
> **ARCH-7 子 agent 实例隔离**（仅预留接口，随 ARCH-1 工厂定稿）。
> 本层是「能力主线」：决定这个客户端能不能真正接上多家 AI、能不能可靠地跑长对话。
>
> **状态（2026-10-23）**：ARCH-1/2/3/4/5/6/7 全部 ✅ 落地。
> ARCH-6 已实现真实注入（插话写进工具结果）与「取消未开始的工具」；
> ARCH-7 已实现 `AgentScope` 隔离 + SUB 强制 ASK 红线，并已接上调用方
> （`dispatch_subagent` 工具，见 §7.6；`agent.subagent_enabled` 默认仍为 off，用户显式开启后才挂进主对话）。
> 落地细节见各模块的「落地记录」小节。

---

## 1. 目标

1. 把硬编码的 DeepSeek 换成**多供应商 Provider 抽象**，支持运行时切换。
2. 建一套**可视化设置体系**，模型/密钥/工作区/工具开关都能在设置页改。
3. 支持**多工作区 profile**，随时切换当前生效的那个。
4. 会话**跨重启不丢**、长对话**不爆上下文**。

| 项 | 现状 | 问题 |
| --- | --- | --- |

## ARCH-1 模型 Provider 抽象

### 1.1 设计

**核心原则：把「选哪家模型」从「代码常量」变成「运行时配置」。**

- 新建 `backend/app/llm/` 包，用 LangChain 的 `init_chat_model`（或各 provider 的 Chat 类）做统一入口。
- 每个 provider 一个描述：`id`、`label`、`base_url`（可空）、`env_key`、`model 列表`。
- 运行时根据当前设置**按需构建**模型实例，替换掉 `rag_agent.py` 里的模块级 `model` / `agent` 单例。

### 1.2 Provider 清单（首批）

| provider | 底层类 | 说明 |
| --- | --- | --- |
| `deepseek` | `ChatDeepSeek` | 现状迁移，默认 |
| `openai` | `ChatOpenAI` | OpenAI 兼容，可接各类中转/本地 |
| `anthropic` | `ChatAnthropic` | Claude |
| `google` | `ChatGoogleGenerativeAI` | Gemini |
| `ollama` | `ChatOllama` | 本地模型，无需云密钥 |

> 关键点：`openai` provider 的 `base_url` 可配，天然覆盖「硅基流动 / 通义 / Kimi / 各类 OpenAI 兼容端点」，这是「多 AI 支持」里性价比最高的一条。

### 1.3 改动文件

| 动作 | 文件 | 内容 |
| --- | --- | --- |
| 新增 | `backend/app/llm/__init__.py` | 包说明 |
| 新增 | `backend/app/llm/registry.py` | provider 注册表：id → 描述/默认 base_url/所需密钥键 |
| 新增 | `backend/app/llm/factory.py` | `build_chat_model(provider_id, model, api_key, base_url) -> BaseChatModel` |
| 新增 | `backend/app/llm/state.py` | 运行时「当前模型」缓存 + 失效机制（设置变了重建） |
| 重构 | `backend/app/agents/rag_agent.py` | 去掉模块级 `model`/`agent`，改为 `get_agent()` 工厂，按当前设置装配 |
| 重构 | `backend/app/controllers/chat_controller.py` | `agent`/`model` 改为每次（或设置变更时）从工厂取 |

### 1.4 关键取舍

- **模型实例缓存**：`create_agent` 编译图有开销，不能每请求重建。方案：`llm/state.py` 缓存「当前 provider+model+参数」对应的实例，设置变更时失效重建。
- **系统提示词**：`SYSTEM_PROMPT` 与供应商无关，保持一份，`get_agent()` 里复用。
- **参数可配**：`temperature` / `max_tokens` 随设置下发（默认沿用现状 `temperature=0`，给高级用户留开关）。

### 1.5 模型配置补齐（增补：模型清单 / 能力元数据 / 自定义 Provider / 连通测试）

> 原方案骨架（registry / factory / 运行时切换）成立，但核查出五处缺口：
> ① 模型清单写死在注册表，用户加不了新模型；② 模型**无能力元数据**——ARCH-5 压缩阈值的分母
> 「模型上下文上限」原方案无处取；③ `llm.base_url` 全局单值，多个 OpenAI 兼容端点**不能并存**；
> ④ 设置页无法验证密钥/模型名是否可用；⑤ 换模型后历史轮次无从追溯、UX-5 无法按轮取对单价。

#### A. 模型清单：内置 + 自定义

注册表（`registry.py`）每个 provider 附内置模型列表，每条含**能力元数据**；用户可通过
`llm.custom_models` 追加自定义模型，字段同构：

| 字段 | 说明 |
| --- | --- |
| `model` | 模型名（API 调用用） |
| `label` | 展示名 |
| `context_window` | 上下文上限（token）——**ARCH-5 压缩阈值的分母来源；自定义模型必填** |
| `supports_tools` | 是否支持工具调用（false 则不出现在默认可选列表） |
| `supports_vision` | 是否支持图片输入（预留，首版 UI 只展示不启用） |
| `price_in` / `price_out` | 输入/输出单价（元/百万 token，UX-5 成本计算用） |

- 选择器列表 = 内置 ∪ 自定义；同一 `provider+model` 时**自定义覆盖内置**（用于修正单价/窗口）。
- 覆盖场景：新模型发布但注册表未更新、中转站私有模型名。

#### B. 自定义 Provider（多 OpenAI 兼容端点并存）

- `llm.custom_providers`（json）：`[{id, label, base_url}]`，协议固定 OpenAI 兼容（复用 `ChatOpenAI`）。
- 每个 `custom-<id>` 对应钥匙串键 `secrets.custom-<id>.api_key`（走 ARCH-2 密钥链路，各端点密钥独立）。
- factory 的 provider 解析顺序：内置 5 家 → `custom_providers` → 报「未知 provider」。
- 内置 `openai` 的 `llm.base_url` 保留（作为「官方或单一端点」的简单路径）。

#### C. 连通性测试（设置页「测试」按钮）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/llm/probe` | body `{provider, model, base_url?}`；发一次最小请求，返回 `{ok, latency_ms, error?}`；密钥直接从钥匙串取，**不回传**；错误区分「密钥错误 / 模型名不存在 / 网络不通」 |

#### D. 按轮记录所用模型

- `done` 事件与 trace（OPS-6）补 `model` 字段（`provider/model`）：换模型后历史轮次可回放「当时用的谁」，UX-5 成本统计按轮取对单价。

### 1.6 验收标准

- [ ] 在设置页切换 DeepSeek / OpenAI / Ollama 后，新对话立即用新模型（无需重启后端）。
- [ ] 未配置密钥时，后端给出明确错误（延续现状「must be set」），前端显示「请在设置页配置密钥」。
- [ ] `\doc` 检索问答用的裸模型同样走 factory，不用再 `new` 一个。
- [ ] 现有 DeepSeek 对话功能不回归（作为默认 provider）。
- [ ] 设置页可添加自定义模型并填 `context_window`；切换后 ARCH-5 压缩阈值按该值计算。
- [ ] 两个自定义 OpenAI 兼容端点并存，密钥各自独立，切换即用。
- [ ] 「测试」按钮能区分「密钥错误 / 模型名错误 / 网络不通」三种失败。
- [ ] 历史会话每轮显示当时所用模型（`done.model` 字段）。

## ARCH-2 设置体系与可视化（含 API Key 决策）

### 2.1 决策：设置存哪、密钥存哪

> **决策**：**普通设置入 `app_settings` 表；API Key 入系统钥匙串（后端 `keyring`）。**

理由与取舍：

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 全部明文存 `app_settings` | 最简单 | 密钥明文落 SQLite，备份/同步即泄露 | ❌ |
| 全部存钥匙串 | 最安全 | 非密钥设置没必要，且读起来绕 | ❌ |
| **密钥走钥匙串 + 普通设置入表** | 安全与简单兼顾 | 需引入 `keyring` 依赖 | ✅ 采用 |
| 前端 Electron `safeStorage` 加密 | 免后端依赖 | 加密密钥在 Electron 进程内，Python 后端解不开 | ❌（后端要解密才能调 API） |

**降级方案**：`keyring` 在无图形环境的 Linux 上可能无后端 → 此时退化为「Fernet 加密后存 `app_settings`，密钥文件放应用数据目录（权限 0600）」。`services/secrets.py` 封装成统一 `get_secret(key) / set_secret(key, value)`，调用方不关心实现。

### 2.2 设置项清单（第一版）

| 组 | 键 | 类型 | 存储 | 说明 |
| --- | --- | --- | --- | --- |
| 模型 | `llm.provider` | string | 表 | deepseek/openai/… |
| 模型 | `llm.model` | string | 表 | 具体模型名 |
| 模型 | `llm.base_url` | string | 表 | 可空，openai 兼容端点 |

| 模型 | `llm.custom_models` | json | 表 | 自定义模型列表（含 context_window/单价等元数据，见 §1.5.A） |
| 模型 | `llm.custom_providers` | json | 表 | 自定义 OpenAI 兼容端点（多个并存，见 §1.5.B） |

## ARCH-5 上下文管理（token 预算 + 自动压缩）

### 5.1 设计

- **Token 估算采用「方案 B」**：统一用 `tiktoken` 的 `cl100k_base` 编码做近似，中文按「1 字 ≈ 0.6~1 token」校正——一套代码覆盖所有供应商，不依赖各家私有 tokenizer（DeepSeek 无公开库）。
  - 估算范围必须**含系统提示词 + 历史消息 + 本轮工具结果**（工具输出往往是大头，漏算会严重偏乐观）。
  - 估算只用于「是否压缩」的判断，允许略微高估（宁多勿少），**不用于计费**（计费走 UX-5 的 API usage）。
- 新增 `services/context_manager.py`：负责 `estimate_tokens(messages)` 估算、压缩触发与摘要。
- 压缩策略（首版简单可控）：
  1. 当累计 token 超过阈值（如模型上下文的 70%）时，对**最早的一批消息**做摘要，替换原文。**「模型上下文上限」取当前模型元数据的 `context_window`**（ARCH-1 §1.5.A；自定义模型必填该字段），未知时保守按 32k 处理并记警告日志。
  2. 摘要复用现有裸模型 `model`（不挂工具）做一次性总结。
  3. 系统提示词与最近 N 条消息不压缩（保证近期连贯）。

### 5.2 改动文件

| 动作 | 文件 | 内容 |
| --- | --- | --- |
| 新增 | `backend/app/services/context_manager.py` | `estimate_tokens()`（tiktoken cl100k_base + 中文校正）+ 压缩触发 + 摘要 |
| 扩展 | `backend/app/controllers/chat_controller.py` | 补种/入图前调用压缩 |
| 扩展 | `backend/app/config.py` | 阈值/保留条数/中文校正系数可配 |
| 扩展 | `backend/pyproject.toml` | 加 `tiktoken` 依赖 |

### 5.3 验收标准

- [ ] 超长对话逼近上限时自动压缩，不报「上下文超长」。
- [ ] 压缩后仍能回答「我们最早聊过什么」级别的摘要性问题。
- [ ] 压缩过程可通过 `debug=true` 在日志/事件里看到（便于排查）。

## ARCH-6 执行中插话与打断（steering）—— 增补：改造前必须定稿

> **为什么必须在改造前**：本模块要新增 SSE 事件与 controller 编排分支。UX-1（M2）把消息流与
> 输入栏建好之后再补，等于前端重写一遍。事件协议在 M1 末冻结时一并定稿，M2 前端按协议一次做对。

### 设计

把「用户只能在 confirm_required 时介入」升级为**执行中随时介入**，三档打断语义：

| 档 | 用户动作 | 系统行为 | 实现层级 |
| --- | --- | --- | --- |
| 追加指令（steer） | 流式期间直接发消息 | 入 steering 队列；当前工具步完成后作为新 user 消息注入，模型据此调整后续步骤 | `_drive_agent` 循环步间检查 |
| 取消当前工具 | 点工具轨迹卡片上的「取消」 | 当前工具步结束后丢弃其结果，注入「用户取消了该操作」提示 | 工具 wrapper 出口检查取消标记 |
| 整体停止 | 「停止」按钮 | 中止本轮 agent 循环，保留已产生的现场（现有 `stopped` 链路扩展） | 现有 stopped 分支 |

> 首版**不做工具执行中途强杀**（进程级 cancel 复杂且危险），只做「步间」介入——已覆盖绝大多数场景。

**关键取舍（为什么这么做）**

1. **插话注入在「工具结果」而不是「新的一条 user 消息」**：正在跑的 LangGraph 图只接受一次输入，中途插 user 消息要改图结构与恢复机制；而 `ToolMessage` 的内容本来就会在下一步喂给模型，把插话写进这里效果等价，且零新机制。
2. **注入点在 `finalize()` 之后**：截断（EXT-5）与审计只处理工具自己产出的内容。插话是用户原话，既不该被截断，也不该被记成"某个工具吐出了用户的话"。
3. **`steer_accepted` 不占 SSE 通道**：这是用户另外发起的一次 HTTP 请求，回执放在响应体里最直接，也不影响主流的事件顺序。
4. **取消只对「还没开始执行」的工具生效**：同步工具跑起来后无法安全中断（进程级 cancel 复杂且危险），后端如实返回 409 并建议改用「终止」——前端不假装成功。
5. **`begin_turn` 清空队列**：上一轮末尾没等到工具边界的插话不能串到下一轮，否则用户会在毫无预期的时候看到自己很久以前的一句话影响新一轮。
6. **开关沿用已有设置键 `agent.steering_enabled`**：M2 冻结协议时就登记了，本批只是把行为接上，没有新增设置项。

**已知限制**

- 插话条数上限 5、单条 2000 字（`steering.MAX_PENDING` / `MAX_CONTENT_CHARS`），超出直接 400，不排队等待。
- 只在工具边界注入：一轮里如果模型一次工具都不调（纯回答），插话不会被注入，随 `begin_turn` 丢弃。

## ARCH-7 子 agent 实例隔离（接口预留）—— 增补：工厂签名必须一次做对

> **为什么必须在改造前**：ARCH-1 的 `get_agent()` 工厂是全项目 agent 的唯一装配入口。若首版签名只支持
> 「全局单例」，后续 TASK Phase 2 / 探索性子任务要隔离上下文时，就得改工厂签名 + 全部调用方。
> 本模块**只预留接口，不实现多 agent 行为**（默认关闭），成本极低。

### 设计

- `get_agent()`（ARCH-1）签名升级为 `get_agent(scope: AgentScope = MAIN)`，`AgentScope` 枚举：
  - `MAIN`：主对话 agent（现状，全量工具 + 共享 thread）。
  - `SUB`：子 agent——独立 thread_id、**受限工具集**（默认只读）、独立 `max_iterations`、只回传结论不回传过程（过程走 EXT-5 落盘，需要时可续读）。
- 装配参数（工具集、迭代上限、thread）由 `AgentScope` 在 `llm/state.py` 派生，调用方无感。
- TASK（`26-复杂任务拆分方案.md`）的子任务执行器**必须走该抽象**（哪怕首版 scope 恒为 MAIN）。
- **权限**：SUB 默认继承当前权限模式，但**写操作强制降级为每次询问**——子 agent 自主性高，确认不能省（此规则为红线，不开放配置，见 `27-设置体系规范.md` §5.3）。

### 改动文件

| 动作 | 文件 | 内容 |
| --- | --- | --- |
| 扩展 | `backend/app/llm/factory.py` / `state.py` | `AgentScope` 枚举 + 按 scope 派生装配参数 |
| 扩展 | `backend/app/tools/policy.py` | `SessionContext` 加 `scope` 字段；SUB 的写操作强制 ASK 分支 |

### 设置项

`agent.subagent_enabled`（默认 **off**；打开后主对话多出 `dispatch_subagent`，见 §7.6）、
`agent.subagent_max_parallel`（默认 2，即同时最多 2 个子 agent）。

**关键取舍（为什么这么做）**

1. **派发登记成 `Kind.READ`**：它自己不写盘、不执行，只是"另起一个隔离 agent 去读"。真正的风险在子 agent 内部，那一层已有 `SCOPE_SUB` 红线。在门口再拦一道只会让用户每派一次点一次"允许"。
2. **子 agent 用独立 `MemorySaver` + 独立 thread_id**：不复用主对话检查点，所以它的中间步骤不会污染主对话、也不会接在"上一次派发"的中间状态上继续跑。
3. **会话 id 派生 `#sub-<随机>`**：子 agent 内部的工具从 `current_session_id()` 取会话 id——若与主对话相同，ARCH-6 的插话队列会被子 agent 抽走，用户的话就"插到别人那里去了"。
4. **超时/步数超限单独识别**：两者都返回"把任务拆小"的具体建议，而不是把异常原文丢给模型（模型看到 stack 只会瞎猜）。
5. **缓存改多槽 + 指纹带开关**：单槽会让每次派发都重建主对话图；指纹不带开关则"用户刚打开，这一轮工具清单还是旧的"。
6. **`verify_all_tools_registered(SUBAGENT_TOOLS)` 放在导入期**：工具默认不挂载，但策略必须先在册，否则"一打开就崩"。

**已知限制**

- 子 agent 的 token 消耗不进 `_usage` 统计，界面上看不到它花了多少。
- 子 agent 的工具调用不进主对话 trace（只进后端日志），排查时要看日志。
- 子 agent 之间不共享发现，两个子任务读同一个文件会读两遍。
- 子 agent 不能向用户提问：需要确认方向的任务不该派出去（提示词里已写明）。
