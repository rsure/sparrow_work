# 前端测试基建 —— Vitest + jsdom 的最小可用闭环

> 起因：改造方案里反复把「前端无测试基建」记成已知限制（`doc/20-改造总计划.md` 附录二「已知限制」、
> `doc/23-体验层改造方案.md` §3.3 验收标准），Markdown 渲染与 XSS 只能靠「唯一入口 + DOMPurify 默认白名单」这类
> 结构性约束来保证，一旦有人改 `MarkdownView.vue` 的渲染链，没有任何自动化用例会报警。
> 本文记录这次补基建的**选型理由、目录约定、覆盖范围与后续缺口**。
>
> **状态**：✅ 已落地。`pnpm run test:frontend` 8 个 spec / 98 个用例全绿，`pnpm run typecheck` 通过。

---

## 1. 目标与非目标

### 1.1 目标

1. 让前端具备和后端一样的「改完就能跑一遍」的能力：`pnpm run test:frontend` 一条命令。
2. 优先覆盖**改错了不会报错、只会安静出错**的地方：请求封装（`request.ts` 的四种调用方式与流式解析）、
   防抖/过滤/切片这几个纯逻辑 composable、Markdown 渲染链（XSS）、文件胶囊的交互分支。
3. 测试代码同样遵守 `AGENTS.md` 的三条硬性要求（字段/函数/import 都要有中文注释、文件顶部有模块说明）——
   **读测试的人应该比读源码的人更容易懂**，否则新同学不会去改测试。

### 1.2 非目标（这次不做）

1. 不追求总覆盖率数字：页面（`views/`）、store、大部分 `services/` 这次没有用例，见 §6。
2. 不做端到端（E2E）：Electron 窗口、真实后端、真实文件系统不在这次范围；这类场景继续靠人工验收。
3. 不接入 CI、不默认塞进 `pre-commit`，见 §7。

## 2. 选型：为什么是 Vitest 3 + jsdom

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| **Vitest 3.2.x**（采用） | ✅ | 与 Vite **共用同一套 transform**：`vite.config.ts` 里的 `@vitejs/plugin-vue`、`@` 别名都能原样复用，测的就是真实编译产物；原生 ESM，无 babel 转译链 |
| Vitest 4.x | ❌ | peer 要求 `vite: ^6 \|\| ^7 \|\| ^8`，本项目 Vite 停在 `^5.4.11`（升 Vite 6 会连带影响 Electron 打包与插件版本），属"为了测试工具升级整个构建链"，不划算 |
| Jest + ts-jest | ❌ | 需要另建一套 babel/ts-jest 转译与 `moduleNameMapper`，与 Vite 的别名/ESM 语义不一致，容易出现"测试里 import 失败但打包正常"的错位 |
| happy-dom（替代 jsdom） | ❌ | `dompurify` 依赖真实 DOM 的属性/命名空间语义，happy-dom 对部分属性与 SVG 的处理与浏览器有差异；XSS 用例正好是"要相信 DOM 语义"的地方，不能省 |

实际安装版本（`pnpm install` 后实测）：

| 包 | 版本 | 作用 |
| --- | --- | --- |
| `vitest` | 3.2.7 | 测试运行器（`describe` / `it` / `expect` / mock） |
| `@vitest/coverage-v8` | 3.2.x | 覆盖率（用 Node 自带 V8 覆盖率，免插桩） |
| `@vue/test-utils` | 2.5.1 | 组件 `mount`、`find`、`trigger`、`emitted` |
| `jsdom` | 26.1.0 | 在 Node 里模拟浏览器 DOM（`document` / `window`） |
| `vite` | 5.4.21 | 已有，被 Vitest 复用 |

> 依赖只在 `frontend/package.json` 的 `devDependencies` 里，不进产物包；
> `pnpm build` 打出来的 bundle 与加测试前一致。

## 3. 目录与配置

```
frontend/
├── vitest.config.ts          # 测试专用配置（不写进 vite.config.ts，避免"哪条配置是给谁的"分不清）
└── tests/
    ├── setup.ts              # 每个测试文件运行前执行：补 jsdom 缺失的浏览器 API
    ├── unit/                 # 纯逻辑：服务封装 / composable / 主题
    │   ├── http.spec.ts
    │   ├── request.spec.ts
    │   ├── useDebouncedRef.spec.ts
    │   ├── useFileFilter.spec.ts
    │   ├── useFileSegments.spec.ts
    │   └── themePresets.spec.ts
    └── components/           # 组件：mount 后看渲染结果与交互
        ├── MarkdownView.spec.ts
        └── FilePathChip.spec.ts
```

### 3.1 `vitest.config.ts` 的三条硬约定

1. `plugins: [vue()]` 与 `resolve.alias` 的 `@` → `./src` **必须与 `vite.config.ts` 保持一致**：
   否则测试里 `import '@/services/request'` 解析失败，或测的是另一份编译设置下的组件。
2. `include: ['tests/**/*.spec.ts']`：只认测试目录里的 `*.spec.ts`，避免误跑 `src/` 下的同名文件。
3. `globals: false`：不注入全局 `describe/it/expect`，每个文件显式 `import { describe, it, expect } from 'vitest'`。
   多写一行 import，换来"这个符号从哪来"一眼可见——与 `AGENTS.md` R3（每条 import 说明用途）同向。

覆盖率段落：`provider: 'v8'`、`include: ['src/**/*.{ts,vue}']`、排除 `src/main.ts`（纯装配）与
`src/data/big-mock.ts`（静态大数组，不是逻辑）、报告输出 `text`（终端总览）+ `html`（点进文件看哪行没覆盖）到 `frontend/coverage/`。
**故意不设 thresholds**：这些用例不是挡板，是学习脚手架，把阈值一挂，随便改一行页面就会因为"总覆盖率"红掉。

### 3.2 `tests/setup.ts` 补了什么、为什么要补

jsdom 只实现了 DOM 规范的一部分，缺的 API 不会"明确报错"，而是让被测代码在某一刻抛 `TypeError`，
排查成本极高。所以一次性补齐（已存在则不覆盖，避免盖掉真实实现）：

| API | 谁需要它 | 不补会怎样 |
| --- | --- | --- |
| `TextEncoder` / `TextDecoder`（取自 `node:util`） | `services/request.ts` 的 `sse` / `stream` 逐块解码流 | 调 `stream()` 时 `new TextDecoder()` 直接抛错 |
| `window.matchMedia` | Vant 组件（Popup/List 等）在挂载时探测暗色模式 | 组件挂载时 `matchMedia is not a function` |
| `ResizeObserver` | Vant `List` / `Popover` 监听尺寸变化 | `new ResizeObserver is not a constructor` |
| `Element.prototype.scrollIntoView` | Vant `Popover` 定位 | 点开菜单时抛错 |

注意两个细节：

- 补的 API **同时写到 `globalThis` 与 `window`**：jsdom 环境下两者不是同一个对象，只写一个会出现"我在测试里能看到，组件里看不到"。
- `matchMedia` 的替身恒返回 `matches: false`（即"浅色模式"）：测试不该依赖宿主系统的主题。

## 4. 怎么跑

```bash
# 根目录：只跑前端
pnpm run test:frontend

# 根目录：前后端一起跑（= test:backend && test:frontend）
pnpm run test

# 覆盖率（生成 frontend/coverage/index.html）
pnpm run test:frontend:coverage

# 前端目录下：监听模式，改文件自动重跑（日常写用例用这个）
pnpm --filter app-frontend run test:watch

# 只跑某一个文件（vitest 支持文件名片段过滤）
pnpm --filter app-frontend exec vitest run request
```

`frontend/tests/` 与 `frontend/vitest.config.ts` 已加进 `frontend/tsconfig.json` 的 `include`，
所以 `pnpm run typecheck`（`vue-tsc --noEmit`）**也会检查测试代码**——测试里的类型错误同样会在提交前被拦下。

### 5.1 三个「堵缺口」的用例，值得单独说

**XSS 四连（`MarkdownView.spec.ts`）**：`<script>`、`<img onerror>`、`javascript:` 链接、`<iframe>` 四种 payload 分别断言
"节点被删掉 / 危险属性为 `undefined` / 危险协议被清空"。

这条用例为什么可信？因为它不是空转：`markdown-it` 配置的是 `html: true`，原始 HTML 会**原样放行**——
用同样的配置直接跑 `md.render()`，四段 payload 的输出分别是
`<p>正常文本<script>alert(1)</script></p>`、`<img src="..." onerror="alert(1)">`、
`<p><a href="javascript:alert(1)">点我</a></p>`、`<iframe src="...">`。
也就是说：**把 `DOMPurify.sanitize` 从渲染链里去掉，这四条断言立刻红**。
这正是 `doc/23-体验层改造方案.md` §3.3 里"未做自动化 XSS 用例"缺的那一环。

**SSE 跨分片（`request.spec.ts`）**：把一帧切成两段喂进去，其中一段**切在"你"字的第 2 个字节中间**。
网络分片本来就不按字符边界切，`TextDecoder({ stream: true })` 就是为这个存在的；
如果以后有人把 `sse` 改成"每次 `read` 就 `JSON.parse`"，这条用例会立刻失败。

**防抖 composable（`useDebouncedRef` / `useFileFilter`）**：断言的是"输入框即时可用、过滤结果延迟"这一对**看似矛盾**的行为。
这是真实 bug 的高发点：把 `keyword` 直接绑到输入框，中文输入法下每敲一个字母都会过滤一次列表，列表会"跳"。

## 7. 为什么没接进 `pre-commit` / CI

`.githooks/pre-commit` 目前**只做一件事**：跑迁移漂移检查（`pnpm run check:migrations`，纯本地、2~3 秒）。
保持"一次提交只多 2~3 秒"是它存在的理由，把前端测试（一次 ~3.5s，且随用例增长会变慢）塞进去，
会让"随手提交"变成一件需要等待的事，最终结果是大家都用 `git commit --no-verify` 绕过——挡板反而失效。

当前约定：

- **改前端代码 → 自己跑 `pnpm run test:frontend`**（会在 `AGENTS.md` §4 自查清单里写明）。
- 提交前钩子继续只管迁移漂移。
- 需要"提交必过测试"时，把 §4 的命令加进钩子即可（一行），但那属于团队协作策略，不在这次范围内。

## 8. 写新用例的约定

1. **一个 `it` 只讲一件事**，用例名写"行为 + 预期"，像 `'sse 一帧被两个网络分片切开时也能正确还原'`，
   不写 `'test sse'`。
2. **不要改全局再忘记还原**：用 `vi.stubGlobal` / `vi.stubEnv`，依赖 `vitest.config.ts` 里的
   `restoreMocks: true` + 用例 `afterEach` 里的 `vi.unstubAllGlobals()` / `vi.unstubAllEnvs()`。
3. **假定时器必须成对**：`vi.useFakeTimers()` 的用例要在 `afterEach` 里 `vi.useRealTimers()`，
   否则同文件后续用例的时间相关逻辑会集体失灵。
4. **`composable` 要放进 `effectScope()` 里跑**：`useFileFilter` 等内部用了 `onScopeDispose`，
   裸调用会打印"no active effect scope"告警，且定时器不会被清理（用例之间互相污染）。
5. **组件测试要 stub 掉 `van-*`**：`main.ts` 里全局注册的 Vant 组件在测试里不存在，直接 `mount` 会得到
   "Failed to resolve component" 警告。用 `global.stubs`，需要触发事件时给一个**渲染函数**写的替身
   （项目用的是运行时版 Vue，内联 `template` 字符串无法编译）。
6. **不要依赖 `wrapper.vm` 里的内部状态**：`<script setup>` 组件的内部默认不对外暴露，
   应从渲染结果（DOM / `emitted()` / 被 mock 的函数调用）断言行为。
7. **测"为什么"而不是"是什么"**：`AGENTS.md` 的注释要求同样适用于测试，
   每个用例上方写一句"这条用例在防什么回归"。
