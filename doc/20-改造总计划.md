## 1. 目标与范围

把当前「Electron + Vue3 + FastAPI」外壳，改造成一个**桌面 AI 客户端**（对标 Claude Code / Cursor 形态，但保持本项目的「本机文件 + 知识库」定位），具备：

1. **多 AI 供应商**：DeepSeek / OpenAI / Anthropic / Gemini / Ollama（本地）可配置、可运行时切换。
2. **可视化设置**：模型、密钥、工作区、主题、工具开关都在设置页里改，不再改 `.env`。
3. **多工作区**：可定义多个工作区（profile），随时切换当前生效的那一个。
4. **可扩展**：支持安装 **Skill** 与 **MCP 服务**，工具能力可插拔。
5. **现代体验**：CC 式三栏页面架构、主题定制（背景/配色/自定义）、Markdown 与代码高亮、文件引用跳转。
6. **工程可靠**：数据库可迁移、密钥不入库、日志可诊断、可自动更新。

### 范围外（本次不做，避免摊子铺太大）

- 多用户 / 账号体系（本机单用户桌面应用，不需要）。
- 云端同步 / 协作（后续再说）。
- 移动端适配（Vant 是移动组件库，但本项目定位桌面，重构后以桌面布局为主）。

## 2. 现状结论（决定改造难度的关键事实）

改造不是「从零」，而是「在已有 Agent 上补架构」。已具备、无需重做的部分：

| 能力 | 位置 | 结论 |
| --- | --- | --- |
| 流式对话 + SSE | `backend/app/controllers/chat_controller.py` | 完整，保留 |
| LangGraph Agent + 工具 | `backend/app/agents/rag_agent.py` | 需改造为多 Provider，但 Agent 骨架保留 |
| 人工确认（HITL） | `chat_controller.py` 的 interrupt 链路 | 完整，扩展能力时复用 |
| RAG 知识库 | `services/rag_store*.py` + FAISS | 保留，后续增强 |
| 安全沙箱/权限/审计 | `doc/01~07` + `tools/policy.py` | 完整，作为 Skill/MCP 的权限底座 |
| 扫描模块 | `sanner_*` | 保留 |

必须重构的**关键约束**（各分册会展开）：

1. **AI 供应商硬编码**：`rag_agent.py:136` 模块级 `ChatDeepSeek`，启动即锁定 → ARCH-1。
2. **设置只有工作区、且无界面**：`setting_controller.py` 仅 `/settings/workspace`，前端无 SettingsView → ARCH-2。
3. **会话状态是内存态**：`InMemorySaver` + `_SESSIONS` 字典，重启丢现场 → ARCH-4。
4. **无数据库迁移**：`db_config.py` 靠 `create_all`，加字段会丢数据 → OPS-1。
5. **页面是巨石**：`scannHistory.vue` 1138 行；`App.vue` 是顶部导航单栏；无 markdown/代码高亮 → UX-1/3。
6. **主题写死**：`styles/main.css` 一套深色变量，`color-scheme: dark` 硬编码 → UX-2。

## 7. 全局约定（贯穿所有分册，避免各做各的）

1. **一个设置入口**：所有用户可改配置，统一走 `PUT /api/settings/*`，由后端落库/落钥匙串；前端不再读 `.env` 以外的运行时配置。
2. **密钥与普通设置分离**：普通设置入 `app_settings` 表；密钥入系统钥匙串（见 ARCH-2 / OPS-2）。
3. **权限复用**：Skill / MCP 引入的新工具，一律走现有 `tools/policy.py` 的策略登记 + `interrupt()` 确认链路，不另开一套权限。
4. **接口/字段注释**：延续 `AGENTS.md` 三条硬性要求（字段/方法/import 都要注释），改造时顺手补注释，不改业务逻辑。
5. **可回滚**：每个模块尽量「新增文件 + 小步替换」，能独立验证、独立回退。
6. **统一命名**：后端接口字段 `snake_case`，前端类型沿用后端字段名不转换（延续现状）。
7. **设置统一走 `27-设置体系规范.md`**：统一入口 + `组.键` 命名空间 + `SETTING_DEFS` 声明式注册；任何新模块的配置只写声明，不建自己的设置表/接口。
8. **事件契约一次定全**：SSE 事件里凡落库/回放需要的字段（usage、subtasks、truncated、steer 等），首发版本就带上（OPS-6）——后补字段 = 历史回放不兼容。

1. **迁移必须可重复执行**：本项目 `init_db()` 的 create_all 先于 Alembic 跑，新表会被提前建出来 → 0002 里按 inspector 判断后再 DDL；部分建表的存量库也兼容。
2. **重命名不能走 ORM 赋值**：`ChatSession.updated_at` 配了 `onupdate`，改标题会把会话顶到列表最前；改用 Core UPDATE 并显式 `updated_at=updated_at`。这个 bug 是被测试发现的。
3. **JSON 列的 None 语义**：`usage_json=None` 默认会存成字符串 `'null'`，`IS NOT NULL` 过滤不掉；列改 `JSON(none_as_null=True)` 并在服务层再兜一层真值判断。
4. **预算弹窗复用 interrupt 链路**：没有新开协议，`ask_budget()` 的 payload 带 `kind="budget"`，控制器据此把事件名换成 `budget_exceeded`；前端 `/chat/resume` 直接复用。
5. **预算"停止"要阻塞整轮**：只 return FAIL 的话模型会换工具继续试，用户被反复弹窗；加 `TurnBudget.blocked` 后整轮直接拒绝、不再询问。
6. **压缩不能拆工具调用对**：切分点回退到 HumanMessage；摘要用 HumanMessage 而不是 SystemMessage（避免与 create_agent 自己的系统提示词冲突，Anthropic 会拒绝）。
7. **确认弹窗改为受控组件**：Vant 的 `showConfirmDialog` 塞不进「记住本工作区」勾选框，因此新增 `AskOverlay.vue`，确认与预算共用。

**已知限制**：
- 上下文压缩的"效果"没有端到端压测（需要真实长对话）；目前只保证结构与降级路径正确。
- 摘要会额外消耗一次模型调用；若模型已接近窗口上限，这次调用本身也可能失败 → 已有机械摘要兜底。

   只做前缀会被 `WITH t AS (SELECT 1) DELETE FROM users` 绕过，只做黑名单会被注释与大小写绕过。
4. **降级读出来的文本禁止入库**：`.pptx` 在没有引擎时只能按字节解码，结果是乱码。
   如果静默入库，检索会命中一堆乱码切片，比"没有这条知识"更糟。所以 `index_file` 直接抛错，
   让上层汇总能说清"哪个文件没进去、为什么"。
5. **`.rtf` / `.odt` 不能"硬读"**：它们是容器格式，纯文本解码出来是标记源码。
   `read_text_any` 原来对 `.rtf` 走"非二进制就按文本解码"的兜底，测试才发现 —— 现在统一给"另存为"提示。
6. **实例归属用 `owned` 标记**：引擎的 `get_pool_status` 命中说明用户自己开着这个文件，
   此时绝不能 `close_file`（会把用户正在编辑的窗口关掉）。测试里专门钉了"不关用户实例"这条。
7. **文本缓存键必须含 `mtime_ns`**：只按路径缓存会让"用户改了文件再问一次"读到旧内容；
   含 size + mtime 后，文件一改缓存自然失效。

**已知限制**：
- 引擎端口探测失败后有 30 秒冷却，期间所有解析直接走降级路径（不反复探，避免每个文件卡 8 秒）。
- `read_doc` 的段标记是 `[正文] / [大纲] / [文本框与批注]`，与原设计的 `[第 N 段]` 不同 ——
  引擎返回结构树而不是段落数组，逐段编号不可靠。
- Word 的批注与文本框会作为正文的一部分喂给模型（已标记来源，但没有"排除批注"的开关）。
- 引擎复用用户已打开的实例时，读到的是内存现状（含未保存改动），且无法标注"是否含未保存改动"——
  引擎没有暴露该字段。

- 迁移 **0006_memory_lifecycle 零漂移**（`alembic upgrade head` 已在真实 `backend/app.db` 上执行过；
  三列 `last_used_at` / `use_count` / `merged_count` 均已生效）。

**关键决策 / 踩到的坑**：
1. **远端失败整批降级，而不是逐条降级**：512 维与 1536 维向量不能比较，混用不会报错、只会让检索排名变噪声；
   整批降级至少让 `stats.embedding` 能如实显示当前用的是哪套。
2. **本地后端作为默认值，而不是"没配就报错"**：这个项目要能在没网、没密钥的机器上跑完全部测试；
   远端是能力升级，不是运行前置条件。
3. **合并取"更长正文"而不是拼接**：拼接会产生读不懂的复合句，且每条记录都要保持"一句话可读"；
   长度是信息量最便宜又最稳的代理。
4. **淘汰只敢动 `importance <= 2`**：`>=3` 是用户明确认可过的结论，自动删除的代价远高于留噪声。
   两个阈值都可以设 0 关闭——删记忆不可逆，默认值必须保守。
5. **先有使用记录，才有资格谈淘汰**：原 `search()` 只读不写，库里所有记忆看起来一样新，
   所以先补 `_touch_usage`，再谈 TTL/上限。使用记录写失败只 `log.debug`，不能让检索跟着失败。
6. **`reindex` 用探针向量取目标维度**，而不是读设置里的模型名推断：模型名与真实维度没有映射表，
   直接问后端算一条最准（远端换模型也能自适应）。
7. **迁移只加列、不批量重算历史向量**：历史行因缺 `dim` 天然被 `reindex` 挑中，把"要不要花钱重算"的决定权留给用户。
8. **测试踩坑：本地 2-gram 相似度比直觉低**。写合并测试时挑的样本必须实测 ≥ 0.85
   （`注释要用中文` vs `注释要用中文，不要英文注释。` 只有 0.6928，会被判成"新建"而不是"合并"）；
   最终用 §13.2 里那对 0.896 的样本。
9. **测试踩坑：迁移没跑导致 `no such column: memories.last_used_at`**。实体加了列但没 `alembic upgrade head`，
   所有涉及 `memories` 的用例全红；先跑迁移再跑测试。
10. **工具坑：PowerShell 的 `(Get-Content) -replace ... | Set-Content` 会把文件写成 UTF-16LE**，
    后续 `read` 报 `invalid UTF-8 text`、vitest 报 `Unterminated string literal`，且写盘工具因"文件已变更"拒绝覆盖。
    改源码一律用编辑工具，别用文本管道。

**已知限制**：
- 本地后端对同义改写几乎无感（只认字面），真语义合并必须切远端 embedding；不做是因为那要么多一次模型调用、要么依赖网络。
- 降级静默：只在日志里留一行，用户只能从 `stats.embedding` 的「已降级」提示发现异常（不弹窗是刻意的，每轮都弹会淹没对话）。
- 合并不可撤销：没有保留被合并的原文，追溯只能靠 `merged_count` 与那条更长的正文。
- `reindex` 同步执行、无分批与进度上报；条数上限调到 5000 又切远端时，一次全量重算可能几十秒，前端只有 loading 态。

## 附录十三：ARCH-7 调用方补完（`dispatch_subagent`）报告（2026-10-23）

**为什么要做**：附录十一把 ARCH-7 的「能力」做完了（`AgentScope`、SUB 只读工具集、SUB 强制 ASK 红线），
但**没有任何调用方**——一条没人走的路，正确与否无法验证。本批补上调用方，让子 agent 真的能被派出去。

**范围**：
- 新工具 `tools/subagent_tool.py` 的 `dispatch_subagent(task, context="")`：校验（开关 / 空任务 / 2000 字上限 / 并发槽）
  → 起 SUB 图 → 只回收结论；超时 120s、步数上限用 `scope_max_iterations(SUB)`。
- 主对话按开关挂载：`build_tools(SCOPE_MAIN)` 在 `agent.subagent_enabled` 打开时追加 `SUBAGENT_TOOLS`；
  提示词追加 `SUBAGENT_PROMPT`（什么时候该派、怎么派）。
- 缓存改多槽：`llm/state.py` 单槽缓存换成 `_cached_agents: dict[指纹, 图]`，MAIN / SUB 各占一槽、
  不再互相顶掉；指纹末尾追加 `:{subagent_enabled()}`，开关一变立刻重建。
- 策略登记：`Policy(tool="dispatch_subagent", kind=Kind.READ)`；导入期就 `verify_all_tools_registered(SUBAGENT_TOOLS)`。
- 设置项描述同步改写（不再说"首版默认关闭/暂无调用方"）。

**验证结果**：
- 后端 **385 个测试通过、0 失败**（本批净增 15 条，全是 `tests/test_subagent_dispatch.py`）。
- 前端无改动（`agent.subagent_enabled` 是普通布尔设置项，设置页自动渲染）——仍 **124 个用例通过**。
- 冒烟：`build_tools('main')` 关闭 18 个工具 / 打开 19 个（多 `dispatch_subagent`）；`build_tools('sub')` 9 个且永不含派发工具。

**关键决策 / 踩到的坑**：
1. **派发登记成 `Kind.READ` 而不是 `WRITE`**：它自己不写盘、不执行，只是"另起一个隔离 agent 去读"；
   真正的风险在子 agent 内部，那一层已有 SUB 红线。在门口再拦一道只会让用户每派一次点一次"允许"。
2. **子 agent 用独立 `MemorySaver` + 独立 thread_id**：中间步骤不污染主对话检查点，也不会接在"上一次派发"的中间状态上继续跑。
3. **会话 id 派生 `#sub-<随机>`**：子 agent 内部的工具从 `current_session_id()` 取会话 id——若与主对话相同，
   ARCH-6 的插话队列会被子 agent 抽走，用户的话就"插到别人那里去了"。
4. **超时与步数超限各自识别**：两者都返回"把任务拆小"的具体建议，而不是把异常原文丢给模型。
5. **缓存必须改多槽**：单槽下每派一次子任务都重建主对话图（`invalidate()` 全清），代价是每轮都重新装配工具。
6. **`verify_all_tools_registered(SUBAGENT_TOOLS)` 放在导入期**：工具默认不挂载，但策略必须先在册，否则用户一打开开关就崩。
7. **测试踩坑①**：`dispatch_subagent` 是 `StructuredTool`，位置参数调用抛 `TypeError`，必须 `.invoke({...})`。
8. **测试踩坑②**：`build_tools()` 返回工具对象列表，`"dispatch_subagent" in 列表` 恒为 `False`，
   要比 `{getattr(t, "name", "") for t in tools}`。

**已知限制**：
- 子 agent 的 token 消耗不进 `_usage` 统计，界面上看不到它花了多少。
- 子 agent 的工具调用不进主对话 trace（只进后端日志），排查要翻日志。
- 子 agent 之间不共享发现：两个子任务读同一个文件会读两遍。
- 子 agent 不能向用户提问：需要用户拍板方向的任务不该派出去（提示词里已写明）。
