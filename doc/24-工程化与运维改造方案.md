## OPS-1 数据库迁移（Alembic）—— 里程碑 M0，最先做

### 1.1 现状

`db/db_config.py` 的 `init_db()` 用 `Base.metadata.create_all()` + `RagBase.metadata.create_all()` 建表。加字段/改字段只能「手动改库或删库重建」，会丢数据。

### 1.2 设计

1. 引入 **Alembic**，配置 `alembic.ini` + `migrations/`（`env.py` 指向现有 `engine`/`Base`）。
2. **首版迁移**：把当前所有表结构「冻结」成初始 migration（`autogenerate` 生成，人工审一遍）。
3. 之后所有 `entity/` 改动**必须**带一个 migration；`init_db()` 保留为「新库快速建表」的兜底，正式启动改走 `alembic upgrade head`。

### 1.3 改动文件

| 动作 | 文件 | 内容 |
| --- | --- | --- |
| 新增 | `backend/alembic.ini`、`backend/migrations/env.py`、`backend/migrations/versions/0001_initial.py` | 迁移基线 |
| 扩展 | `backend/app/main.py` | 启动时 `alembic upgrade head`（或保留 init_db 兜底） |
| 扩展 | `backend/pyproject.toml` | 加 `alembic` 依赖 |

### 1.4 验收标准

- [ ] 全新库能 `alembic upgrade head` 建成，与 `create_all` 结果一致。
- [ ] 新增一个字段能通过一次 migration 平滑升级，旧数据不丢。

### 1.5 提交前漂移校验（M2 ✅ 已落地）

> 迁移写好了不代表**不会漂**：改了 `entity/*.py` 却没补迁移时，代码能跑、测试也过，
> 但用户升级后库里就是少一列。这里把 `alembic check` 挂到提交流程上，让漂移在**提交前**暴露。

**做法**（`backend/app/db/migration_check.py` + `backend/scripts/check_migrations.py`）：

1. 建一个**临时 SQLite 文件**，从零 `upgrade head`（顺带验证迁移链本身可执行）；
2. 对这个临时库执行 `alembic check`（等价于命令行，比对"迁移建出来的结构"与"ORM 元数据"）；
3. 有差异 → 打印差异清单 + 修复指引，退出码 1；无差异 → 退出码 0。

**为什么用临时库而不是开发者的 `app.db`**：本地库可能落后几个版本或手工改过，
直接比对会产出与提交内容无关的噪音；临时库检验的是"一份干净的迁移链是否与实体一致"，可复现。

**已知噪声的过滤**（写在 `migrations/env.py` 的 `_include_object`，并有注释）：
- LangGraph 自管的 `checkpoints` / `writes` / `checkpoint_blobs` / `checkpoint_writes` 不参与比对（否则会报"删表"）；
- SQLite 的 `INTEGER PRIMARY KEY` 反射出来恒为 `nullable=True`，与 metadata 恒冲突，按"主键 + 整型"放过整列比较。

**接入方式**：

| 入口 | 命令 | 说明 |
| --- | --- | --- |
| 手动 | `pnpm run check:migrations` | 提交前自检；也用于排查 CI 失败 |
| git 钩子 | `pnpm run setup:hooks`（`setup` 已包含） | 设置 `core.hooksPath=.githooks`，`pre-commit` 自动跑上一条 |
| 测试 | `backend/tests/test_migrations.py::test_entities_match_migrations` | 忘记写迁移时这条用例直接失败，失败信息里有字段名 |

实测：插入一个未迁移的字段后，输出 `add_column chat_session.drift_probe` 并以 1 退出；移除后恢复 `No new upgrade operations detected.`。

## OPS-2 密钥安全（钥匙串）—— 依赖 ARCH-2 设置接口

> 决策已在 ARCH-2 给出：**密钥走系统钥匙串，普通设置入表**。这里落地实现细节。

### 2.1 设计

- 后端新增 `services/secrets.py`，统一入口：
  - `get_secret(key) -> str | None`
  - `set_secret(key, value) -> None`
  - `delete_secret(key) -> None`
  - `has_secret(key) -> bool`（前端只显示「已设置/未设置/末四位」）
- 实现：

  - 降级：`keyring` 不可用 → Fernet 加密存 `app_settings`，Fernet 密钥文件放应用数据目录（权限 0600）。
- **永不**在日志、`/api/settings` 响应、错误信息里输出完整密钥。

## OPS-4 自动更新 —— ✅ 已落地（M5 收尾批）

### 4.1 设计

- Electron 主进程接入 `electron-updater`（electron-builder 生态现成）。
- 走 GitHub Releases / 自建静态源；`electron-builder.yml` 加 `publish` 配置。
- 更新检查：启动时 + 手动「检查更新」；设置页可关自动检查。

### 4.2 落地记录

| 动作 | 文件 | 内容 |
| --- | --- | --- |
| 新增 | `electron/src/shared/update.ts` | `UpdateStatus` / `UpdateState`，三个进程共用的状态形状 |
| 新增 | `electron/src/main/updater.ts` | `initUpdater()` / `checkForUpdates()` / `maybeAutoCheck()`；IPC `update:state`、`update:check`、`update:install`、`app:version` |
| 扩展 | `electron/src/main/index.ts` | `bootstrap()` 里 `createWindow()` 之后 `initUpdater(() => mainWindow)` + `void maybeAutoCheck(handle.port)` |
| 扩展 | `electron/src/preload/index.ts` | `window.desktop.updates.{getState,check,install,onState}` 与 `getAppVersion()` |
| 扩展 | `electron/electron-builder.yml` | `publish: [{provider: generic, url: ...}]`（打包时生成 `resources/app-update.yml`） |
| 扩展 | `backend/app/services/ops_settings_defs.py` | `ops.auto_update_check`（BOOL，默认开，diagnostic 分区） |
| 扩展 | `frontend/env.d.ts`、`frontend/src/views/AboutView.vue` | 版本号 + 更新状态 + 「检查更新 / 立即重启安装」 |
| 扩展 | `frontend/tests/components/FilePathChip.spec.ts`、`frontend/tests/unit/http.spec.ts` | 桌面 API 替身补齐新字段（否则 typecheck 报缺属性） |
| 新增 | `backend/tests/test_ops_update_check.py` | 键声明正确 + 能随配置导出导入（2 条用例） |

**关键取舍**：

1. **`autoDownload = false` + 原生对话框**：发现新版本先问「下载 / 以后再说」，下载完再问「立即重启安装 / 稍后」。
   不用页面弹层，是因为更新时页面可能正处在任何状态（甚至白屏）；`autoInstallOnAppQuit = true` 保证选了「稍后」也不会无限拖延。
2. **开发态不检查**：未打包时 electron-updater 找不到 `app-update.yml` 会直接抛错，`checkForUpdates()` 在这里提前返回
   `status='disabled'` 并给一句人话说明——让「关于」页在 `pnpm run dev` 下也讲得通，而不是显示一个红色错误。
3. **自动检查开关放在后端设置里**（`ops.auto_update_check`）而不是 Electron 自己存一份：
   否则会出现「设置页关了它、下次启动还是检查」的分裂状态。代价是改完要**下一次启动生效**（代码注释里写明了），
   换来的是这个开关也能随 OPS-5 的配置导出搬到另一台机器。
4. **状态广播而不是轮询**：`update:state-changed` 单向推给渲染进程，页面只在挂载时补一次 `getState()`，
   避免「关于」页定时器一直转。

### 4.3 验收标准

- [x] 可关闭自动更新：`ops.auto_update_check=false` → 桌面壳启动时读它为 false，只把状态置为 `disabled`，不发检查请求。
- [ ] 发布新版本后，旧版能检测并引导安装 —— **代码链路完整（检查 → 下载 → 重启安装），但没有做过真实发布验证**：
      需要一份签名安装包 + 可访问的 `publish.url`，本机（无代码签名证书、`publish.url` 是占位地址）无法完成。
      详见 §7 风险表最后一行。

**关键取舍**：

1. **密钥只导出「设置过没有」，导出值不进明文**：先跑一遍 `diagnostic_service.redact(value, key)`，
   只要脱敏后与原值不同，就**整键替换成 `***REDACTED***` 并记进 `redacted_keys`**。
   留一半结构（例如只抹 `env` 里那个值、其余照抄）会让用户误判"这份文件是干净的"，
   而导入端还会把占位符写回配置——两边都不安全。
2. **导入不原子**：跨版本配置必然含本机没声明的键，原子写入会让整份导入失败。改为逐键取舍，
   并把 `skipped: [{key, reason}]` 回给前端列出「哪些没进来、为什么」。
3. **`secrets.` 前缀的判断必须早于 `get_def()`**：否则用户拿到的是"未声明的设置键"这种误导性原因
   （密钥本来就不该出现在配置里，理由是"密钥不随配置导入"）。这个坑在实现时踩过一次，已修并有测试钉住。
4. **导入后立即生效**：成功后前端 `Promise.all([settingsStore.loadAll(), workspacesStore.loadAll()])`；
   后端 `put_settings` 本来就会 `publish`，工作区订阅者会刷新 `tool_utils.WORKSPACE_ROOTS`——所以模型/工作区/主题都会立刻变。

**会话导出**：与 UX-4 共用 `GET /api/chat/history/sessions/{id}/export?format=md|json`（返回文本而非 `FileResponse`，
Electron 里由前端落盘，免去主进程再开一次保存对话框）。

**全量备份（`app.db` + FAISS）本轮不做**：SQLite 文件在后端运行期间被打开，
直接拷贝存在拿到半写状态的风险；正确做法是停服拷贝或走 SQLite 在线备份 API，
属于独立一块工作。当前诊断包（OPS-3）已含库版本、关键表计数与日志，够定位问题。

### 5.3 验收标准

- [x] 配置导出不含密钥（有测试：植入 `sk-...` 后断言导出文本里搜不到，且该键进 `redacted_keys`）。
- [x] 导入后模型/工作区/主题恢复（`llm.model`、`workspaces.*`、`theme.*` 都是普通设置键，

## OPS-6 Agent trace 结构化留存 —— ✅ 契约冻结（M2）+ 落库（M4 第二批）

> **为什么必须在改造前**：trace 的**数据表**可以用 Alembic 随时加（无压力），但 SSE 事件
> （`done`/`tool_end`/`plan` 等）的**字段契约**必须一次定全——事件发布后再补字段，历史会话回放就不兼容。
> 因此事件契约与 OPS-1（M0）/ M2 事件设计同批冻结；表与落库可在 M5 实现。

### 设计

- **事件契约规则**：凡落库/回放需要的字段，事件首发版本就带上。具体补齐：
  - `tool_end` 补 `total_chars` / `truncated` / `continuation_ref`（EXT-5 输出治理字段）；
  - `done` 补 `usage`（UX-5）+ `subtasks`（TASK）+ `steer_count`（ARCH-6）+ `model`（按轮记模型）。

> ✅ **M2 已实现**：`GET /api/chat/events` 就是这份契约的可执行版本；
> `chat_controller._tool_end_payload` / `_done_payload` 为唯一构造入口，字段恒定存在（无值时为 `null`），
> `backend/tests/test_event_contract.py` 把字段名钉住。`usage` 已由各 provider 的 `usage_metadata`
> 按轮累加填**真实值**（不是估算），`subtasks`/`steer_count` 仍为占位。
- **trace 表**（Alembic 0003，已落地）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | int PK | 自增主键 |
| `session_id` | str, 索引 | 会话 id |
| `turn_id` | str | 一轮用户请求（steer / confirm / budget 事件同 turn 归属） |
| `seq` | int | 步骤序号（turn 内递增） |
| `kind` | str | tool_call / steer / confirm / budget / plan_update |
| `payload_json` | str | 结构化内容；大对象只存 EXT-5 continuation 引用，不存全文 |
| `duration_ms` | int | 该步耗时 |
| `created_at` | datetime | 时间戳 |

- **写入**：`chat_controller` 事件发射处旁路落库，`trace.enabled` 开关控制；**落库失败只记日志，绝不影响对话**。

> ✅ **M4 第二批已落地**：表 `trace_events`（迁移 0003），服务 `app/services/trace_service.py`。
> 埋点位置（都在 `chat_controller`）：`turn_start`（`_start_turn`）、`tool_call`（四处 tool_start）、
> `tool_result`（`_tool_end_payload`，一处覆盖全部 tool_end）、`confirm`、`budget`、`done`（`_finish_turn`）、`error`。
> `seq` 由服务层按 turn 维护（**不用自增 id 排序**：并发会话会穿插）。
> 查询接口 `GET /api/trace/sessions/{id}?turn_id=`；过期清理按 `trace.keep_days` 在启动时执行。
> payload 里单个字符串截断到 2000 字符——大内容本来就已经被 EXT-5 落到 `tool-out-*`，这里不存第二份。
- **消费方**：OPS-3 诊断包含 trace；UX-4 历史会话按事件流回放；B8 eval（`doc/2.0/质量评估/eval轨迹回放.md`）以 trace 为数据源。

## 7. 风险与回滚

| 风险 | 缓解 |
| --- | --- |
| Alembic 基线冻结错误 | 首版 migration 用 autogenerate + 人工逐表核对 |
| keyring 依赖跨平台 | 降级路径 + 单点封装 |
| 自动更新分发 | 先手动安装包验证，再开自动更新 |
| 自动更新**未经真实发布验证** | 代码链路完整，但 `publish.url` 仍是占位地址、也没有可签名安装包；正式发布前必须先上传一份带 `latest.yml` 的安装包到真实源，再用旧版实测「检查 → 下载 → 重启安装」 |
| 配置导出把密钥带出去 | 导出前跑 `diagnostic_service.redact()`，键名命中即整键换占位符并记进 `redacted_keys`；导入端拒绝占位符（有测试） |
| 导入把别的机器配置写坏 | 逐键 `coerce` 校验，非法项进 `skipped` 不落库；密钥命名空间永久排除 |
