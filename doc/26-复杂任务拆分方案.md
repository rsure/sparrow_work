# 复杂任务拆分方案（独立模块 TASK）

> **状态（Phase 1 已落地）**：控制器层编排 + 规划/调度服务 + 前端 Todo 面板 + 写前校验。
> Phase 2（并行分道 / 子 agent 隔离 / 快照回滚 / 动态重规划）未做，见 §10 与文末实现说明。
>
> 本模块**独立成册、可开关、可分期**：Phase 1 只动 `chat_controller` + 新增规划服务 + 前端 Todo 面板，
> 复用现有单 agent 与工具链；Phase 2 再升级为 LangGraph 子图多 agent。
> 对应总计划里的 **TASK 复杂任务拆分**，是「真正可用 AI 客户端」的头号能力之一。
> **增补（改造前必须定稿）**：§5.1 验证闭环、§5.2 动态重规划、§5.3 文件冲突防护——子任务 schema 的
> `verify` / `files` 字段、`plan_update` 事件与「读后写」校验契约随本方案冻结，方案发布后再改即协议破坏。

---

## 1. 目标

1. **分析任务强度**：判断一个请求是「一步能答」还是「需要多步」。
2. **复杂任务拆子任务**：把复杂任务拆成有序、可独立执行的子任务列表。
3. **逐个执行 + 汇总**：执行各子任务，最后汇总成主任务的最终回答。
4. 前端实时展示**任务计划与进度**（复用 UX-1 右栏的 Todo 位）。

---

## 2. 现状结论（已核查）

- 当前是**单 agent 循环**：`agents/rag_agent.py` 用 `create_agent(model, tools, ...)` 生成「模型 ⇄ 工具」图。
- `chat_controller.py` 用 `max_iterations`（默认 25）做递归上限；复杂任务一旦步数耗尽，走 `GraphRecursionError` 分支，
  现在的处理是**丢现场 + 提示「请把任务拆小一些」**（`chat_controller.py` 的异常分支）。
- **没有任何「任务拆分 / 计划 / 汇总」机制**——复杂任务靠模型自己硬扛，扛不动就报错，用户只能手动拆。

结论：需要一套「先规划、再分步执行、最后汇总」的编排，把「任务拆分」从用户的负担变成系统能力。

---

## 3. 总体设计：三阶段流水线

```
用户请求
   │
   ▼
[1 强度分析 Judge]  模型判复杂度：simple → 直接走现有 agent；complex → 产出子任务列表
   │ (complex)
   ▼
[2 拆分 Plan]       拆成有序子任务 [{id,title,description,depends_on,files}]，推 plan 事件 → 前端 Todo
   │
   ▼
[3 执行 Execute]    逐个执行子任务（复用现有 agent+tools+确认），推 task_start/task_end 更新进度
   │
   ▼
[4 汇总 Summarize]  把各子任务结果整合成最终回答 → done
```

---

## 4. 强度分析与拆分（Judge / Plan）

- **触发**：用户提交后、进入 agent 之前，先用裸模型（`rag_agent.model`，不挂工具）跑「强度分析」prompt，要求输出 JSON：

```json
{ "complexity": "simple" | "complex", "subtasks": [ ... ] }
```

- **子任务结构**：
  - `id`：序号（1 起）
  - `title`：一句话标题（前端 Todo 展示）
  - `description`：给执行用的明确目标 + 完成标准
  - `depends_on`：依赖的子任务 id 列表（首版可只支持顺序执行，忽略依赖）
  - `verify`：可选的验证命令；缺省时取**当前工作区**的 `verify.commands` 设置（见 §5.1 与 `27-设置体系规范.md`）
  - `files`：该子任务**预计写入**的文件（工作区相对路径数组，可为空；只读文件不必列）——冲突检测的依据，见 §5.3

- **simple 直接走原链路**：`complexity=simple` 时行为与现在完全一致，零开销、零回归。
- **拆分原则（写进 prompt）**：子任务应「可独立执行、有明确完成标准、数量 2~7 个」，避免拆得过碎。

---

## 5. 子任务执行（Execute）

- **逐子任务复用 `_drive_agent`**：每个子任务作为一次 `_drive_agent` 输入，沿用现有 tools / `interrupt()` 确认 / checkpointer。
- **预算分配**：`max_iterations` 按子任务拆分（如总 25 均分到 N 个子任务，剩余兜底），避免一个子任务耗尽全部步数。
- **上下文共享**：Phase 1 子任务同在一个 checkpointer thread（会话上下文延续），汇总时能拿到各子任务中间产出；Phase 2 按 lane 分 thread（§5.3 L3），禁止同 thread 并发写 checkpoint。
- **进度事件**：每开始/结束一个子任务，推 `task_start` / `task_end`（含子任务结果摘要），前端 Todo 勾选。
- **失败隔离**：某子任务失败不整体崩溃，标记失败并把原因带进汇总（或让模型重试一次）。

### 5.1 验证闭环（Verify）—— 增补：随本方案定稿，改造前必须纳入

「执行 → 验证 → 纠错」是 agent 的核心循环；缺验证的拆分只是「分别硬扛」。

- **验证来源**（优先级从高到低）：子任务自身的 `verify` 字段 → 当前工作区的 `verify.commands` 设置（如 `pnpm typecheck`，按工作区存储，见 `27-设置体系规范.md` §5.2）→ 两者皆无则**静默跳过**（不视为失败）。
- **编排**：子任务执行完成 → 运行 verify 命令（复用 RUN_TOOLS，走权限确认）→ 失败则把**报错输出喂回同一子任务重试一次**（报错走 EXT-5 输出外壳，截断保护生效）→ 重试仍失败标记 `verify_failed` 进汇总。
- **开关**：`agent.verify_loop_enabled`（默认开）。

### 5.2 动态重规划（Replan）—— 增补：事件与 schema 必须改造前定稿

静态拆分跑偏后，执行中无法中途调整。首版提供最小闭环：

- **触发**：某子任务失败（含 `verify_failed`）后，模型可申请 replan——输出调整后的**完整**子任务列表（增/删/改），附 `reason`。
- **事件**：新增 SSE `plan_update`（负载同 `plan` 另含 `reason`，见 §7）；前端 Todo 面板原位更新，历史计划可展开对比。
- **人工介入**：`plan_update` 后默认**暂停等待用户确认**（复用 confirm_required 链路）——计划变更是高风险动作，不自动执行。
- **开关**：`task.replan_enabled`（默认 **off**，首版保守）；关闭时失败子任务只进汇总，不重规划。

> **落地记录（Phase 2 已完成）**：
> - 重规划逻辑在 `app/services/task_planner.py` 的 `build_replan_prompt` / `make_replan`，编排在
>   `chat_controller.py` 的 `_maybe_replan`（子任务收尾时调用）与 `_run_replan_resume`（处理确认）。
> - `plan_update` 负载是 `{reason, subtasks, pending}`：`pending=true` 是"待确认的草稿"，
>   确认后后端**再推一条** `pending=false`；拒绝时改推一条原有的 `plan` 事件（前端 Todo 回到原计划）。
> - 确认复用 `confirm_required`，但 `kind="replan"` 且 `can_remember=false`——它问的是"要不要换计划"，
>   和"允不允许写这个文件"不是一类事，不该给"记住授权"。
> - 一轮只重排一次（`sess.task_replan_pending` 非空就不再申请），避免失败→重排→再失败的无限循环。
> - 模型给出的新列表无法解析或缺字段时**保持原计划**继续，绝不让一次解析失败把整轮断掉。

### 5.3 文件冲突防护 —— 增补：schema 与写入契约必须改造前定稿

> **结论：原方案不能避免「多个子任务改同一文件」的错误。**
> 串行执行只消除了「并发写」，消除不了**语义覆盖**：后一个子任务从上下文中拿旧版本内容整文件回写，
> 就会覆盖掉前一个子任务的修改（lost update）。更根本的是，`subtasks` 里没有「涉及哪些文件」的字段，
> 系统连「两个子任务会碰同一文件」都识别不了，无法提示、无法调度。Phase 2 并行后还会叠加真并发写
> 与同 thread 并发 checkpoint 问题。
> 本节给四层防护：**计划期定作用域 → 写入期乐观锁 → 调度期分道 → 收尾期快照回滚**。

#### L1 计划期：子任务声明文件作用域（最便宜、最有效）

- `subtasks[].files` 由 planner prompt 强制输出（只列**写入**目标，不列只读文件）。
- **冲突检测**：计划生成后两两取 `files` 交集，得到冲突组，按 `task.conflict_policy` 处置：

| 策略 | 行为 | 适用 |
| --- | --- | --- |
| `merge`（默认） | 冲突组**合并为一个子任务**（同一文件尽量一次改完） | 大多数场景 |
| `serialize` | 保留拆分，后者强制 `depends_on` 前者，且每步后必跑 verify | 改动确实要分阶段（先实现、再改测试） |
| `block` | 不自动执行，弹计划确认，让用户手动调整 | 高价值/高风险工作区 |

- **UI**：Todo 面板每子任务显示 `files`，冲突项标红并可一键合并（写回 `plan` 确认流程）。

#### L2 写入期：读快照 + 写前校验（乐观锁，防丢失更新）

- **读快照登记**：工具层维护 `(thread_id, path) → {hash, read_at}`，`read_file` 时登记；`edit_file` 命中后更新。
- **写前校验**（`write_file` 与 `edit_file` 均适用）：
  1. **未读先写一律拒绝**——已存在的文件若本 thread 无读快照，直接拒绝并要求先 `read_file`（堵住「凭上下文旧拷贝整文件回写」）；
  2. **hash 不一致即拒绝**——磁盘当前 hash ≠ 登记 hash，返回「文件在读取后被修改（其它子任务或用户），请重新读取后再写入」+ 当前内容摘要（走 EXT-5 外壳截断）。
- **优先增量编辑**：新增 `edit_file`（精确 `old → new` 字符串替换，未命中即报错），SYSTEM_PROMPT 规定：
  **改现有文件一律用 `edit_file`**；`write_file` 只用于新建或整文件重构（需说明理由）。
- 被拒写入不终止任务：模型重读后重试（计入 `max_iterations`）。
- 开关 `task.write_stale_guard`（默认开）。该机制**独立于拆分**，主 agent 同样受保护。

#### L3 调度期：依赖生效 + 分道并行

- **Phase 1（串行）**：按 `depends_on` 拓扑排序（有环 → 退化列表顺序并警告）；每子任务结束必跑 verify（§5.1）。
- **Phase 2（并行）**：以 `files` 交集做**并查集分道**——同文件子任务同一 lane，lane 内串行、lane 间并行；
  每 lane 独立 `thread_id`（禁止同一 thread 并发 checkpoint）；**文件级线程锁**（`path → RLock`）兜底；
  并发度 ≤ `task.max_parallel_subtasks`（Phase 1 恒为 1）。
- 跨 lane 的 `depends_on` 退化为同 lane（依赖必须先完成）。
- **落地修正（与原文一处不同）**：兜底锁用的是 `threading.RLock`（`app/tools/path_lock.py`）而不是原文写的
  `asyncio.Lock`。原因：工具函数都是同步 `def`，LangGraph 把它们丢进线程池执行，
  同一个事件循环之外抢 `asyncio.Lock` 既拿不到也不会阻塞——真正能互斥的只有线程锁。
  加锁点：`write_file` / `edit_file`（整段"校验→备份→落盘→登记"）与 `file_ops` 的单项操作（**只锁 src 不锁 dst**，
  否则 A→B 与 B→A 并发会互相等锁死掉）。
- 分道用并查集取**传递闭包**：a↔b 因同一文件、b↔c 因同一文件时，a/b/c 必须三者同道（否则 a 与 c 会并行）。

#### L4 收尾期：按子任务快照与回滚 + 汇总前复核

- **快照**：子任务开始前把 `files` 涉及的现存文件复制到应用数据目录 `.task_snapshots/<turn_id>/<subtask_id>/`
  （只备份被写文件，不备份整库），记录 `(path, hash, backup_path)`。
- **回滚**：子任务失败 / `verify_failed` / 汇总前全量验证失败 → 可**按子任务粒度**还原，不影响其它子任务结果。
- **汇总前复核**：跑一次工作区级 verify；同一文件被多个子任务改过时，把累计 diff 附进汇总，用户能看清最终改了什么。
- B1 git 工具（`doc/2.0/工具生态/git工具.md`）落地后，快照可替换为 `git stash` / 临时 worktree，更省空间。

#### 设置项（见 `27-设置体系规范.md`）

`task.file_scope_guard`（on）/ `task.conflict_policy`（merge）/ `task.write_stale_guard`（on）/ `task.max_parallel_subtasks`（1）。

#### 验收标准

- [x] 「A 写 X、B 也写 X」的用例：`merge` 下计划合并为一个子任务；`serialize` 下 B 带 `depends_on=[A]` 且逐步 verify。
      （`backend/tests/test_task_plan.py` 的 `test_serialize_policy_adds_dependency` / `test_merge_policy_merges_group`）
- [x] 读文件后由外部改动（模拟另一子任务写），模型 `write_file` 被拒并提示重读；重读后写入成功，任务不卡死。
      （`test_task_plan.py` 的 `test_write_rejected_when_changed_after_read`）
- [ ] 未 `read_file` 直接 `write_file` 覆盖已存在文件被拒（未读先写防护）。—— **有意不做**，理由见 §15.2 第 3 条。
- [x] Phase 2：同 lane 串行、异 lane 并行；并发写同一文件无交错损坏（文件锁 + 乐观锁双保险）。
      （`backend/tests/test_task_phase2.py`：`test_build_lanes_is_transitive_closure` / `test_path_lock_serializes_same_path` /
      `test_parallel_lanes_run_each_subtask_once`）
- [x] 子任务 verify 失败可回滚其写入，其它子任务结果保留。（`_finalize_task` → `_rollback_task`；
      `test_snapshot_and_restore_existing_file` / `test_restore_removes_file_created_by_subtask`）

## 6. 汇总（Summarize）

- 全部子任务完成后，用「汇总」prompt 把各子任务结果整合成最终回答（引用关键文件/结论）。
- 汇总产物经现有 `done` 事件返回（含 `answer`、`tool_calls`、`files` 等现有字段）。

## 7. SSE 事件扩展

在现有 `thinking/token/tool_start/tool_end/confirm_required/stopped/done/error` 之外新增：

| 事件 | 负载 | 说明 |
| --- | --- | --- |
| `plan` | `{subtasks:[{id,title,description,files}]}` | 拆分结果，前端初始化 Todo 列表（含文件作用域，冲突项标红） |
| `plan_update` | `{subtasks, reason, pending}` | 动态重规划后的新计划（§5.2）；`pending=true` 是待确认草稿，确认后同事件再发一次 `pending=false` |
| `task_start` | `{id,title,index,total,lane?}` | 子任务开始；并行时多一个 `lane`（车道号），`index` 为 null（没有全局序号） |
| `task_end` | `{id,title,summary,status,lane?}` | 子任务结束（success/failed/verify_failed）；并行时带 `lane` |

> `done` 事件可附带 `subtasks` 字段（含各子任务状态），历史会话也能回放计划。
> 并行车道执行期间**不发 `token`**：多个车道同时逐字输出会互相穿插，改成每条车道跑完后整段补发一次。

## 8. 与现有能力联动

| 能力 | 联动方式 |
| --- | --- |
| `max_iterations` | 按子任务均分预算 + 总兜底 |
| `interrupt()` 确认 | 子任务内的写/执行操作照旧弹确认，不受拆分影响 |
| checkpointer | 子任务同 thread，上下文延续；ARCH-4 持久化后跨重启可恢复 |
| MEM 记忆 | 汇总后可把关键结论写入工作区记忆（可选，联动 `memory`） |
| UX-1 右栏 | Todo 面板渲染 plan / 进度（复用 ContextPanel 的 Todo 位） |

## 13. 风险与回滚

| 风险 | 缓解 |
| --- | --- |
| 强度分析多一次 LLM 调用（费时/费钱） | 开关可关；simple 判定也可先用启发式规则降本 |

### 15.2 与原文的三处有意偏离

1. **判定与拆分合并为一次模型调用**（原文是 Judge + Plan 两次）。
   理由：两次调用里第一次只输出一个布尔值，性价比太低；用启发式预筛代替"每次都要问模型"。
2. **校验失败不自动重试**（原文要求"重试一次"）。
   理由：重试同样可能触发写确认，一旦在重试中途 `interrupt()`，"第几个子任务"与 resume 链路会纠缠不清。
   现在的做法是把校验输出写进该子任务摘要，由汇总模型在最终回答里如实说明。
3. **不强制"未读先写一律拒绝"**（原文 §5.3 L2 第 1 条）。
   理由：模型经常在几轮前读过文件，强制重读会产生大量无意义往返，且无法区分"没读过"与"登记被淘汰"。
   只保留真正危险的判定：**读之后磁盘内容变了**。这条能挡住所有"丢失更新"，误伤最小。

### 15.3 状态机（改这段前务必先看）

```
_run_with_tasks
  ├─ 开关关 / 判 simple / block 策略 → _drive_agent(finalize=True)   ← 与改造前完全一致
  └─ plan.is_complex → order_subtasks → build_lanes → flatten_lanes（压平成执行顺序）
       sess.task_plan = plan; 发 plan 事件
       └─ _drive_tasks（循环 sess.task_cursor）
            ├─ 并发度 > 1 且 parallel_ok 且车道数 > 1
            │    └─ _drive_lanes_parallel（每车道一份 SessionState + 独立 thread_id）
            │         ├─ 某车道停在 interrupt → 记 task_pending_lane / task_lane_state，其余车道取消
            │         └─ 全部跑完 → 各车道文本按车道号顺序整段并回主会话
            ├─ 发 task_start → _snapshot_task → _drive_agent(finalize=False)
            │    ├─ 停在 interrupt → 返回（游标不动），前端弹确认
            │    └─ 跑完 → _complete_subtask
            │         ├─ _finalize_task（校验；失败则 _rollback_task 还原该子任务的文件）
            │         └─ 失败且 task.replan_enabled → _maybe_replan → 发 plan_update + confirm_required
            └─ 全部跑完 → _summarize_tasks（token + done + done.subtasks）

/chat/resume（_run_resume_stream 按三类挂起状态分发）
  ├─ pending_action == "replan" → _run_replan_resume
  │    ├─ 同意 → 换计划、task_cursor = 0、再发一次 plan_update(pending=false) → _drive_tasks
  │    └─ 拒绝 → 发一条 plan 事件回到原计划 → _drive_tasks（继续剩余子任务）
  ├─ pending_action（原生 interrupt） → _run_native_resume
  └─ task_pending_lane → _run_lane_resume
       ├─ 该车道又停在 interrupt → 只更新挂起信息后返回
       └─ 跑完 → 收尾该子任务 → 删掉车道 thread → _drive_tasks(parallel_ok=False) 串行收尾
```

`_finish_turn` 会清掉 `task_plan`（本轮结束）并调用 `_cleanup_task_resources`（删车道 thread + 清快照目录），
`_start_turn` 会清掉 `subtask_results` 与全部 Phase 2 字段（下一轮重置）。

### 15.4 Phase 2 实现说明

**并行怎么做的**：没有引入 LangGraph 子图，而是"每个车道一份 `SessionState` + 一个独立 `thread_id`"。
理由：子图的收益是隔离与编排，而这里需要隔离的只有"上下文与 checkpointer"，一个独立的 `thread_id` 就够了；
换成子图要重写 `_drive_agent` 的事件转发，风险远大于收益。车道 thread 在 `_finish_turn` 与车道收尾时都会
`checkpointer.delete_thread`，不会在磁盘上累积。

**并行的三条硬限制**（都是有意为之，不是没做完）：

1. **并行只在"整轮从没停过"时成立**。任一轮里出现过 `interrupt()`（写文件确认）或预算暂停，
   恢复后一律以串行收尾（`_run_lane_resume` / `_run_replan_resume` 都传 `parallel_ok=False`）。
   理由：多个车道同时弹确认会让"这个确认是哪个子任务的"无法回答，`pending_interrupt_id` 只有一个位置可存。
2. **并行车道不发逐字 `token`**。多条车道同时输出会互相穿插，读起来是乱码；改成每条车道跑完后整段补发。
3. **一轮只重排一次**。`sess.task_replan_pending` 非空后 `_maybe_replan` 直接返回，避免
   "失败 → 重排 → 再失败 → 又重排"烧钱。

**快照的边界**：只备份子任务 `files` 里声明的文件、且单文件超过 8MB 时跳过（记 `skipped`，不阻断执行）；
回滚时"原本不存在、现在存在"的文件会被删掉——那是该子任务新建的，留着就是失败残留。
备份目录在应用数据目录（`app.core.paths.data_dir()`）下的 `.task_snapshots/`，不在用户工作区里，
不会污染项目、也不会被文件扫描工具扫到。
