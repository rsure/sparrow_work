# 扩展性层改造方案 —— Skill / MCP / 工具生态 / 工具输出治理契约

> 对应总计划里程碑 **M4**（EXT-1/2/3/4）；
> 另含「改造前必须定稿」的增补模块 **EXT-5 工具输出治理契约**（M0/M1 与工具层改造同批，先于一切工具扩建）。
> 目标：让客户端像 Claude Code 一样**可扩展**——装 Skill、接 MCP、不断长出新的工具能力，
> 同时所有新能力都**复用现有权限模型**，不另开一套安全。

---

## 1. 目标

1. **Skill 系统**：可安装、可发现、可调用的「技能包」。
2. **MCP 客户端**：可配置、可连接外部 MCP server，把其 tools 动态挂进 Agent。
3. **工具生态**：在现有原子工具之上，补齐常用能力，并统一工具权限粒度。

---

## 2. 统一设计原则（关键）

> Skill 与 MCP 本质都是「给 Agent 增加能力」，**共用一套扩展注册表 + 权限确认**，否则两套并行维护成本翻倍。

统一后的扩展生命周期：

```
定义(manifest) → 发现/注册 → 装配成 LangChain Tool → 挂到 agent 的 TOOLS 列表
                          ↓
              所有新工具执行前：走 tools/policy.py 的策略登记
              有风险的操作：复用 interrupt() 确认（与现有 write_file/delete 一致）
```

## EXT-1 Skill 系统 —— ✅ 已落地（M4 首批）

> **实现说明**：目录约定与 SKILL.md 格式按下方设计落地（单层 `root/*/SKILL.md`）。
> 与本文的差异：``tools`` 只作**声明与展示**，不做强制限制——技能本质是提示词，
> 它调用的工具仍要过 `policy` 的确认与 DENY，硬性限制"技能只能调某几个工具"反而会
> 让"技能说要读文件、但工具在白名单外"变成难解释的失败。首版选择"声明 + 审计可见"。

### 1.1 设计

参考 Claude Code 的 Skill 形态，落地为「本机目录 + frontmatter 清单」：

```
skills/                          # 用户级 skill 目录（默认 ~/.<app>/skills）
└── 某个技能/
    └── SKILL.md                 # 清单 + 指令正文
```

`SKILL.md` 结构（精简版）：

```markdown
---
name: my-skill            # 唯一 id，kebab-case
description: 一句话说明，模型据此判断何时调用
tools: [read_file]        # 可选：该 skill 需要哪些底层工具的权限
---
（正文：给模型的指令，模型遇到匹配场景时按此执行）
```

### 1.2 两种调用方式（覆盖不同场景）

| 方式 | 说明 | 类比 |
| --- | --- | --- |
| **自动触发** | 把 skill 的 `description` 注入系统提示词，模型判断命中时「阅读 SKILL.md 正文后执行」 | Claude Code 的 skill |
| **斜杠指令** | 用户输入 `/skill-name args`，程序直接解析执行，不经过模型 | 现有 `\doc` 指令的泛化 |

> 关键复用点：现有 `chat_controller.py` 的 `_parse_doc_command` / `\doc` 分派，就是「斜杠指令」的雏形，把它泛化成**通用 slash command 框架**，`\doc` 变成其中一个内置 skill。

## EXT-2 MCP 客户端 —— ✅ 已落地（M4 第二批）

> **依赖已安装**：`mcp==1.30.0` + `langchain-mcp-adapters==0.3.2`
> （`uv add` 时顺带把 `websockets` 从 17.2 回落到 16.1.1，正是 pyproject 里锁的 `<17`，符合预期）。
> 与最初设计的差异集中在"权限"与"配置存放位置"，见下面的实现修订。

### 2.1 设计（原方案）

1. **配置**：MCP server 列表存 `app_settings`（key=`mcp_servers`），支持三种传输；
2. **连接管理**：启动/懒加载连接，缓存 `MultiServerMCPClient`，设置变更时重连；
3. **装配**：`client.get_tools()` → 包装成带权限策略的 LangChain Tool → 并入 agent 的 TOOLS；
4. **权限**：MCP 工具默认「高危需确认」，复用 `interrupt()`；可按 server/工具名加白名单。

### 2.2 实现修订（落地时改了什么，为什么）

| 原设计 | 实际做法 | 原因 |
| --- | --- | --- |
| 设置键 `mcp_servers` | `mcp.enabled` / `mcp.servers` / `mcp.auto_approve_tools` | 与 doc/27「组.键」命名约定一致；总开关单独一个键才能整体停用 |
| 缓存 `MultiServerMCPClient` 长连接 | **不缓存连接**，每个工具调用由适配器自建 session | 适配器本身就是这个模型（`get_tools` 后 session 关闭）；好处是单个 server 挂掉不污染后续调用 |
| 直接在 `get_tools()` 结果上加策略 | **包装成新的 StructuredTool**，调 `policy.guard()/finalize()` | 直接并进 Agent 会绕过 `policy` 的全部护栏（确认/预算/审计/截断）。包装后与内置工具走同一条路径 |
| `require_confirm=True` 表达"需确认" | `Kind.MCP` + `Policy.default_level = ASK / ALLOW` | `Kind.MCP` 默认 DENY（未知能力一律拒绝）；若只靠 `require_confirm`，免确认时 `require_confirm=False` 会退化成 DENY，把工具禁用 |
| 配置里存 `keyring secrets.mcp.<id>.token` | token 写在 `mcp.servers[].headers` / `env` | 大多数 MCP server 用一条 header 或一个环境变量；再套一层 keyring 抽象，用户反而不知道该往哪填。**脱敏由诊断导出负责**（`env`/`headers` 整段抹除） |

## EXT-3 工具生态增强 —— ✅ 已落地

> 本模块的两条核心要求（"每个工具在 policy 登记三态" + "统一入参 schema"）在既有工具上已经满足：
> `verify_all_tools_registered` 启动自检会拦住任何未登记工具。
> **本轮补齐**：`http_request`（`app/tools/http_tool.py`）与 `sql_query`（`app/tools/sql_tool.py`），
> 两者的 SSRF / 不可信内容围栏抽到共享的 `app/tools/net_guard.py`（`web_tool.py` 改为从它导入）。
>
> 说明：工具本身不是瓶颈，**瓶颈是每个工具的权限粒度与结果展示**。本模块重点：
> 1. 给每个工具在 `policy.py` 里声明 `只读/需确认/禁止` 三态；
> 2. 统一工具入参/出参的 JSON schema，便于前端渲染轨迹。

在现有 `READ_TOOLS / WRITE_TOOLS / RUN_TOOLS / GLOB_TOOLS / FILE_OPS_TOOLS / WEB_TOOLS` 之上补充：

| 工具 | 用途 | 优先级 | 状态 |
| --- | --- | --- | --- |
| `browser`（可选） | 无头浏览器取动态页 | 低（web_fetch 已够用） | 不做 |
| `sql_query` | 查本地 SQLite（面向分析类任务） | 低 | ✅ 已落地 |
| `http_request` | 通用 HTTP 调用（带域名白名单） | 中 | ✅ 已落地 |
| 工具**结果可视化** | 前端把 tool output 渲染成表格/JSON 折叠 | 归 UX-3 | 归 UX-3 |

### 3.0 两个新工具的设计要点（落地记录）

- **`http_request`**（`app/tools/http_tool.py`）
  - 只允许 `http/https`；域名白名单与私网拦截复用 `net_guard.check_url`（**跳转后再校验一次**，防 302 绕过）。
  - 非 `GET/HEAD/OPTIONS` 属"写方法"，必须同时满足 `APP_ALLOW_HTTP_WRITE_METHODS=true`，否则直接失败并提示环境变量名。
  - `GET/HEAD` 带 `payload` 直接拒绝（避免把请求体静默丢弃）。
  - 响应体按 `APP_HTTP_MAX_RESPONSE_BYTES`（默认 512KB）截断，整体包进 `<<<EXTERNAL_UNTRUSTED_CONTENT>>>` 围栏。
  - 策略：`Kind.NET` + `off_by_default=True`（同 web 工具，受 `APP_ALLOW_WEB_TOOLS` 总开关约束）+ `require_confirm=True`。
- **`sql_query`**（`app/tools/sql_tool.py`）
  - 以 `file:...?mode=ro` 的只读 URI 打开，**只允许 `SELECT` / `WITH` / `EXPLAIN`**，禁多语句、禁写关键字（两道检查）。
  - `set_progress_handler` 做 5 秒查询超时；行数上限 `max_rows`（1~200，默认 50），输出按 `列: a | b` + 行。
  - 策略：`Kind.READ` + `path_args=("db_path",)` + `path_op=OP_READ`（读操作在 `path_decision` 里天然放行，但仍走统一审计）。
- **`net_guard`**（`app/tools/net_guard.py`）：`as_untrusted` / `is_private_host` / `check_url` 三个函数一份实现，
  `web_tool` 与 `http_tool` 共用 —— 改造前 SSRF 检查只存在于 `web_tool.py`，再加一个联网工具就会有两份，改一处漏一处。

- [x] 新增工具都在 `policy.py` 登记（`verify_all_tools_registered` 自检通过）——见 `tests/test_ext_tools.py::test_new_tools_registered_with_expected_kind`。
- [x] 工具入参有完整 `Field(description=...)`，`/docs` 可读。

## EXT-4 文档解析注册表 —— ✅ 阶段 1+2 已落地；Office 家族已改走本地 Office CLI（A~D 完成，E 待桌面壳）

> **实现位置**：`app/services/document_parser.py` —— 注册表形态本身**不改**。
> **现状（阶段 1+2）**：已注册 `.pdf`（PyPDFLoader）、`.docx`（Docx2txtLoader）、`.txt` / `.md` / `.markdown`、
> `.xlsx`（openpyxl）；后缀判断已收口到 4 个调用点（工具读文件 / 文件夹批量索引 / RAG 入库 / 预览分类），
> 换行统一归一化为 `\n`（否则 Windows 文件的 `\r\n\r\n` 匹配不到切分符 `\n\n`）。
> **本轮方向调整（2026-10-20 定稿）**：Office 家族（`.docx` / `.xlsx` / `.pptx`，以及旧版 `.doc` / `.xls` / `.ppt`、
> WPS 的 `.wps` / `.wpt` 等）**不再用 openpyxl / python-pptx / docx2txt 自行解析**，改为调用**本机 Office CLI
> （`editor_sdk` MCP 服务，经 `edsdk.py` 暴露 `list` / `schema` / `call`）读取**。注册表对外契约
> （`parse_document` / `supported_suffixes` / `structured_suffixes` / `is_structured`）保持不变，**只替换 parser 实现**。
> **仍不支持**：`.rtf` / `.odt`（CLI 无对应品类）、WPS 专属 `.et` / `.dps`（引擎不支持，需另存为 `.xlsx` / `.pptx`）。

> 全部改为从注册表派生（`tool_utils` / `file_read_tool` / `rag_store_service` / `file_browse_service` 四个调用点）。
> **下面所有"新增格式"的收益都建立在这一条上：换实现只改 `document_parser` 内部，4 个调用点零改动。**

### 4.1 为什么换成 Office CLI（三条决定性理由）

| # | 理由 | 具体依据 |
| --- | --- | --- |
| 1 | **格式覆盖一次到位** | Python 路线要 `openpyxl` + `python-pptx` + `striprtf` + `odfpy` 四套库，且旧版 `.doc` 无纯 Python 方案；CLI 一次覆盖 Word / Excel / PPT 三类共 20+ 后缀，连 `.wps` 与旧二进制格式都在内 |
| 2 | **数值与结构语义由引擎给出** | Excel 公式结果、日期/数字格式、合并单元格、PPT 占位符层级都是引擎的既有语义；不必再纠结 `data_only=True` 取不到缓存值、`python-pptx` 漏掉文本框这类问题 |
| 3 | **打包与依赖风险显著下降** | 不再为每个库维护 PyInstaller `hiddenimports`（上一批 `openpyxl` 的 hiddenimports 曾静默失效，见 doc/20 附录五第 5 条）；包体少几个 MB，也少一类"打包后 `No module named`"故障 |

> 附带收益：CLI 返回的是**带坐标的结构**（段落 UTF-16 偏移、sheet 行列、slide 形状 id）。
> 后续若要做"引用到具体单元格/段落"或"AI 直接改文档"，同一条通道可直接复用，不必再引一套写库。

### 4.2 为什么不用 LibreOffice headless（备选方案对比）

| 方案 | 优点 | 缺点（决定不选的原因） |
| --- | --- | --- |
| Python 库（现状） | 纯进程内、无外部依赖、CI 友好 | 格式覆盖不全、旧格式无解、每个库都要单独维护打包 |
| `soffice --headless --convert-to txt` | 格式覆盖广、纯命令行 | 只能产出**扁平文本**，丢掉 sheet/slide/段落结构；转换精度受 LibreOffice 排版引擎影响（复杂表格、中文版式易错行）；仍需随包分发几百 MB 运行时 |
| **本地 Office CLI（选定）** | 用用户机器上真实的 Office/WPS 引擎读取，保真度最高；返回结构化坐标；无需分发运行时 | 强依赖本机引擎与服务进程；只能在本机跑（CI 需替身）；有进程间调用开销 |

> 结论：本项目定位"本机文件 + 真实文档"，**保真度与结构**的权重高于"零外部依赖"；
> 用 `office.enabled` 开关 + 失败降级（4.7）把"引擎不在"这一情形的体验兜住。

### 4.3 目标架构：注册表不变，只换 Office 家族的 parser

### 4.4 适配层 `app/services/office_cli.py`（唯一出口）

```python
# app/services/office_cli.py —— 本地 Office CLI 的唯一出口，解析链路只经过这里
READ_ONLY_TOOLS: frozenset[str]   # 允许解析链路调用的只读工具白名单（不含任何写工具）

class OfficeCliUnavailable(RuntimeError):
    """探测不到 editor_sdk 端点。调用方据此降级，不得当致命错误抛出。"""

def endpoint() -> str | None                  # 探测 39099~39108 并缓存；失败后冷却 30s，避免每个文件都超时
def call(tool: str, args: dict, timeout_ms: int) -> dict   # 唯一出口：白名单断言 → MCP tools/call → 取 result
def read_doc(path: Path) -> str               # doc 品类：结构树 + 大纲 + 文本框/批注 → 文本
def read_sheet(path: Path) -> str             # sheet 品类：子表 → 已用区域 → 分页取单元格 → 文本
def read_slide(path: Path) -> str             # slide 品类：逐页形状摘要 + 文本 + 备注 → 文本
```

**为什么不 `subprocess` 调 `edsdk.py`**：`edsdk.py` 只是 **MCP over HTTP 的客户端封装**（`list` / `schema` / `call` 三个命令），
后端直接用 `httpx` 打端点即可 —— 少一层进程，且**不依赖本机 `python3`**（PyInstaller 冻结包里没有独立解释器，
`sys.executable` 指向应用自身，起不了 `python3 edsdk.py`）。代价是 `schema` 的便利性没了，
所以适配层里内置**参数常量与断言**，用单测锁住调用形状；排障时仍可手工用 `edsdk.py` 复现同一请求。

引擎既有事实（来自 SKILL 约定，务必按此实现）：

| 事实 | 含义 / 用法 |
| --- | --- |
| 端点 | 默认从 `39099` 起顺序探测 10 个端口（39099–39108）；`editor_sdk_port` 可固定，`editor_sdk_token` 用于鉴权 |
| `open_file` | 默认 fresh open，且**只在后台装载**（不弹预览、不进用户视图）；返回 `file_id` |
| `get_pool_status` | 按 `file_path` 查 pool 中已打开的实例（该过滤带路径规范化，比编辑工具的反查更宽容） |
| 品类前缀 | `doc_*` / `sheet_*` / `slide_*` 只能作用于对应品类；类型不匹配会报错 |
| 写能力 | CLI 本身**有写工具**（插入/替换/`save_file`），解析链路必须被白名单挡住，见 4.6 |

### 4.5 一次解析的生命周期（六步）

1. **探测端点**：`endpoint()` 不可用 → 抛 `OfficeCliUnavailable` → 走 4.7 的降级，**不重试刷屏**。
2. **优先复用已有实例**：`get_pool_status(file_path=绝对路径)` 命中 → 复用其 `file_id`，并记 `owned = False`。
3. **否则后台打开**：`open_file(file_path=绝对路径, open_with_existing=true)` → `owned = True`。
   > 路径必须是**绝对路径**且与注册时字符串一致：`./a.docx` 与 `/abs/a.docx` 在反查里不是同一份。
4. **按品类只读取文本**（分页，受 `office.max_rows` / `office.max_cols` 约束）：
   - **doc**：`doc_resolve_document_structure`（扁平结构树，正文从这里拼）+ `doc_get_outline`（保留标题层级）+ `doc_list_textbox_and_comment`（文本框与批注，结构树里不一定有）
   - **sheet**：`sheet_get_sheet_info` → 逐子表 `sheet_get_used_range`（真实边界，**不得按预览猜**）→ 分页 `sheet_get_cell_data`
   - **slide**：`slide_get_info` → 逐页 `slide_get_page_info` + `slide_get_text`（可选 `slide_get_notes_text` 取备注）
5. **组装文本**：统一加结构标记 `[Sheet 名称]` / `[Slide N]` / `[第 N 段]`，用 `\n\n` 分隔（`default_splitter` 天然兼容），
   截断处沿用阶段 2 已定的标注格式（`…（超过 N 行，已截断）`）。
   > ⚠️ **doc 品类没有"导出全文"的单一工具**，必须走结构树拼接 —— 这是本方案最容易低估工作量的一处，
   > 工作量与 `read_sheet` 不在一个量级。
6. **释放**：`finally` 里**只关闭 `owned = True` 的实例**（`close_file`）。
   绝不能关用户正在看的实例 —— 那等同于把用户的编辑器关掉。

### 4.6 只读白名单（安全边界）

- 解析链路只允许 `READ_ONLY_TOOLS`（`*_get_*` / `*_list_*` / `*_find` / `*_resolve_*` / `*_calculate_*` 一类），
  `call()` 入口先断言，命中写工具直接抛 `ValueError`。白名单是**代码常量**，不进设置（不可被用户放宽）。
- 理由：CLI 是一条**有写能力**的通道。若解析链路能触达写工具，"读一个被投毒的文档"就可能变成"改用户文件"。
- `office_cli` **不注册成 Agent 工具**：它只服务解析链路，模型无法直接调用。
  要让模型编辑 Office 文档，必须另开模块并走 `policy.guard()`（同 EXT-2 那条教训：不要绕过统一护栏）。

### 4.7 失败与降级矩阵

| 情形 | 解析结果 | 用户可见提示 |
| --- | --- | --- |
| 端点探测不到（引擎未启动 / 被防火墙拦） | 回落 `_parse_text`（二进制格式基本是乱码） | 设置页「Office 引擎：未连接」；首次触发时对话里提示一次"启动 Office 引擎或另存为 `.docx`" |
| `open_file` 失败（加密、损坏、后缀与内容不符） | 回落 `_parse_text` | 工具结果里给一句原因（不抛堆栈） |
| 单次调用超时（`office.timeout_ms`） | 返回已读到的部分 + 「已超时截断」 | 不阻断整轮 |
| 行/列超限 | 截断 + 标注 | 标注写清截断位置 |
| 引擎不支持该后缀（`.rtf` / `.odt` / `.et` / `.dps`） | 判定不支持 | 明确提示"请另存为 `.docx` / `.xlsx` / `.pptx`" |

> 降级原则与阶段 1 一致：**"读到一部分"优于"整份读不了"**，但降级结果**不能被当成正常文本入库**——
> 二进制回落文本（乱码）会在结果头部带 `[降级读取]` 前缀，RAG 入库侧据此跳过，避免污染知识库。

### 4.8 新增设置键（按 doc/27 声明式注册）

| 键 | 类型 | 默认 | category | 说明 |
| --- | --- | --- | --- | --- |
| `office.enabled` | bool | on | office | Office 家族是否走本地 CLI；关掉后回落文本试读 |
| `office.port` | int（0~65535） | 0 | office | 0 = 自动探测 39099–39108；固定端口填具体值（须与桌面壳拉起引擎时一致） |
| `office.timeout_ms` | int（1000~120000） | 15000 | office | 单次 CLI 调用超时；大文件可调高 |
| `office.max_rows` | int（100~50000） | 5000 | office | 单 sheet 最多读多少行（取代常量 `MAX_XLSX_ROWS`） |
| `office.max_cols` | int（5~200） | 40 | office | 单 sheet 最多读多少列（取代常量 `MAX_XLSX_COLS`） |

> 走 doc/27 的三步：声明（`app/services/office_settings_defs.py`）→ 读（`settings_service`）→ 写（设置页 meta 驱动，零前端改动）。
> `office.port` 的**唯一真相在设置里**：桌面壳拉起引擎时读同一个键，避免"壳里固定 40000、后端还在探测 39099"。

### 4.9 分阶段落地

| 步骤 | 内容 | 前置 | 风险 | 状态 |
| --- | --- | --- | --- | --- |
| **A** | `office_cli.py` 适配层：端点探测 / 调用 / 超时 / 只读白名单 / 实例归属 / 降级异常；单测全部用假 MCP 响应（不依赖真引擎） | 无 | 低（纯新增） | ✅ |
| **B** | `.xlsx` 切到 `read_sheet`，**暂时保留 `_parse_xlsx`（openpyxl）作对照实现**，同一批表做 A/B 比对后再删 | A | 中（合并单元格、公式结果可能有差异） | ✅（对照实现**改为长期保留**作降级路径） |
| **C** | `.docx` 切到 `read_doc`，同时放行 `.doc` / `.dot` / `.wps` / `.wpt` | A | 中（doc 无全文导出工具，要拼结构树） | ✅ |
| **D** | `.pptx` / `.ppt` / `.pps` / `.pot` 走 `read_slide`（原"阶段 3"提前到位） | A | 中（逐页形状需递归并限深，避免组合形状爆栈） | ✅ |
| **E** | 桌面壳拉起 `editor_sdk`（固定端口）+ 设置页「Office 引擎」状态点；打包去掉 `openpyxl` / `python-pptx` 的 `hiddenimports` | A | 中（跨 Electron / 后端两个进程的生命周期） | ⏳ 未做（`editor_sdk` 不在本仓库） |

> 顺序理由：A 是唯一新增文件，先落地才能让 B~E 并行；B 放在 C 之前，因为 Excel 结构最规整、
> 差异最容易量化（少一格、多一行一眼能看出），最适合给适配层做第一次真实校验。

**跨阶段注意点**：

1. **性能与并发**：一次只开一个实例（批量索引串行），并对 `(路径, size, mtime)` 做文本缓存（LRU 200 条）——
   否则一次索引 50 个 Excel 会把引擎反复装载，耗时从秒级涨到分钟级。
2. **体积/行数保护**：沿用 `MAX_READ_BYTES`(20MB) 思路；Excel 用 `office.max_rows/cols` 两个设置键；
   slide 另设 200 页上限（常量），防爆内存与上下文。
3. **结构标记规范**：统一 `[Sheet 名称]` / `[Slide N]` 前缀，检索命中时能回指位置；
   Word 品类没有单一"导出全文"工具，改为拼三段并各打标记 —— `[正文]` / `[大纲]` / `[文本框与批注]`
   （**与原设计的差异**：原写 `[第 N 段]`，但引擎返回的是结构树而不是段落数组，逐段编号并不可靠，
   三段标记反而让模型能区分"正文"与"批注"，不会把批注当正文总结）。
4. **编码**：文本由引擎以 Unicode 返回，跳过编码探测；仍需 `\r\n` → `\n` 归一化（Windows 文档常见）。
5. **预览**：继续复用 `read_preview` 的 text 分支展示解析后文本，不做 Office 转图片预览。
6. **隐私**：正文只在本机引擎内处理（不出网）；日志只记路径、字符数与耗时，**不打印正文**。

### 4.11 风险与回滚

| 风险 | 缓解 |
| --- | --- |
| 引擎未随应用分发 / 端口被占 | `office.enabled` + `office.port` 双开关；探测失败冷却 + 明确提示；降级不抛错 |

| 写工具被解析链路触达 | 只读白名单 + 入口断言 + 不注册为 Agent 工具 |

| 回滚 | 保留 `_parse_xlsx` 等旧实现与 `office.enabled=off` 双通道；回滚 = 改一个设置键，**不改注册表、不改调用点** |

## EXT-5 工具输出治理契约 —— 增补：改造前必须定稿（出参统一外壳）

> **为什么必须在改造前**：EXT-3 续建工具、UX-3 轨迹渲染、ARCH-5 token 估算都要消费工具出参。
> 出参契约后改 = 全部工具与全部调用方返工。本契约与 M0/M1 同批定稿，先于任何新工具落地。

### 设计（原方案：JSON 外壳）

> ⚠️ **实现修订（M2）**：LangChain 工具的返回值必须是 `str`（模型直接读它），
> 返回 JSON 会让模型把外壳当正文。所以落地时把「外壳」拆成两层：
> **工具返回值 = 截断后的纯文本**；**结构化元数据走事件与进程内登记表**。
> 契约语义（总字符数 / 是否截断 / 续读标记）完全保留，只是不再塞进工具返回值里。

原设计（供对照）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `content` | str | 实际进入模型上下文的文本（可能已被截断） |
| `truncated` | bool | 是否发生截断 |
| `total_chars` | int | 原始输出总字符数（截断前） |
| `continuation` | ref \| null | 续读指针，指向落盘的完整输出 |

### 实现状态（M2 ✅ 已落地）

| 契约项 | 实现位置 | 说明 |
| --- | --- | --- |
| 截断 + 原始长度 | `tools/output_contract.py` | `TruncateResult{output,total_chars,truncated,continuation_ref}`；保留**前 N** 字符（保住 `OK:`/`FAIL:` 前缀），超阈值追加一句"已截断 + 续读标记"提示 |
| 统一出口 | `tools/policy.py` 的 `make_tool` wrapper | 所有注册工具在审计与返回前都过一遍；治理层自身异常时退化为"不截断" |
| `\doc` 直连链路 | `chat_controller._doc_search` | 检索摘要同样走一遍，避免两条链路行为不一致 |
| 完整内容落盘 | `app_settings` 键 `tool-out-<uuid>` | 单条上限 200 万字符；`get_all_setting_values()` 会跳过该前缀（不当设置回传） |
| 续读（后端） | `read_continuation(ref)` + `GET /chat/tool-output/{ref}` | 只接受 `tool-out-` 前缀，避免变成"任意设置读取"接口 |
| 事件字段 | `tool_end.total_chars / truncated / continuation_ref` | OPS-6 契约的一部分，每帧必带 |
| 前端入口 | 工具轨迹「查看完整输出」 | 走续读接口 + 弹窗展示 |

**未做的部分（有意延后）**：
- `read_file` 的 `offset/limit` 分页与「模型自主续读」：需要新增一个 `read_tool_output` 工具并进权限策略表，
  属于 EXT-3 工具生态的范畴；当前模型侧的做法是"缩小查询范围重试"（截断提示里已写明）。
- `SYSTEM_PROMPT` 里补续读说明：与上一条同批做，否则告诉模型一个不存在的工具反而更糟。

## 5. 风险与回滚

| 风险 | 缓解 |
| --- | --- |
| MCP 连接拖慢 Agent 启动 | 懒加载 + 连接失败只记日志不阻断 |
| 恶意 MCP server 越权 | 默认高危需确认 + 域名/命令白名单 |
| slash command 与 `\doc` 冲突 | 泛化时保留 `\doc` 别名，行为逐条对齐 |
| Office 引擎缺失导致 Office 文件读不出 | `office.enabled=off` 回落文本试读 + 降级标注；设置页可见引擎状态（见 4.11） |
