# 01 · Java 后端总体架构与集成方案

> 适用版本：`backend_java/` 骨架（2026-10）
> 目标：用 Spring Boot 3 + LangChain4j + LangGraph4j 复刻 Python 后端的能力，
> 并让 Electron 可以在 Java / Python 两套后端之间切换。

---

## 1. 目标与边界

### 1.1 目标

1. **接口兼容**：前端 `frontend/` 不改代码就能连上 Java 后端；
2. **能力对齐**：模型调用、工具调用、RAG、MCP、会话历史、人工确认、用量统计；
3. **可学习**：分层清晰、注释完整，适合逐模块阅读和仿写；
4. **可切换**：Electron 通过配置或命令选择 Java / Python，默认 Java；
5. **可打包**：Java 后端能打成可执行 jar，随 Electron 安装包一起分发。

### 1.2 暂不处理

- 登录、权限、多租户；
- 网络攻击面加固（按项目要求“安全性暂不考虑”，但代码仍不做危险默认值）；
- 分布式部署、集群、远程数据库；
- 生产级监控告警。

### 1.3 兼容原则

| 维度 | 约定 |
| --- | --- |
| 端口 | 默认 `8000`，可通过 `APP_PORT` / `--server.port` 覆盖 |
| 接口前缀 | `/api`（`server.servlet.context-path`） |
| 健康检查 | `GET /api/health`，返回 `{code:0,message:"ok",data:{...}}` |
| 统一外壳 | 多数接口返回 `ApiResponse<T>` |
| 裸 JSON | `/chat/*` 辅助接口、`/skills/*`、`/mcp/*`、`/memory/*`、`/trace/*`、`/diagnostic/summary`、`/commands` 保持 Python 的裸 JSON 形状 |
| SSE | `text/event-stream`；事件名与 Python 侧一致（`thinking`、`token`、`tool_start`、`tool_end`、`confirm_required`、`done`、`error`、`stopped` 等） |
| 字段命名 | JSON 一律 `snake_case`；Java 内部用驼峰 + `@JsonProperty` 映射 |
| 时间 | ISO-8601 字符串；与前端约定一致 |

## 2. 技术选型

| 层 | 选型 | 版本 | 说明 |
| --- | --- | --- | --- |
| JDK | Eclipse Temurin / Corretto | 17+ | LangGraph4j 的编译目标就是 17 |
| 构建 | Maven + Maven Wrapper | 3.9.11 | 仓库自带 `mvnw`，不要求全局 Maven |
| Web | Spring Boot Web (MVC) | 3.5.16 | 内嵌 Tomcat，`SseEmitter` 支持流式 |
| 校验 | Jakarta Validation | Boot 管理 | `@NotBlank` / `@Min` / `@Max` |
| 数据库 | SQLite JDBC | 3.53.4.0 | 单文件、零部署，适合桌面应用 |
| 模型 / 工具 / RAG / MCP | LangChain4j | 1.22.0 | 核心与各供应商模块 |
| 图运行时 | LangGraph4j | 1.9.6 | 对应 Python 的 LangGraph |
| 检查点 | `langgraph4j-sqlite-saver` | 1.9.6 | 对应 `AsyncSqliteSaver` |
| 序列化 | Jackson | Boot 管理 | 与 Spring MVC 共用 |
| 测试 | JUnit 5 + MockMvc | Boot 管理 | 健康检查集成测试已提供 |

### 2.1 为什么不用 Spring AI 2.0

- Spring AI 2.0 的核心是 `ChatClient` + Advisor，**没有 LangGraph 等价的图运行时、
  检查点、中断/恢复**；而本项目 Python 侧大量依赖 `LangGraph`。
- Spring AI 2.0 要求 Spring Boot 4.1 / Spring Framework 7 / JDK 21 / Jackson 3，
  对学习项目和现有生态都是额外迁移成本。
- 如果以后要做企业级 MCP/可观测性，可以再评估 Spring AI Alibaba（它补了 Graph/HITL），
  但当前目标是“仿写 LangGraph 项目”，LangChain4j + LangGraph4j 的映射最直接。

### 2.2 为什么不用 FAISS（重要）
-- 可以尝试使用 sqlite-vec

Maven Central 上**没有** `dev.langchain4j:langchain4j-faiss` 这个构件。
Python 侧可以用 `faiss-cpu`，Java 侧第一版改用：

- `InMemoryEmbeddingStore`（LangChain4j 自带，适合学习与单机小数据）；
- 或自己实现 `EmbeddingStore`（把向量存 SQLite/BLOB，内存里做余弦相似度）；
- 或换 Milvus / Elasticsearch / Qdrant 等有官方集成的向量库。

详见 [03-LangChain4j与LangGraph4j集成指南](./03-LangChain4j与LangGraph4j集成指南.md) 的 RAG 章节。

### 4.1 分层规则

1. **Controller 不写业务**：只做参数校验、协议适配、调用 Service。
2. **Controller 不直接依赖 LangChain4j / LangGraph4j**：所有模型与图操作都在 Service/Agent 层。
3. **Service 接口面向领域**，不要暴露 `ChatModel`、`CompiledGraph` 等第三方类型给 Controller。
4. **AgentRuntime 只产生事件**，不关心 SSE；由 `ChatService` 把事件写成 SSE。
5. **工具是原子能力**：一个工具只做一件事；场景组合交给系统提示词或图。
6. **DTO 用 record**：只承载数据，不写业务逻辑；snake_case 用 `@JsonProperty`。
7. **依赖方向单向**：`controller → service → dto / common / util`；
   `config` 只被框架与启动类使用，谁都不许反向依赖 `controller`。

## 5. 关键请求流

### 5.1 健康检查（已实现）

```text
Electron startBackend()
  → GET http://127.0.0.1:8000/api/health
  → HealthController.health()
  → HealthService.getHealth()
  → ApiResponse.ok(HealthData)
  → Electron 判断 body.code === 0
```

`HealthData` 同时返回 `runtime` 与 `runtime_version`（Java），
并保留 `python_version` 字段（值为 `N/A`）兼容旧前端。

### 5.2 流式对话（待实现）

```text
POST /api/chat/stream
  → ChatController.stream(ChatRequest)
  → ChatService.stream(request)
      ├─ 校验/创建 sessionId（同时作为 LangGraph4j threadId）
      ├─ 组装系统提示词（固定规则 + 当前技能清单）
      ├─ 从 ToolRegistry 取工具（主 Agent / 子 Agent 作用域）
      ├─ AgentRuntime.run(turn, sink)
      │    ├─ agent 节点：StreamingChatModel.chat(...)
      │    ├─ 工具节点：执行 AgentTool，把结果写回 state
      │    └─ 条件边：还有工具调用 → 回到 agent；否则 → END
      └─ sink 把事件写入 SseEmitter
  → 响应 text/event-stream
```

事件到 SSE 帧的映射：

```text
event: token
data: {"text":"你"}

event: tool_start
data: {"name":"read_file","input":{...}}

event: done
data: {"session_id":"...","answer":"...","usage":{...}}
```

### 5.3 人工确认 / 恢复（待实现）

Python 侧的核心机制是 `interrupt()` + `Command(resume=...)`；
LangGraph4j 的对应机制是 **节点级中断 + 检查点 + `GraphInput.resume`**：

```text
1. 图编译时：CompileConfig.builder()
       .checkpointSaver(sqliteSaver)
       .interruptBefore("confirm")
       .build();

2. 执行到 confirm 节点前：图暂停，SQLiteSaver 写入检查点；
   后端发 confirm_required 事件（含 interrupt_id 与待确认动作）。

3. 前端 POST /api/chat/resume
       {session_id, interrupt_id, approved}

4. ChatService.resume(...)
       graph.stream(GraphInput.resume(Map.of("approved", true)),
                    RunnableConfig.builder().threadId(sessionId).build());

5. 图从 confirm 节点继续；approved=false 时走拒绝分支。
```

**注意**：LangGraph4j 的中断发生在节点边界，不是在工具函数内部。
Python 侧 `tool_utils.ask_user` 在工具内部 `interrupt()` 的写法，Java 侧需要：

- 把“需要确认的工具调用”抽成一个独立节点，在节点前后中断；或
- 走应用层 `pending_action` 表：工具返回 `confirm_required`，用户确认后由
  `ChatService` 直接执行，不经过图（对应 Python 的 `_run_native_resume`）。

### 5.4 会话历史

```text
GET /api/chat/sessions
  → ChatService.listSessions()
  → SELECT ... FROM chat_session ORDER BY pinned DESC, updated_at DESC

GET /api/chat/history/sessions/{id}
  → ChatService.history()
  → SELECT ... FROM chat_message WHERE session_id=? ORDER BY id ASC
```

检查点表由 `SQLiteSaver` 自己创建，与业务表同库不冲突。
不要把检查点表当业务历史表使用：前者是图状态，后者是展示用消息。

## 6. API 契约

### 6.1 统一响应

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

- `code=0` 成功；非 0 为业务失败；
- HTTP 状态码：业务失败通常仍返回 200；参数错误 400；未实现 501；未知异常 500。
- 未匹配路径返回 404（`GlobalExceptionHandler` 已处理）。

### 6.2 裸 JSON 接口

以下接口为了兼容前端现有 `chatJson()` / 直接 `fetch`，**不套 ApiResponse**：

| 路径 | 形状 |
| --- | --- |
| `/chat/sessions` | `{"sessions":[...]}` |
| `/chat/history/sessions/{id}` | `{"session_id":"...","messages":[...]}` |
| `/chat/sessions/{id}` | `SessionInfo` |
| `/chat/stop` | `{"stopped":bool,"session_id":"..."}` |
| `/chat/{id}/steer` | `{"session_id","steer_id","content","queued","pending"}` |
| `/chat/{id}/tool-cancel` | `{"session_id","cancelled","tool"}` |
| `/chat/history/sessions/{id}/export` | `ExportedSession` |
| `/chat/history/sessions/{id}/usage` | `SessionUsage` |
| `/chat/history/sessions/{id}` DELETE | `{"deleted":bool,"session_id":"..."}` |
| `/chat/tool-output/{ref}` | `ToolOutputPayload` |
| `/chat/events` | 事件协议字典 |
| `/skills`、`/skills/reload`、`/skills/{name}` | 技能快照/详情 |
| `/mcp/servers`、`/mcp/reload`、`/mcp/test` | MCP 快照/试连结果 |
| `/memory/*`（除 SSE） | 记忆列表/统计/检索结果 |
| `/trace/*` | 轨迹列表/事件 |
| `/diagnostic/summary` | 诊断概要 |
| `/commands` | `{"commands":[...]}` |

### 6.3 SSE 事件协议

建议事件名与 Python 侧保持一致：

| 事件 | 负载 | 说明 |
| --- | --- | --- |
| `thinking` | `{session_id, stage}` | 阶段提示，如“正在理解问题” |
| `token` | `{text}` | 模型增量文本 |
| `tool_start` | `{name, input, tool_call_id}` | 工具开始 |
| `tool_end` | `{name, output, ok, elapsed, continuation_ref?}` | 工具结束 |
| `confirm_required` | `{session_id, interrupt_id, action, can_remember, preview}` | 等待用户确认 |
| `done` | `{session_id, answer, tools, usage, elapsed, files?}` | 本轮正常结束 |
| `stopped` | `{session_id, answer, reason}` | 用户终止 |
| `error` | `{message, type?}` | 出错 |

实现时建议先定义枚举/常量，避免事件名拼错。

## 8. 模型接入方案

### 8.1 三层结构

```text
LlmProviderRegistry（数据）
  ├─ 内置供应商：deepseek / openai / anthropic / google / ollama
  └─ 后续：从设置库读取 custom-* 自定义端点
        ↓
LlmModelFactory（扩展点）
  ├─ OpenAiCompatibleLlmModelFactory（已实现）
  ├─ AnthropicLlmModelFactory（TODO）
  ├─ GoogleAiGeminiLlmModelFactory（TODO）
  └─ OllamaLlmModelFactory（TODO）
        ↓
LlmModelFactoryRouter（路由）
  → ChatModel / StreamingChatModel
```

### 8.2 运行时切换

Python 侧通过 `llm/state.py` 缓存图，设置变更时 `invalidate()`。
Java 侧建议：

- `ChatService` 每次请求开始时读取当前 `llm.provider` / `llm.model`；
- 用 `(provider, model, baseUrl, temperature, maxTokens)` 做缓存键；
- 设置保存后清空缓存；
- 不要在多处 new 模型，统一走 `LlmService.createChatModel(...)`。

### 8.3 密钥

当前骨架的 `ProbeRequest` 允许传 `api_key`，只用于本地连通性测试。
正式实现时应：

- 把密钥存 Windows Credential Manager（JNA）或 Java KeyStore；
- `LlmModelSpec.apiKey` 只在内存中传递；
- 日志与异常信息里不要打印 Key。

### 8.4 baseUrl 注意事项

LangChain4j 的 OpenAI 客户端会在 `baseUrl` 后拼接 `/chat/completions`：

- OpenAI：`https://api.openai.com/v1`
- DeepSeek：`https://api.deepseek.com/v1`
- 自定义中转站：按供应商文档给到 `/v1` 这一级

如果填成 `https://api.deepseek.com/v1/`（末尾多斜杠），可能出现 `//chat/completions`，
需要在实现时统一去掉末尾斜杠。

## 9. Agent 集成方案

### 9.1 图的节点划分

推荐先把图控制在 4 类节点：

| 节点 | 职责 |
| --- | --- |
| `agent` | 调用 `StreamingChatModel`，产出文本或工具调用请求 |
| `tools` | 执行 `AgentTool`，把结果写回消息列表 |
| `confirm` | 写盘/执行类工具的前置确认节点（触发中断） |
| `summarize` | 上下文压缩/收尾（可选） |

### 9.2 状态

- 用 `MessagesState<ChatMessage>` 存消息列表；
- 用 `AgentState` 的额外键存 `session_id`、`pending_interrupt`、`approved` 等；
- 检查点序列化用 `LC4jJacksonStateSerializer`（已在 `AgentGraphConfig` 装配）。

### 9.3 工具策略

- `ToolPolicy.READ_ONLY`：直接执行；
- `WRITE` / `EXECUTE` / `DATABASE`：先进入 `confirm` 节点；
- 子 Agent 只用 `listForScope(true)`，默认只读；
- 启动时自检：每个工具都必须有策略，否则拒绝启动（对应 Python 的 `verify_all_tools_registered`）。

### 9.4 终止

- `CompiledGraph` 没有“外部强杀”接口；建议：
  - 会话级 `AtomicBoolean cancelled`；
  - 工具节点与 agent 节点每次循环检查；
  - 已发出的流由 `ChatService` 发 `stopped` 事件并关闭 `SseEmitter`。

## 10. RAG 方案

### 10.1 管道

```text
文件/文本
  → DocumentParser（PDF/DOCX/TXT/Markdown）
  → DocumentSplitter（按 500 字、重叠 80 字）
  → EmbeddingModel（供应商 embedding 或本地 ONNX）
  → EmbeddingStore（InMemory / 自定义 SQLite）
  → EmbeddingStoreContentRetriever（topK / 阈值 / 过滤）
  → 拼进提示词
```

### 10.2 第一版建议

- 用 `InMemoryEmbeddingStore`，启动时从 `rag_chunk` 表重建；
- 向量以 JSON 数组字符串存 SQLite（教学够用）；数据量大时改 BLOB；
- 检索分值用余弦相似度；
- 文档解析依赖按需添加：
  - PDF：`org.apache.pdfbox:pdfbox`
  - DOCX：`org.apache.poi:poi-ooxml`
  - 通用：`org.apache.tika:tika-core` + `tika-parsers-standard-package`

### 10.3 与 Python 的差异

- 没有 FAISS；不要照搬 `faiss_index/` 文件格式；
- `SimpleVectorStore` / `InMemoryEmbeddingStore` 不提供 FAISS 的 IVF/HNSW 性能；
- 如果必须用 FAISS，需要自己写 JNI 适配器，或在 Python 侧保留 RAG 服务。

---

## 11. MCP 方案

- 用 LangChain4j `DefaultMcpClient` 建立连接；
- 传输方式：`stdio` / `sse` / `streamable_http`；
- 用 `McpToolProvider` 把外部工具转成 LangChain4j Tool；
- 工具名加 server 前缀，避免冲突；
- 配置变更后 `reload()`，并清空 Agent 缓存；
- 单个 server 连接失败只影响它自己，不能拖垮内置工具。

## 14. 打包方案

### 14.1 构建 jar

```bash
pnpm run build:backend:java
# = node scripts/run-maven.mjs -DskipTests package
#   + node scripts/sync-java-backend.mjs
```

产物：

- `backend_java/target/backend-java.jar`（约 42MB，含依赖）
- `electron/resources/backend/backend-java.jar`

### 14.2 随包 JRE

Electron 安装包不能假设用户装了 JDK 17。可选方案：

1. 用 `jlink` 生成精简 JRE，放到 `electron/resources/backend/jre/`；
2. 用 `jpackage` 生成自带运行时的应用镜像；
3. 首版先要求用户安装 JDK 17，并在安装说明里写清楚。

`electron-builder.yml` 的 `extraResources` 会把整个 `resources/backend/` 打进安装包，
所以只要把 `jre/` 放进去，主进程就能通过 `resolveJavaExecutable()` 找到它。

### 14.3 启动参数

```bash
java -Dfile.encoding=UTF-8 -jar backend-java.jar --server.port=8000
```

`-Dfile.encoding=UTF-8` 用于避免 Windows 控制台中文日志乱码。

## 15. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 机器只有 JDK 8 | 启动前检查 `JAVA_HOME`；文档与 Electron 日志明确提示 |
| Maven 首次下载慢 | Maven Wrapper + `startupTimeoutMs=180000`；可先跑 `pnpm run setup:java` |
| LangGraph4j API 演进 | 固定 1.9.6；升级前先跑测试 |
| 没有 FAISS | 第一版用 `InMemoryEmbeddingStore`，或自定义 `EmbeddingStore` |
| 中断粒度是节点级 | 用 confirm 节点或应用层 pending_action 表 |
| SQLite 写锁 | Hikari 连接池固定 1 条 |
| 控制台中文乱码 | `-Dfile.encoding=UTF-8` |
| 端口被占用 | `APP_PORT` / `--port` 覆盖；Electron 会先探活复用 |

## 16. 架构决策记录（ADR 摘要）

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 语言/框架 | Java 17 + Spring Boot 3.5 | 稳定、资料多、与 JDK 17 对齐 |
| AI 框架 | LangChain4j 1.22 | 概念与 Python LangChain 最接近 |
| 图运行时 | LangGraph4j 1.9.6 | 唯一成熟的 Java LangGraph 等价物 |
| 检查点 | SQLiteSaver | 与桌面单机场景匹配 |
| 向量库 | InMemoryEmbeddingStore（第一版） | 无官方 FAISS 构件 |
| Web 流式 | Spring MVC `SseEmitter` | 比 WebFlux 简单，够用 |
| 默认后端 | Java | 用户要求；Electron 可切 Python |
| 未实现接口 | 返回 501 | 应用可启动，学习者逐块实现 |
