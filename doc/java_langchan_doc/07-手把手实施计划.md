## 0. 你现在到底卡在哪（三句话）

**第一句**：模型是通的，工具是通的，权限也是通的。你唯一没做的是「**说话**」——后端和前端之间那套「带事件类型的数据」你还没说对。

**第二句**：前端只认 15 个事件名（`token`、`tool_start`、`done`…）。你现在发的是 `delta`，前端 `switch` 里根本没有 `delta` 这个分支，所以它**老老实实把事件丢了**。这不是 bug，这是「协议对不上」。

**第三句**：所有难的地方，本质是一件事——**「一次对话」的执行线程，和「一个 HTTP 流」不是一对一绑死的**。用户在弹窗上点「同意」的时候，前端的流已经关了，后端那条执行线程还在等。你要做的就是**给这条线程一个可以换插头的插座**。

先把这三句记住，后面所有代码都是在兑现这三句话。

## 3. 重头戏：事件到底怎么做

这一章是全文核心。看完你会明白：**事件不是一个 `switch`，是四层东西拼起来的**。

### 3.1 先看清现状：你为什么一条都发不出去

`backend_java/src/main/java/com/example/backendjava/service/impl/ChatServiceImpl.java:211-224` 现在是这样：

```java
// 现状：事件名写死成 "delta"，赋值方式是把 Map 塞进 data
.onPartialResponse(partial -> {
    try {
        emitter.send(SseEmitter.event()
                .name("delta")                                  // ← 前端 switch 没有这个分支
                .data(Map.of("text", partial), MediaType.APPLICATION_JSON));
    } catch (IOException e) { ... }
})
```

对比前端 `frontend/src/services/chat.ts` 的 `dispatchChatEvent`：

```ts
switch (event) {
  case 'token': return handlers.onToken?.(data as TokenEvent)
  case 'tool_start': return handlers.onToolStart?.(data as ToolStartEvent)
  // ... 没有 'delta'
}
```

所以现在的情况是：**后端喊「delta」，前端只认「token」，两个人各说各话**。

而且不止名字不对。`token` 事件的载荷是 `{text}`，你用 `Map.of("text", partial)` 恰好是对的——但一旦你要发 `tool_end`（要 `total_chars`/`truncated`/`continuation_ref`），`Map.of` 就会出现三个问题：

1. 键名靠手写字符串，写成 `totalChars` 前端就收不到（前端只认 snake_case）；
2. `Map.of` **不允许 null 值**，`continuation_ref` 明明是「没截断时没有」；
3. 编译期完全不知道这个 Map 里该有什么，改错一个键名要跑起来才发现。

这就是为什么下面要搞「枚举 + 载荷 + 信封」三层。

### 3.2 先说一个致命的硬约束（它决定了整个架构）

打开 `frontend/src/stores/chat.ts:1133-1164`，前端是这么干活的：

```ts
// 第 1133 行：发起一轮对话，等这条 SSE 流结束
await chat_stream(payload, handlers, { signal })

// 第 1137 行起：如果收到过 confirm_required，就循环开新流
while (pendingAsks.length) {
  const ask = pendingAsks.shift()
  // 用户点了「同意/拒绝」之后：
  await chat_resume({ session_id, interrupt_id, approved, remember }, handlers, { signal })
}
```

**翻译成人话**：

```
前端：发一轮对话 ────────────────► 后端
                                    │
   ◄──── event: token × N ──────────┤
   ◄──── event: confirm_required ───┤   ← 用户要点头了
   ◄──── 流关闭（这次 await 返回）───┘
        ↓
   弹窗，等用户点
        ↓
前端：POST /chat/resume ──────────► 后端   ← 注意：这是一条**全新的 SSE 流**
                                    │
   ◄──── event: tool_end ───────────┤   ← 但用户看起来是「接着上面继续」
   ◄──── event: token × N ──────────┤
   ◄──── event: done ───────────────┤
   ◄──── 流关闭 ─────────────────────┘
```

**这个约束非常狠**：它意味着你**不能**在原来的 `SseEmitter` 上傻等用户点确认——那条流必须当场关闭，否则前端 `await chat_stream(...)` 永远不返回，弹窗永远不出来。

但它也意味着：`/chat/resume` 打开的**新流**必须能接上**旧线程**的后续输出。

怎么做到？**把「往哪里写事件」做成一个可以随时换绑的对象**。这就是 3.6 节的 `ChatSessionBus`。

### 3.3 三层设计：枚举 → 载荷 → 信封

```
① ChatEventType（枚举）        —— 事件名的唯一来源，杜绝 "delta" 这种手滑
        ↓
② ChatEventPayloads（record）  —— 每种事件一个强类型载荷，字段用 @JsonProperty 保证 snake_case
        ↓
③ AgentEvent（已有 record）     —— 信封：{type, data}，data 是 Map
        ↓
④ AgentEventSink（已有接口）    —— 出口：SseAgentEventSink / TraceEventSink / CompositeAgentEventSink
```

**为什么中间还要转成 Map？** 因为 `service/AgentEventSink.java` 和 `dto/AgentDtos.AgentEvent` 你已经写好了，`emit(AgentEvent)` 就是这个形状。改接口的代价大，转一次 Map 的代价小。而且 `AgentEvent.data` 是 `Map<String,Object>`，塞什么都能发，未来加事件不用改接口。

**为什么载荷要用 record 而不是直接 `Map.of`？** 三个原因，逐个对应上面说的三个毛病：
- 字段名写在 record 组件上 + `@JsonProperty`，**只写一次**，且编译期检查；
- record 转 Map 时 null 会被保留（我们要的），不会像 `Map.of` 那样炸；
- 读代码的人打开 `ChatEventPayloads.java` 就看到了**完整协议**，不用去翻 Python。

### 3.4 新建文件 ①：`ChatEventType.java`

**路径**：`backend_java/src/main/java/com/example/backendjava/chat/event/ChatEventType.java`

```java
// 模块说明：SSE 事件名枚举。全后端「事件名字符串」的唯一来源。
//
// 为什么要有这个枚举：事件名是前后端契约（见 frontend/src/services/chat.ts 的 dispatchChatEvent）。
// 如果散落在各处写 "token" / "delta" / "done" 这样的字面量，拼错一个字母前端就静默丢事件，
// 而且编译期毫无提示 —— 本项目已经踩过这个坑（曾经发 "delta"，前端只认 "token"）。
// 约定：新增事件必须先在这里登记，再在 ChatEventPayloads 里加载荷。
package com.example.backendjava.chat.event;

/**
 * 对话 SSE 事件类型。
 *
 * <p>枚举常量名 = 前端 switch 的分支名，wireName 用于发送（两者保持一致，
 * 保留 wireName 是为了将来需要改线上名字时只改一处）。</p>
 */
public enum ChatEventType {

    /** 思考/准备阶段提示：让用户知道后端在做事，而不是卡住了。 */
    THINKING("thinking"),

    /** 模型增量文本：一段一段的正文。 */
    TOKEN("token"),

    /** 工具开始执行。 */
    TOOL_START("tool_start"),

    /** 工具执行结束（含截断信息，前端据此显示「展开全文」）。 */
    TOOL_END("tool_end"),

    /** 需要用户确认：发完这条事件后，当前 SSE 流必须立刻关闭。 */
    CONFIRM_REQUIRED("confirm_required"),

    /** 用户主动停止。 */
    STOPPED("stopped"),

    /** 一轮正常结束：携带答案与统计。 */
    DONE("done"),

    /** 出错：message 面向用户，detail 只在 debug 模式带。 */
    ERROR("error"),

    /** 用户的插话已被注入到工具结果中。 */
    STEER_INJECTED("steer_injected"),

    /** 预算（token/费用/时长）超限。 */
    BUDGET_EXCEEDED("budget_exceeded"),

    /** 拆解出的任务计划（`\doc` 与计划模式使用）。 */
    PLAN("plan"),

    /** 计划变更。 */
    PLAN_UPDATE("plan_update"),

    /** 子任务开始。 */
    TASK_START("task_start"),

    /** 子任务结束。 */
    TASK_END("task_end");

    /** 线上发送用的事件名，必须与前端 switch 的分支字面量一致。 */
    private final String wireName;

    /**
     * 构造事件类型。
     *
     * @param wireName 线上发送用的事件名
     */
    ChatEventType(String wireName) {
        this.wireName = wireName;
    }

    /**
     * 读取线上事件名。
     *
     * @return 形如 token / tool_start 的字符串
     */
    public String wireName() {
        return wireName;
    }
```

### 3.7 新建文件 ④：`SseAgentEventSink.java`（写出去的那只手）

**路径**：`backend_java/src/main/java/com/example/backendjava/chat/event/SseAgentEventSink.java`

这个类是**唯一碰 `SseEmitter` 的地方**。它要实现 `AgentEventSink`（你已经写好的接口）。

```java
// 模块说明：把 AgentEvent 写成 SSE 帧的那个「水龙头」。
//
// 为什么单独成类：SseEmitter 只能在 Web 线程里安全写，业务代码（工具线程、模型回调线程）
// 不应该知道 SSE 长什么样。这里做一层隔离：业务只管 emit，格式化与线程安全都在这。
// 帧格式必须与 Python 一致：event: xxx\ndata: {...}\n\n（前端 sse() 按这个解析）。
package com.example.backendjava.chat.event;

// 标准库：IOException 来自 send 失败（客户端断开）
import java.io.IOException;

// Spring：MediaType 指定按 JSON 序列化，StringHttpMessageConverter 会把 String 当文本发出去
import org.springframework.http.MediaType;
// Spring：SseEmitter 是服务端 SSE 的出口对象
import org.springframework.web.servlet.mvc.method.annotation.SseEmitter;

// 已有的事件接口与信封类型
import com.example.backendjava.dto.AgentDtos;
import com.example.backendjava.service.AgentEventSink;

/**
 * SSE 事件出口：一个实例对应「一条 HTTP 流」。
 *
 * <p>线程安全：{@code send} 用对象锁串行化。SseEmitter 内部会做缓冲，
 * 并发写同一个 emitter 可能丢帧或抛 IllegalStateException，加锁最省心。</p>
 */
public class SseAgentEventSink implements AgentEventSink {

    /** 当前流对应的 emitter。 */
    private final SseEmitter emitter;

    /** 串行化 send 的锁；不要用 emitter 自己当锁，避免和 Spring 内部锁交叉。 */
    private final Object lock = new Object();

    /** 是否已关闭（客户端断开或我们主动 complete 之后置 true），关闭后一切事件直接丢弃。 */
    private volatile boolean closed;

    /**
     * 构造出口。
     *
     * @param emitter 本流对应的 SseEmitter
     */
    public SseAgentEventSink(SseEmitter emitter) {
        this.emitter = emitter;
    }

    /**
     * 发送一条事件。
     *
     * @param event 事件信封；type 作为 SSE 的 event 名，data 作为 JSON 负载
     */
    @Override
    public void emit(AgentDtos.AgentEvent event) {
        // 已关闭（客户端走了）就没必要再写，直接丢，避免无谓的异常刷日志
        if (closed) {
            return;
        }
        synchronized (lock) {
            // 双重检查：等锁期间可能已经被别的线程关掉了
            if (closed) {
                return;
            }
            try {
                // 注意：data 传 Map + APPLICATION_JSON，Spring 会用 Jackson 序列化成 JSON 对象。
                // 千万不要「自己序列化成字符串再传 APPLICATION_JSON」，那样会被再包一层引号。
                emitter.send(SseEmitter.event()
                        .name(event.type())
                        .data(event.data(), MediaType.APPLICATION_JSON));
            } catch (IOException | IllegalStateException ex) {
                // 客户端断开或容器已回收：标记关闭，后续静默丢弃（这不是业务错误，不打 ERROR）
                closed = true;
            }
        }
    }

    /**
     * 正常结束这条流（前端会看到流关闭）。
     *
     * <p>幂等：重复调用不会报错。</p>
     */
    public void close() {
        synchronized (lock) {
            if (closed) {
                return;
            }
            closed = true;
            try {
                emitter.complete();
            } catch (RuntimeException ex) {
                // 已经是完成/超时状态：忽略，close 的语义就是「尽量关掉」
            }
        }
    }

    /**
     * 异常结束这条流。
     *
     * @param error 导致流结束的异常
     */
    public void closeWithError(Throwable error) {
        synchronized (lock) {
            if (closed) {
                return;
            }
            closed = true;
            try {
                emitter.completeWithError(error);
            } catch (RuntimeException ex) {
                // 同上：状态已结束就忽略
            }
        }
    }

    /**
     * 查询这条流是否已结束。
     *
     * @return true 表示已关闭
     */
    public boolean isClosed() {
        return closed;
    }
}
```

**这一层做完，你就有「怎么发」的能力了。** 但还差「发到哪」——因为要换流。

### 3.8 新建文件 ⑤：`ChatSessionBus.java`（关键！可换插头的插座）

**路径**：`backend_java/src/main/java/com/example/backendjava/chat/runtime/ChatSessionBus.java`

这是全文**最重要的一个类**。它持有「每个会话当前该往哪条流写」以及「当前在等哪个确认」。
把它理解成一个**插线板**：

- `/chat/stream` 到来 → 把新插头插上（`bind`）；
- 要确认了 → 把插头拔掉、关掉旧流（`detach`），但**执行线程继续跑**，只是暂时没地方输出；
- `/chat/resume` 到来 → 插上新插头（`bind`），并踢醒等待中的线程（`answer`）；
- 线程醒来，继续往**新插头**写。

```java
// 模块说明：会话级事件总线 —— 「一次对话」和「一条 HTTP 流」之间的可换绑插座。
//
// 为什么必须有它：前端契约要求 confirm_required 之后当前 SSE 流立刻结束，
// 用户点完同意再用 /chat/resume 打开一条「新流」继续看后续输出（见 frontend/src/stores/chat.ts:1133-1164）。
// 也就是说：执行线程（跑模型、跑工具的那个）不能和某一条具体的 SseEmitter 绑死。
// 本类用 sessionId → Turn 的映射，让执行线程只管「往总线写」，总线决定「现在写给谁」。
//
// 代价（写在这里免得上线踩）：
//   1) 一个待确认的轮次会占住一个线程（阻塞在 future.get 上）；
//   2) 进程重启后待确认的轮次会丢（没有落盘，Python 用 LangGraph checkpoint 解决，见第 7 章）。
package com.example.backendjava.chat.runtime;

// 标准库：并发容器与原子类型
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.TimeUnit;
// 标准库：UUID 生成中断 id
import java.util.UUID;

// 已有的事件信封、工厂与 SSE 出口
import com.example.backendjava.chat.event.ChatEvents;
import com.example.backendjava.chat.event.CompositeAgentEventSink;
import com.example.backendjava.chat.event.SseAgentEventSink;
import com.example.backendjava.dto.AgentDtos;
// 确认结果类型：直接复用工具层的 record，避免两套
import com.example.backendjava.tools.ToolApprovalGateway.ApprovalRequest;
import com.example.backendjava.tools.ToolApprovalGateway.ApprovalResult;
// 预算请求类型
import com.example.backendjava.tools.ToolApprovalGateway.BudgetRequest;

// 日志门面：后台出口失败时记一笔，不影响主流程
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
// Spring：单例
import org.springframework.stereotype.Component;

/**
 * 会话级事件总线。
 *
 * <p>三个职责：</p>
 * <ol>
 *   <li>记住每个会话「当前该往哪条 SSE 流写」；</li>
 *   <li>在需要确认时把流摘下来（detach）并挂起一个 Future；</li>
 *   <li>在 /chat/resume 时换上新流并兑现 Future，让挂起的工具线程继续跑。</li>
 * </ol>
 */
@Component
public class ChatSessionBus {

    /** 等待用户点确认的最长时间；超时按「拒绝」处理，避免线程永远挂着。 */
    private static final long ASK_TIMEOUT_MINUTES = 10;

    /** 日志：后台出口失败、换流失败等非致命问题记这里。 */
    private static final Logger log = LoggerFactory.getLogger(ChatSessionBus.class);

    /** 会话 id → 本轮运行状态。 */
    private final Map<String, Turn> turns = new ConcurrentHashMap<>();

    /** 会话 id → 本轮记事本；与 turns 同生命周期。 */
    private final Map<String, TurnRecorder> recorders = new ConcurrentHashMap<>();

    /** 事件工厂：总线自己也发事件（confirm_required / budget_exceeded）。 */
    private final ChatEvents events;

    /** 与流无关的出口链（落库/审计/日志）；见 3.9.3 里那个 backgroundEventSink Bean。 */
    private final CompositeAgentEventSink background;

    /**
     * 构造总线。
     *
     * <p>参数类型写具体的 CompositeAgentEventSink 而不是 AgentEventSink：
     * 因为容器里还有一个 TraceEventSink 也是 AgentEventSink，写接口会报「找到两个 Bean」。</p>
     *
     * @param events     事件工厂
     * @param background 与流无关的出口链（落库等），不能为 null
     */
    public ChatSessionBus(ChatEvents events, CompositeAgentEventSink background) {
        this.events = events;
        this.background = background;
    }

    /**
     * 一轮对话的运行时状态。
     *
     * <p>用普通内部类而不是 record：字段需要就地修改（换 sink、改停止标记）。</p>
     */
    public static final class Turn {

        /** 会话 id。 */
        private final String sessionId;

        /** 当前绑定的 SSE 出口；为 null 表示「现在没有流在看」，事件直接丢弃。 */
        private volatile SseAgentEventSink sink;

        /** 是否已请求停止（前端点了「停止」）。 */
        private volatile boolean stopRequested;

        /** 当前唯一一个待确认的询问；没有则为 null。 */
        private volatile PendingAsk pending;

        /** 本次询问的中断 id，与 confirm_required 事件里的 interrupt_id 一致。 */
        private volatile String interruptId;

        /**
         * 构造一轮状态。
         *
         * @param sessionId 会话 id
         */
        Turn(String sessionId) {
            this.sessionId = sessionId;
        }

        /**
         * 读取会话 id。
         *
         * @return 会话 id
         */
        public String sessionId() {
            return sessionId;
        }

        /**
         * 查询是否已被请求停止。
         *
         * @return true 表示前端点了停止
         */
        public boolean stopRequested() {
            return stopRequested;
        }
    }

    /**
     * 一个待确认的询问。
     *
     * @param interruptId 中断 id
     * @param future      等待用户决定的结果
     * @param event       当时发出的 confirm_required 事件；换流后要补发，否则新流看不到弹窗
     */
    private record PendingAsk(String interruptId,
                              java.util.concurrent.CompletableFuture<ApprovalResult> future,
                              AgentDtos.AgentEvent event) {
    }

    /**
     * 开启（或复用）一轮对话。
     *
     * @param sessionId 会话 id
     * @return 本轮状态
     */
    public Turn open(String sessionId) {
        return turns.computeIfAbsent(sessionId, Turn::new);
    }

    /**
     * 取（或创建）本轮的记事本。
     *
     * @param sessionId 会话 id
     * @return 本轮记录器
     */
    public TurnRecorder recorderOf(String sessionId) {
        open(sessionId);
        return recorders.computeIfAbsent(sessionId, key -> new TurnRecorder());
    }

    /**
     * 静默摘流：用于 emitter 的 onCompletion / onTimeout / onError 回调。
     *
     * <p>与 {@link #detach(String)} 的区别：这里不调用 emitter.complete()
     * （因为是容器/前端先关的，再 complete 一次会抛异常），只把绑定清掉。</p>
     *
     * @param sessionId 会话 id
     */
    public void detachQuietly(String sessionId) {
        Turn turn = turns.get(sessionId);
        if (turn != null) {
            turn.sink = null;
        }
    }

    /**
     * 把一条新的 SSE 流插到会话上。
     *
     * @param sessionId 会话 id
     * @param sink      新流的出口
     */
    public void bind(String sessionId, SseAgentEventSink sink) {
        open(sessionId).sink = sink;
    }

    /**
     * 把当前 SSE 流摘下来并关闭（不结束执行线程）。
     *
     * @param sessionId 会话 id
     */
    public void detach(String sessionId) {
        Turn turn = turns.get(sessionId);
        if (turn == null) {
            return;
        }
        SseAgentEventSink current = turn.sink;
        turn.sink = null;
        if (current != null) {
            // 关闭后前端那次 await 才会返回，弹窗才出得来
            current.close();
        }
    }

    /**
     * 往会话当前绑定的流写一条事件，同时扇出给与流无关的出口链。
     *
     * <p>没有流在听时 SSE 这一路静默丢弃——这是「用户关掉页面」的正常情况，不是错误。
     * 但落库那一路照样要写，否则轨迹页会缺记录。</p>
     *
     * @param sessionId 会话 id
     * @param event     事件
     */
    public void emit(String sessionId, AgentDtos.AgentEvent event) {
        // 1) 先扇出给后台出口（落库/审计）：它们的异常绝不能影响 SSE
        try {
            background.emit(event);
        } catch (RuntimeException ex) {
            // 轨迹写库失败只是少一条记录，不该让整轮对话挂掉
            log.warn("后台事件出口失败 type={}", event.type(), ex);
        }

        // 2) 再写当前绑定的 SSE 流（没有就丢弃）
        Turn turn = turns.get(sessionId);
        if (turn == null) {
            return;
        }
        SseAgentEventSink current = turn.sink;
        if (current != null) {
            current.emit(event);
        }
    }

    /**
     * 发起一次「需要用户确认」的等待。
     *
     * <p>流程：发 confirm_required → 关流（detach）→ 阻塞等 future。
     * 注意本方法会阻塞调用线程（也就是工具线程），这是有意为之。</p>
     *
     * @param sessionId 会话 id
     * @param request   确认请求（来自 ToolRuntime 的 ApprovalRequest）
     * @return 用户决定；超时或异常返回「拒绝」
     */
    public ApprovalResult askAndWait(String sessionId, ApprovalRequest request) {
        Turn turn = open(sessionId);
        String interruptId = UUID.randomUUID().toString();
        AgentDtos.AgentEvent event = events.confirmRequired(
                sessionId,
                interruptId,
                request.tool(),
                request.title(),
                request.message(),
                request.args(),
                request.allowRemember());

        java.util.concurrent.CompletableFuture<ApprovalResult> future =
                new java.util.concurrent.CompletableFuture<>();
        turn.interruptId = interruptId;
        turn.pending = new PendingAsk(interruptId, future, event);

        // 1) 先发事件：前端据此弹窗
        emit(sessionId, event);
        // 2) 立刻关流：前端 await 才会返回，弹窗才不会被「挂住」
        detach(sessionId);

        try {
            // 3) 挂起等用户点：超时按拒绝处理，绝不会永久占线程
            return future.get(ASK_TIMEOUT_MINUTES, TimeUnit.MINUTES);
        } catch (Exception ex) {
            return ApprovalResult.DENIED;
        } finally {
            turn.pending = null;
            turn.interruptId = null;
        }
    }

    /**
     * 发起一次「预算超限」的等待（前端同样走确认弹窗，只是事件名不同）。
     *
     * @param sessionId 会话 id
     * @param request   预算请求
     * @return 用户决定；超时或异常返回「拒绝」
     */
    public ApprovalResult askBudgetAndWait(String sessionId, BudgetRequest request) {
        Turn turn = open(sessionId);
        String interruptId = UUID.randomUUID().toString();
        AgentDtos.AgentEvent event = events.budgetExceeded(
                sessionId,
                interruptId,
                request.dimension(),
                request.current(),
                request.limit(),
                "本轮" + request.dimension() + "已超限，是否继续？");

        java.util.concurrent.CompletableFuture<ApprovalResult> future =
                new java.util.concurrent.CompletableFuture<>();
        turn.interruptId = interruptId;
        turn.pending = new PendingAsk(interruptId, future, event);

        emit(sessionId, event);
        detach(sessionId);
        try {
            return future.get(ASK_TIMEOUT_MINUTES, TimeUnit.MINUTES);
        } catch (Exception ex) {
            return ApprovalResult.DENIED;
        } finally {
            turn.pending = null;
            turn.interruptId = null;
        }
    }

    /**
     * 兑现一次等待（由 /chat/resume 调用）。
     *
     * @param sessionId   会话 id
     * @param interruptId 前端带回来的中断 id
     * @param result      用户决定
     * @return true 表示确实兑现了一个等待；false 表示没有匹配的等待（可能已超时）
     */
    public boolean answer(String sessionId, String interruptId, ApprovalResult result) {
        Turn turn = turns.get(sessionId);
        if (turn == null) {
            return false;
        }
        PendingAsk pending = turn.pending;
        // interrupt_id 必须匹配：防止用户点的是上一次已经超时的弹窗
        if (pending == null || !pending.interruptId().equals(interruptId)) {
            return false;
        }
        return pending.future().complete(result);
    }

    /**
     * 查询当前是否有待确认的询问。
     *
     * @param sessionId 会话 id
     * @return true 表示正在等用户点
     */
    public boolean hasPending(String sessionId) {
        Turn turn = turns.get(sessionId);
        return turn != null && turn.pending != null;
    }

    /**
     * 这个会话当前有没有一轮在跑（侧边栏「正在回答」的小圆点靠它）。
     *
     * @param sessionId 会话 id
     * @return true 表示总线上有这个会话的状态
     */
    public boolean isRunning(String sessionId) {
        return turns.containsKey(sessionId);
    }

    /**
     * 请求停止本轮（由 /chat/stop 调用）。
     *
     * <p>若正卡在确认上，直接按拒绝兑现，避免线程等到超时。</p>
     *
     * @param sessionId 会话 id
     * @return true 表示确实叫停了一个在跑的轮次
     */
    public boolean requestStop(String sessionId) {
        Turn turn = turns.get(sessionId);
        if (turn == null) {
            return false;
        }
        turn.stopRequested = true;
        PendingAsk pending = turn.pending;
        if (pending != null) {
            pending.future().complete(ApprovalResult.DENIED);
        }
        return true;
    }

    /**
     * 一轮彻底结束：清掉状态（不影响已经关掉的流）。
     *
     * @param sessionId 会话 id
     */
    public void finish(String sessionId) {
        Turn turn = turns.remove(sessionId);
        recorders.remove(sessionId);
        if (turn != null) {
            SseAgentEventSink current = turn.sink;
            turn.sink = null;
            if (current != null) {
                current.close();
            }
        }
    }

    /**
     * 读取会话的中断 id（调试用）。
     *
     * @param sessionId 会话 id
     * @return 当前中断 id；没有则为 null
     */
    public String interruptId(String sessionId) {
        Turn turn = turns.get(sessionId);
        return turn == null ? null : turn.interruptId;
    }
}
```

> **注意一个细节**：`answer()` 里要校验 `interruptId`。用户可能同时开着两个弹窗（两个标签页），
> 点错的那个必须被忽略，否则会「用旧决定兑现新询问」，这是很隐蔽的 bug。

### 3.9 事件策略怎么组织到一起（你问的第二个问题的正面回答）

**先说结论：不要写一个巨大的 `switch`。**

一个 `switch(type)` 分发到十几个方法，会有三个问题：

1. **加一个出口就要改一次巨大的 switch**（今天写 SSE，明天想落数据库、后天想推 websocket）；
2. 落库失败会拖累 SSE（一个出口抛异常，整轮对话挂掉）；
3. 单测困难（要测 SSE 就得起 Web 环境）。

正确做法是**策略 + 组合**：每个出口是一个 `AgentEventSink` 实现，再写一个组合器把它们串成一条链。
这是**管道模式**（Pipeline / Chain），不是策略模式严格意义上——但你说的「各种事件策略组织到一起」就是它。

```
AgentEvent  ──►  CompositeAgentEventSink
                    ├──► SseAgentEventSink        （写给浏览器）
                    ├──► TraceEventSink           （写 trace_event 表，回放用）
                    └──► （以后）SlackSink / LogSink / MetricsSink ...
```

#### 3.9.1 新建 `CompositeAgentEventSink.java`

**路径**：`backend_java/src/main/java/com/example/backendjava/chat/event/CompositeAgentEventSink.java`

```java
// 模块说明：事件出口组合器 —— 一条事件扇出给多个出口（SSE、轨迹、日志…）。
//
// 这就是「各种事件策略如何组织到一起」的答案：
//   * 每个出口是一个 AgentEventSink 实现（策略）；
//   * 本类把它们合成一条链（组合）；
//   * 新增出口 = 新增一个 Bean，本类与业务代码都不用改（开闭原则）。
// 容错要求：任何单个出口抛异常都不能影响其它出口，更不能打断正在进行的对话。
package com.example.backendjava.chat.event;

// 标准库：List 保存出口顺序
import java.util.List;

// 已有的事件接口与信封
import com.example.backendjava.dto.AgentDtos;
import com.example.backendjava.service.AgentEventSink;

// 日志：单个出口失败时留痕，但不影响对话
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

/**
 * 组合事件出口：按注册顺序把事件分发给所有子出口。
 *
 * <p>子出口按构造时传入的顺序执行；顺序有意义：SSE 必须在最前，
 * 保证用户先看到输出，落库慢一点没关系。</p>
 */
public class CompositeAgentEventSink implements AgentEventSink {

    /** 本类日志。 */
    private static final Logger LOG = LoggerFactory.getLogger(CompositeAgentEventSink.class);

    /** 子出口列表；构造后不再变化。 */
    private final List<AgentEventSink> delegates;

    /**
     * 构造组合器。
     *
     * @param delegates 子出口，按期望的执行顺序排列
     */
    public CompositeAgentEventSink(List<AgentEventSink> delegates) {
        this.delegates = List.copyOf(delegates);
    }

    /**
     * 把事件逐个分发给子出口。
     *
     * @param event 事件信封
     */
    @Override
    public void emit(AgentDtos.AgentEvent event) {
        for (AgentEventSink delegate : delegates) {
            try {
                delegate.emit(event);
            } catch (RuntimeException ex) {
                // 单个出口失败（比如数据库锁）只记日志：绝不能让落库问题打断用户看到回答
                LOG.warn("事件出口 {} 处理 {} 失败：{}",
                        delegate.getClass().getSimpleName(), event.type(), ex.getMessage());
            }
        }
    }
}
```

#### 3.9.2 新建 `TraceEventSink.java`

**路径**：`backend_java/src/main/java/com/example/backendjava/chat/event/TraceEventSink.java`

轨迹落库出口。表 `trace_event` 已经在 `schema.sql` 里建好了（`TraceEvent` 实体 + `TraceEventRepository` 也都有）。

```java
// 模块说明：把事件写进 trace_event 表，供「轨迹」页回放与排查。
//
// 为什么要落库：SSE 事件是「一次性」的，用户关掉页面就没了；
// 出问题时要能回答「这一轮到底调了哪些工具、模型返回了什么」。
package com.example.backendjava.chat.event;

// 标准库：List 收集 token 片段，攒够一批再落库
import java.util.List;
// 标准库：Map 用于把事件 data 序列化成 JSON 字符串
import java.util.Map;
// 标准库：时间格式化
import java.time.Instant;

// Jackson：Map → JSON 字符串
import com.fasterxml.jackson.databind.ObjectMapper;

// 实体与仓库：落库
import com.example.backendjava.entity.TraceEvent;
import com.example.backendjava.repository.TraceEventRepository;
// 已有的事件接口与信封
import com.example.backendjava.dto.AgentDtos;
import com.example.backendjava.service.AgentEventSink;

/**
 * 轨迹出口：把关键事件持久化到 trace_event 表。
 *
 * <p>只记「骨架事件」（tool_start/tool_end/confirm_required/error/done），
 * token 逐条落库会把表撑爆，且没有查询价值，所以显式跳过。</p>
 */
public class TraceEventSink implements AgentEventSink {

    /** 不落库的事件类型。 */
    private static final List<String> SKIPPED = List.of("token", "thinking");

    /** 轨迹仓库。 */
    private final TraceEventRepository repository;

    /**
     * 当前线程正在跑哪一轮。
     *
     * <p>为什么用 ThreadLocal 而不是普通字段：一轮对话一个线程，
     * 而这个是单例 Bean——两个会话同时跑时，普通字段会被后一个覆盖，
     * 结果 A 会话的轨迹被记到 B 会话的轮次下。</p>
     */
    private final ThreadLocal<String> turnId = ThreadLocal.withInitial(() -> "");

    /** 序列化 data 用。 */
    private final ObjectMapper objectMapper;

    /**
     * 构造轨迹出口。
     *
     * @param repository   轨迹仓库
     * @param objectMapper Spring 的 ObjectMapper
     */
    public TraceEventSink(TraceEventRepository repository, ObjectMapper objectMapper) {
        this.repository = repository;
        this.objectMapper = objectMapper;
    }

    /**
     * 设置当前线程的轮次 id，供后续事件共享。
     *
     * @param turnId 轮次 id
     */
    public void setTurnId(String turnId) {
        this.turnId.set(turnId == null ? "" : turnId);
    }

    /**
     * 清掉当前线程的轮次 id。
     *
     * <p>线程池会复用线程，一轮结束时不清，下一轮会继承上一轮的 id。</p>
     */
    public void clearTurnId() {
        this.turnId.remove();
    }

    /**
     * 写一条事件。
     *
     * @param event 事件信封
     */
    @Override
    public void emit(AgentDtos.AgentEvent event) {
        if (SKIPPED.contains(event.type())) {
            return;
        }
        Map<String, Object> data = event.data();
        // 会话 id 从载荷里取（每个载荷都带 session_id；error 事件没有，用空串兜底）
        Object sessionId = data.get("session_id");
        TraceEvent row = new TraceEvent();
        row.setSessionId(sessionId == null ? "" : String.valueOf(sessionId));
        row.setTurnId(turnId.get());
        row.setType(event.type());
        try {
            row.setPayload(objectMapper.writeValueAsString(data));
        } catch (Exception ex) {
            // 序列化失败就存空对象：宁可丢字段，不要让轨迹系统反过来打断对话
            row.setPayload("{}");
        }
        row.setCreatedAt(Instant.now().toString());
        repository.save(row);
    }
}
```

```java
import org.springframework.context.annotation.Configuration;

 * 事件管道装配。
 */

     *

     * @param objectMapper Spring 的 ObjectMapper
     * @return 轨迹出口实例
     */

        return new TraceEventSink(repository, objectMapper);
    }

    /**
     * 对话轮次执行线程池。
     *
     * <p>为什么必须要有：{@code TokenStream.start()} 是阻塞调用，会把 Tomcat 线程占满一整轮；
     * 更关键的是「等用户确认」也会阻塞，绝不能占用 Web 线程。</p>
     *
     * @return 线程池
     */
    @Bean(destroyMethod = "shutdown")
    public ExecutorService chatTurnExecutor() {
        // 每个线程起个可读名字，jstack 时一眼看出是对话线程而不是 Tomcat 线程
        AtomicInteger counter = new AtomicInteger(1);
        ThreadFactory factory = runnable -> {
            Thread thread = new Thread(runnable, "chat-turn-" + counter.getAndIncrement());
            thread.setDaemon(true);
            return thread;
        };
        // 用 cached 池：一轮对话一个线程，等待确认时会长时间占住，固定大小容易饿死
        return Executors.newCachedThreadPool(factory);

    @Bean
    public CompositeAgentEventSink backgroundEventSink(TraceEventSink traceSink) {
        return new CompositeAgentEventSink(List.of(traceSink));
    }
```

> 两者的汇合点就是第 3.8 节那个总线的 `emit()`：**先扇出给全局链落库，再写当前绑定的 SSE 流**。
> 所以你在 `ChatServiceImpl` 里永远只写 `sessionBus.emit(...)` 一行，不用关心「现在有几路出口」。

```java
//
// 为什么在这里发而不是在工具里发：

import java.util.List;
// 标准库：Map 工具入参与结果

 * 工具执行器包装：执行工具，并把过程翻译成事件。
 *
 * <p>一个实例对应「一轮对话」中的一个工具，由 ChatServiceImpl.buildToolMap 创建。</p>

    /** 工具本身。 */
    private final AgentTool tool;

    /** 会话 id。 */
    private final String sessionId;

    /** 本轮状态容器：用于累积工具轨迹、判断是否已被停止。 */

    /** 会话总线：发事件用。 */
    private final ChatSessionBus bus;

    private final OutputContract outputContract;

    /** 事件工厂：构造 tool_start / tool_end 用。 */
    private final ChatEvents events;

    /** 本轮权限模式：ask / workspace / allow，原样传给 SessionContext。 */
    private final String permissionMode;

     * 构造执行器。
     *
     * @param tool           工具
     * @param sessionId      会话 id
     * @param recorder       本轮记录器
     * @param bus            会话总线
     * @param outputContract 输出治理
     * @param events         事件工厂
     * @param permissionMode 本轮权限模式
     */
    public ChatToolExecutor(AgentTool tool, String sessionId, TurnRecorder recorder,
                            ChatSessionBus bus, OutputContract outputContract,
                            ChatEvents events, String permissionMode) {
        this.tool = tool;
        this.sessionId = sessionId;
        this.recorder = recorder;
        this.bus = bus;
        this.outputContract = outputContract;
        this.events = events;
        this.permissionMode = permissionMode;
    }

    /**
     * 执行工具并发出事件。
     *
     * @param request  模型给出的工具调用请求
     * @param memoryId 记忆 id（本项目未使用，保持签名即可）
     * @return 给模型看的工具结果文本
     */

    public String execute(ToolExecutionRequest request, Object memoryId) {
        // 1) 解析入参：JsonUtils.parseMap 是项目内已有的工具方法
        Map<String, Object> arguments = JsonUtils.parseMap(request.arguments());

        // 2) 用户已经点了停止：工具不再执行，直接把结论交回模型，让这一轮尽早收敛
        if (recorder.isStopped()) {
            String skipped = "用户已停止本轮对话，工具 " + tool.name() + " 未执行。";
            bus.emit(sessionId, events.toolEnd(tool.name(), skipped, skipped.length(), false, null));
            return skipped;
        }

        // 3) 工具开始：前端立刻显示「正在读取 xxx」
        bus.emit(sessionId, events.toolStart(tool.name(), arguments));

        ToolResult result;
        // 4) 装配 ThreadLocal 上下文：ToolRuntime 里的权限裁决、审计、预算都靠它拿 sessionId
        ToolSession.setContext(new SessionContext(
                sessionId,
                java.util.List.of(),   // 工作区根目录：走 PathPolicy 的全局白名单
                java.util.Set.of(),    // 会话级禁用工具：本轮不禁用
                java.util.Set.of(),    // 会话级命令白名单：走全局
                "",                    // 工作区 id：留给后续「记住本次授权」用
                permissionMode,
                ToolSession.SCOPE_MAIN));
        try {
            // 5) 执行：权限/预算/审计/截断全在 ToolRuntime 里，这里只管调
            result = tool.execute(arguments);
        } catch (RuntimeException ex) {
            // 工具抛异常不能让整轮对话挂掉：转成失败结果交给模型自己解释
            result = ToolResult.fail("工具执行异常：" + ex.getMessage());
        } finally {
            // 6) 线程池复用线程，必须清理，否则上一个会话的上下文会串到下一个请求
            ToolSession.clear();
        }

        // 7) 取截断信息（取走即删，只能取一次；未截断时 returned.truncated()=false）
        OutputContract.TruncateResult truncation =
                outputContract.takeLastTruncation(sessionId, tool.name());

        // 8) 工具结束：total_chars / truncated / continuation_ref 三个字段全部来自 OutputContract
        bus.emit(sessionId, events.toolEnd(
                tool.name(),
                result.content(),
                truncation == null ? result.content().length() : truncation.totalChars(),
                truncation != null && truncation.truncated(),
                truncation == null ? null : truncation.continuationRef()));

        // 9) 记轨迹：done 事件与历史消息都要用
        recorder.addToolCall(tool.name(), arguments, result.content());
        return result.content();
    }
}
```

> 依赖都写在构造器上，测试时才不用启动整个 Spring 容器。

```java
/**
 * 发起一轮对话，返回 SSE 流。
 *
 * <p>关键点三条：</p>
 * <ol>
 *   <li>模型调用跑到独立线程池，绝不能阻塞 Tomcat 线程（一轮可能几十秒）；</li>
 *   <li>所有输出都走 {@link ChatSessionBus}，这样「换流」时线程不用知道；</li>
 *   <li>一轮结束必须发 done 或 error，并关流，否则前端会一直转圈。</li>
 * </ol>
 *
 * @param request 对话请求
 * @return SSE 流；前端用 fetch 读取
 */
@Override
public SseEmitter stream(ChatRequest request) {
    // 1) 归一化参数（mode/docTopK/maxIterations 的默认值在这个方法里已经补过）
    ChatRequest normalized = request.withDefaults();
    // 2) 会话 id：首轮由后端生成，通过 done 事件回传前端
    String sessionId = (normalized.sessionId() == null || normalized.sessionId().isBlank())
            ? cn.hutool.core.util.IdUtil.fastSimpleUUID()
            : normalized.sessionId();

    // 3) 建流并立刻绑定到总线：之后所有事件都往这条流写
    SseEmitter emitter = new SseEmitter(300_000L);
    SseAgentEventSink sink = new SseAgentEventSink(emitter);
    sessionBus.bind(sessionId, sink);

    // 4) 提前准备本轮记录器（也可以放进总线，这里用一个 Map 挂在 bus 里更省事）
    TurnRecorder recorder = sessionBus.recorderOf(sessionId);

    // 5) 把执行挪到独立线程：本方法必须立刻返回 emitter
    chatTurnExecutor.submit(() -> runTurn(sessionId, normalized, recorder));

    // 6) 前端主动断开时清理绑定，避免向已关闭的流写数据
    emitter.onCompletion(() -> sessionBus.detachQuietly(sessionId));
    emitter.onTimeout(() -> sessionBus.detachQuietly(sessionId));
    emitter.onError(ex -> sessionBus.detachQuietly(sessionId));
    return emitter;
}
```

```java
/**
 * 真正执行一轮对话：装配模型、跑工具循环、发事件、落库。
 *
 * <p>本方法运行在 chatTurnExecutor 线程上，允许长时间阻塞（包括等待用户确认）。</p>
 *
 * @param sessionId 会话 id
 * @param request   归一化后的请求
 * @param recorder  本轮记录器
 */
private void runTurn(String sessionId, ChatRequest request, TurnRecorder recorder) {
    long startedAt = System.currentTimeMillis();
    // 本轮轮次 id：轨迹落库用它把同一轮的事件串起来
    String turnId = cn.hutool.core.util.IdUtil.fastSimpleUUID();
    traceEventSink.setTurnId(turnId);

    try {
        // 1) thinking：让用户立刻看到「我在动」，而不是盯着空屏幕
        sessionBus.emit(sessionId, chatEvents.thinking(sessionId, "start", 0, 0, "正在准备对话…"));

        // 2) 读历史并补种上下文（第一版可以只读条数，不真的补进模型）
        List<ChatMessage> history = chatMessageRepository.findBySessionIdOrderByIdAsc(sessionId);
        sessionBus.emit(sessionId, chatEvents.thinking(sessionId, "history",
                System.currentTimeMillis() - startedAt, history.size(),
                "已载入 " + history.size() + " 条历史消息"));

        // 3) 落用户消息（先落库，避免崩溃时丢失用户输入）
        persistMessage(sessionId, "user", request.message(), turnId);

        // 4) 建模型（供应商/模型名/密钥都在 buildModelSpec 里，已有实现不用动）
        LlmModelSpec spec = buildModelSpec();
        StreamingChatModel streaming = llmModelFactoryRouter.createStreamingModel(spec);
        recorder.setModel(spec.model());

        // 5) 组装工具表：每个工具包一层 ChatToolExecutor，事件就有了
        Map<ToolSpecification, ToolExecutor> tools = buildEventedToolMap(sessionId, recorder);

        // 6) 建 AiServices：这里是「自动工具循环」——模型要工具就自动执行再回来
        Assistant assistant = AiServices.builder(Assistant.class)
                .streamingChatModel(streaming)
                .systemMessage(systemPrompt)
                .tools(tools)
                .maxToolCallingRoundTrips(request.maxIterations())
                .build();

        sessionBus.emit(sessionId, chatEvents.thinking(sessionId, "model",
                System.currentTimeMillis() - startedAt, history.size(), "正在请求模型…"));

        // 7) 跑起来。start() 是阻塞的，直到整轮结束（含所有工具调用）
        assistant.chat(request.message())
                .onPartialResponse(partial -> {
                    // 用户点了停止：不再转发增量，但模型那边没法取消，让它自己跑完
                    if (recorder.isStopped()) {
                        return;
                    }
                    recorder.appendAnswer(partial);
                    sessionBus.emit(sessionId, chatEvents.token(partial));
                })
                .onCompleteResponse(response -> {
                    // 模型侧结束：把用量记下来，真正的 done 在 finally 里统一发
                    TokenUsage usage = response.tokenUsage();
                    if (usage != null) {
                        recorder.setUsage(Map.of(
                                "input_tokens", usage.inputTokenCount() == null ? 0 : usage.inputTokenCount(),
                                "output_tokens", usage.outputTokenCount() == null ? 0 : usage.outputTokenCount(),
                                "total_tokens", usage.totalTokenCount() == null ? 0 : usage.totalTokenCount(),
                                "cost", 0.0));
                    }
                })
                .onError(error -> sessionBus.emit(sessionId,
                        chatEvents.error("模型调用失败：" + error.getMessage(),
                                request.debug() ? stackOf(error) : null)))
                .start();

    } catch (RuntimeException ex) {
        // 任何未预料异常都要变成 error 事件，否则前端只能干等到超时
        sessionBus.emit(sessionId, chatEvents.error(
                "本轮对话失败：" + ex.getMessage(), request.debug() ? stackOf(ex) : null));
    } finally {
        // 8) 落助手消息 + 发 done + 关流。无论成功失败都要走到这里
        finishTurn(sessionId, request, recorder, turnId);
    }
}
```

`finishTurn`：

```java
/**
 * 收尾：落库、发 done（或 stopped）、关流、清理总线状态。
 *
 * @param sessionId 会话 id
 * @param request   请求
 * @param recorder  本轮记录器
 * @param turnId    轮次 id
 */
private void finishTurn(String sessionId, ChatRequest request, TurnRecorder recorder, String turnId) {
    String answer = recorder.answer();
    try {
        // 1) 助手消息落库（工具轨迹也一起存，历史回放要用）
        if (!answer.isBlank()) {
            persistMessage(sessionId, "assistant", answer, turnId);
        }
        // 2) 更新会话的 updated_at 与标题（首轮用第一句话当标题）
        touchSession(sessionId, request.message());
    } catch (RuntimeException ex) {
        // 落库失败不影响用户看到答案：只记日志
        log.warn("会话落库失败 sessionId={}", sessionId, ex);
    }

    // 3) 用户点了停止 → 发 stopped；否则发 done
    if (recorder.isStopped()) {
        sessionBus.emit(sessionId, chatEvents.stopped(sessionId, answer, "user_stop"));
    } else {
        sessionBus.emit(sessionId, chatEvents.done(
                sessionId,
                answer,
                recorder.elapsedMs(),
                recorder.toolCalls(),
                countMessages(sessionId),
                recorder.files(),
                recorder.usage(),
                recorder.steerCount(),
                recorder.model()));
    }
    // 4) 关流并清理：前端收到 done 后会把 loading 关掉
    sessionBus.finish(sessionId);
    // 5) 清掉本线程的轮次 id：线程池复用线程，不清会把下一轮的轨迹记到本轮名下
    traceEventSink.clearTurnId();
}
```

### 4.1 `POST /chat/resume` —— 换插头 + 踢醒线程

```java
/**
 * 用户对确认弹窗做出决定后，恢复被挂起的那一轮。
 *
 * <p>本方法做三件事，顺序不能错：</p>
 * <ol>
 *   <li>把新的 SSE 流插到总线上（这样线程醒来后有地方写）；</li>
 *   <li>兑现挂起的 Future（线程解除阻塞）；</li>
 *   <li>返回新 emitter。</li>
 * </ol>
 *
 * @param request 恢复请求：session_id / interrupt_id / approved / remember
 * @return 新的 SSE 流
 */
@Override
public SseEmitter resume(ChatResumeRequest request) {
    SseEmitter emitter = new SseEmitter(300_000L);
    SseAgentEventSink sink = new SseAgentEventSink(emitter);

    // 1) 先绑新流：必须赶在线程醒来之前，否则线程醒来那一瞬间的输出会丢
    sessionBus.bind(request.sessionId(), sink);

    // 2) 兑现决定。remember=true 时把「本工作区以后都同意」记下来（见 4.1.1）
    ApprovalResult result = new ApprovalResult(request.approved(), request.remember());
    boolean matched = sessionBus.answer(request.sessionId(), request.interruptId(), result);
    if (!matched) {
        // 没有匹配的等待：可能是超时了、或用户点了过期弹窗。
        // 直接发一条 error 并关流，比返回 500 更友好（前端会显示消息而不是崩掉）。
        sink.emit(chatEvents.error("这次确认已经失效（可能超时或已在别处处理），请重新发起对话。", null));
        sink.close();
        return emitter;
    }

    emitter.onCompletion(() -> sessionBus.detachQuietly(request.sessionId()));
    emitter.onTimeout(() -> sessionBus.detachQuietly(request.sessionId()));
    emitter.onError(ex -> sessionBus.detachQuietly(request.sessionId()));
    return emitter;
}
```

#### 4.1.1 `remember` 怎么落地（可选，先留空）

### 4.2 `POST /chat/stop`

```java
/**
 * 停止当前会话正在跑的一轮。
 *
 * <p>限制说明：LangChain4j 1.22 的 {@code TokenStream} <b>没有 cancel() 方法</b>
 * （我 javap 查过，只有 start/onPartialResponse/onCompleteResponse/onError 等）。
 * 所以「停止」是「温柔中断」：不再往前提转发增量、把等待中的确认按拒绝兑现、
 * 立刻发 stopped 并关流；模型侧那条 HTTP 流会在后台自己跑完，我们不再理会。</p>
 *
 * @param request 停止请求
 * @return 是否叫停成功
 */
@Override
public ChatStopResult stop(ChatStopRequest request) {
    String sessionId = request.sessionId();
    // 先问总线「确实有一轮在跑吗」：没有就直接回 false，别顺手建一个空状态出来
    boolean running = sessionBus.requestStop(sessionId);
    if (running) {
        TurnRecorder recorder = sessionBus.recorderOf(sessionId);
        recorder.markStopped();
        // 立刻给用户反馈：不要等他下一次看到 token
        sessionBus.emit(sessionId, chatEvents.stopped(sessionId, recorder.answer(), "user_stop"));
        // 关流：前端 loading 结束
        sessionBus.finish(sessionId);
    }
    return new ChatStopResult(running, sessionId);
}
```

> **为什么不在 `onPartialResponse` 里 `throw` 来退出**？因为那会让 `start()` 抛异常，
> `onError` 会被触发，用户会看到「模型调用失败」，其实是他自己点的停止。
> 用标志位 + 主动发 `stopped`，语义才对。

### 4.3 `POST /chat/{sessionId}/steer` —— 插话

```java
// 模块说明：会话级插话队列 —— 实现 ToolSteeringSource，把用户的插话塞进工具结果里。
//
// 为什么走这个接口：ToolRuntime 每执行完一个工具就会调 drain(sessionId)，
// 把队列里的插话拼到工具结果后面（带 INJECT_PREFIX 前缀），模型下一轮就能看到。
// 这样「执行中插话」不用打断模型，也不用重发请求。
package com.example.backendjava.chat.runtime;

// 标准库：队列与并发容器
import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.UUID;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ConcurrentLinkedQueue;

// 本项目：插话接口
import com.example.backendjava.tools.ToolSteeringSource;

// Spring：注册成 Bean，ToolRuntime 通过 ObjectProvider 注入
import org.springframework.stereotype.Component;

/**
 * 会话级插话队列。
 */
@Component
public class SessionSteeringQueue implements ToolSteeringSource {

    /** 一条待注入的插话。 */
    private record Item(String steerId, String content) {
    }

    /** 会话 id → 待注入插话。 */
    private final Map<String, ConcurrentLinkedQueue<Item>> queues = new ConcurrentHashMap<>();

    /** 会话总线：注入时发 steer_injected 事件。 */
    private final ChatSessionBus bus;

    /** 事件工厂。 */
    private final com.example.backendjava.chat.event.ChatEvents events;

    /**
     * 构造队列。
     *
     * @param bus    会话总线
     * @param events 事件工厂
     */
    public SessionSteeringQueue(ChatSessionBus bus, com.example.backendjava.chat.event.ChatEvents events) {
        this.bus = bus;
        this.events = events;
    }

    /**
     * 入队一条插话。
     *
     * @param sessionId 会话 id
     * @param content   插话内容
     * @return 插话 id
     */
    public String offer(String sessionId, String content) {
        String steerId = UUID.randomUUID().toString();
        queues.computeIfAbsent(sessionId, key -> new ConcurrentLinkedQueue<>())
                .add(new Item(steerId, content));
        return steerId;
    }

    /**
     * 读取当前队列长度。
     *
     * @param sessionId 会话 id
     * @return 待注入条数
     */
    public int pending(String sessionId) {
        ConcurrentLinkedQueue<Item> queue = queues.get(sessionId);
        return queue == null ? 0 : queue.size();
    }

    /**
     * 取走全部待注入插话（由 ToolRuntime 在工具边界调用）。
     *
     * @param sessionId 会话 id
     * @return 插话文本列表；没有则返回空列表
     */
    @Override
    public List<String> drain(String sessionId) {
        ConcurrentLinkedQueue<Item> queue = queues.get(sessionId);
        if (queue == null || queue.isEmpty()) {
            return List.of();
        }
        List<String> texts = new ArrayList<>();
        Item item;
        while ((item = queue.poll()) != null) {
            texts.add(item.content());
            // 每注入一条就通知前端「这条已经进去了」
            bus.emit(sessionId, events.steerInjected(sessionId, item.steerId()));
        }
        return texts;
    }
}
```

### 4.4 `POST /chat/{sessionId}/tool-cancel` —— 取消下一个工具

做法：登记一个「取消标记」，`ChatToolExecutor` 执行前检查。

**新建**：`chat/runtime/ToolCancelRegistry.java`（不建这个类，`consume` 那行就没地方放）

```java
// 模块说明：会话级「取消工具」登记处 —— /chat/{id}/tool-cancel 写，工具执行器读。
//
// 为什么不用「删掉工具」来实现取消：工具表是一轮开始时一次性装好的，
// AiServices 跑起来之后改不了；改成「执行前查一下有没有被取消」最省事。
package com.example.backendjava.chat.runtime;

// 标准库：并发容器（多个会话同时跑，必须线程安全）
import java.util.Map;
import java.util.Set;
import java.util.concurrent.ConcurrentHashMap;

// Spring：单例，两个地方（Controller 层与工具执行器）共用
import org.springframework.stereotype.Component;

/**
 * 取消登记处：每个会话一组「被取消的工具名」，空串表示「下一个工具」。
 */
@Component
public class ToolCancelRegistry {

    /** 会话 id → 被取消的工具名集合；空串代表任意下一个工具。 */
    private final Map<String, Set<String>> cancelled = new ConcurrentHashMap<>();

    /**
     * 登记一次取消。
     *
     * @param sessionId 会话 id
     * @param tool      工具名；空串表示「下一个工具」
     */
    public void register(String sessionId, String tool) {
        String key = (tool == null || tool.isBlank()) ? "" : tool;
        cancelled.computeIfAbsent(sessionId, id -> ConcurrentHashMap.newKeySet()).add(key);
    }

    /**
     * 试探并消费一次取消（消费掉就没了，避免误伤后面的工具）。
     *
     * @param sessionId 会话 id
     * @param toolName  即将执行的工具名
     * @return true 表示这次调用应该被跳过
     */
    public boolean consume(String sessionId, String toolName) {
        Set<String> set = cancelled.get(sessionId);
        if (set == null) {
            return false;
        }
        // 命中：精确点名，或登记了「下一个」
        boolean hit = set.remove(toolName) || set.remove("");
        if (set.isEmpty()) {
            cancelled.remove(sessionId);
        }
        return hit;
    }

    /**
     * 一轮结束时清空，避免下次同会话误命中。
     *
     * @param sessionId 会话 id
     */
    public void clear(String sessionId) {
        cancelled.remove(sessionId);
    }
}
```

```java
/**
 * 最近会话列表。
 *
 * @param limit    最多返回几条
 * @param query    标题模糊搜索；空串表示不过滤
 * @param archived 是否包含已归档
 * @return 会话列表

@Override
public ChatSessionList listSessions(int limit, String query, boolean archived) {
    int safeLimit = limit <= 0 ? 20 : Math.min(limit, 100);
    List<ChatSession> rows = chatPersistence.persistedSessions(archived);
    List<ChatSessionInfo> items = new ArrayList<>();
    for (ChatSession row : rows) {
        // 标题过滤：空 query 不过滤
        if (query != null && !query.isBlank() && !row.getTitle().contains(query)) {
            continue;
        }
        List<ChatMessage> messages = chatPersistence.findMessages(row.getId());
        String preview = messages.isEmpty() ? "" : oneLinePreview(messages.get(messages.size() - 1).getContent());
        items.add(new ChatSessionInfo(
                row.getId(), row.getTitle(), "agent", messages.size(),
                row.getCreatedAt(), row.getUpdatedAt(), preview,
                Boolean.TRUE.equals(row.getPinned()), Boolean.TRUE.equals(row.getArchived())));
        if (items.size() >= safeLimit) {
            break;
        }
    }
    return new ChatSessionList(items);
}
```

### 7.1 一句话结论

**你现在这套「手写循环 + 可换绑总线」已经能跑通全部前端功能了。**
LangGraph4j 解决的是「**执行状态要落盘、要能从磁盘恢复**」这一类问题，不是「发事件」的问题。

### 7.2 对照表

| 能力 | 手写循环（本文方案） | LangGraph4j 图 |
| --- | --- | --- |
| 流式输出 token | ✅ AiServices 直接给 | ✅ 节点里自己发 |
| 工具循环 | ✅ AiServices 内置 | ✅ 自己画 `agent → tools → agent` |
| 弹窗确认后继续 | ✅ 总线换插头（线程挂起） | ✅ `interruptBefore` + checkpoint |
| **进程重启后恢复** | ❌ 丢 | ✅ SQLite 里有 checkpoint |
| **多个待确认并行** | ⚠️ 一个会话一个（够用） | ✅ 天然支持 |
| 多节点计划执行（plan/task） | ❌ 要自己写 | ✅ 这就是它的主场 |
| 学习成本 | 低（本文 3 章） | 高（状态通道、序列化、边条件） |
| 调试难度 | 低（就是普通 Java 方法） | 中（要看 checkpoint） |

**建议**：先把第 3~5 章做完，让功能对齐。等你真的需要「关掉应用明天再继续这个任务」时，再上第 7.3 节。

### 7.3 如果真要上：最小可用图（骨架）

`AgentGraphConfig` 里 `BaseCheckpointSaver` 已经装配好了，但**没有任何图用它**。最小骨架长这样：

```java
// 模块说明：Agent 状态图 —— 用 LangGraph4j 表达「模型 ⇄ 工具」的循环。
//
// 为什么用图而不是 while 循环：图会把每一步的状态写进 SQLite checkpoint，
// 因此「进程重启后继续」和「多个待确认并行」才成立。
// 什么时候该上它：需要断电续跑 / 多任务并行 / 计划模式（plan + task_start/end）。
@Configuration
public class AgentGraphConfig {

    /** 图节点名：模型推理。 */
    private static final String NODE_AGENT = "agent";
    /** 图节点名：工具执行。 */
    private static final String NODE_TOOLS = "tools";
    /** 图节点名：需要确认时停在这里。 */
    private static final String NODE_CONFIRM = "confirm";

    /**
     * 编译好的图。
     *
     * @param saver       检查点存储（GraphConfig 已经提供 SQLite 版）
     * @param model       流式模型
     * @param toolExecutor 工具执行（第 3 章的 ChatToolExecutor 可以直接用）
     * @return 编译后的图
     */
    @Bean
    public CompiledGraph<AgentState> agentGraph(BaseCheckpointSaver saver,
                                                StreamingChatModel model,
                                                ToolRegistry toolRegistry) {
        StateGraph<AgentState> graph = new StateGraph<>(AgentState::new);
        graph.addNode(NODE_AGENT, state -> {
            // 节点里：调模型 → 把 AiMessage 写进 state（messages 通道用追加 reducer）
            return CompletableFuture.completedFuture(Map.of("messages", List.of(aiMessage)));
        });
        graph.addNode(NODE_TOOLS, state -> {
            // 节点里：执行 state 里最后一个 AiMessage 的 toolExecutionRequests
            return CompletableFuture.completedFuture(Map.of("messages", results));
        });
        graph.addNode(NODE_CONFIRM, state -> CompletableFuture.completedFuture(Map.of()));
        // 条件边：有工具请求就走 tools，否则结束
        graph.addConditionalEdges(NODE_AGENT, state -> {
            AiMessage last = lastAiMessage(state);
            return last != null && last.hasToolExecutionRequests() ? NODE_TOOLS : "end";
        }, Map.of(NODE_TOOLS, NODE_TOOLS, "end", "end"));
        graph.addEdge(NODE_TOOLS, NODE_AGENT);
        graph.addEdge(NODE_CONFIRM, NODE_AGENT);

        return graph.compile(CompileConfig.builder()
                .checkpointSaver(saver)
                .recursionLimit(25)
                // 危险工具执行前停在 confirm，等前端点「同意」
                .interruptBefore(NODE_CONFIRM)
                .build());
    }
}
```

**恢复**（`/chat/resume` 里）：

```java
// 用同一个 threadId（= session_id）恢复：图会从 checkpoint 里读回状态接着跑
RunnableConfig config = RunnableConfig.builder().threadId(sessionId).build();
compiledGraph.invoke(GraphInput.resume(Map.of("approved", request.approved())), config);
```

### 7.4 上图的四个坑（都实测过）

1. **`TokenStream` 没有 `cancel()`**。图里想中断，只能靠 `interruptBefore` 在节点边界停，不能停在一个 token 中间。
2. **节点是异步的（`AsyncNodeAction` 返回 `CompletableFuture`）**，而 `AiServices` 是同步阻塞的。你会在节点里写
   `CompletableFuture.supplyAsync(() -> assistant.chat(...).start())`——**注意别把工具线程和图的线程混在一起**，
   `ToolSession` 是 `ThreadLocal`，跨线程就取不到会话上下文了（要么显式传，要么在节点线程里重新 `setContext`）。
3. **状态要可序列化**。`LC4jJacksonStateSerializer` 要求 state 里放的东西能被 Jackson 序列化；
   把 `SseEmitter`、`ToolExecutor` 这类对象塞进 state，会话恢复时必炸。**state 里只放数据（messages、approved、计数）**。
4. **`recursionLimit(25)` 是「步数」不是「轮数」**，一次工具循环至少两跳，设小了会在第 12 次工具调用左右报错。

## 9. 十个坑（我替你先踩了）

1. **`emitter.send` 传字符串 + `APPLICATION_JSON` → 前端收到带引号的字符串**
   Spring 会用 Jackson 再序列化一次，`"abc"` 变成 `"\"abc\""`。**要传 Map/对象**，让 Jackson 序列化一次就够。

2. **`Map.of(...)` 塞 null 直接 `NullPointerException`**
   `continuation_ref` 未截断时应该是 null。用 record + `objectMapper.convertValue` 就没这问题。

3. **`TokenStream.start()` 是阻塞的**
   放在 Controller 里会占满 Tomcat 线程池；赶上十个人同时问，第 201 个请求直接超时。必须丢线程池。

4. **`@Resource` + 线程池 = ThreadLocal 串会话**
   工具线程是池里的，用完必须 `ToolSession.clear()`（`ChatServiceImpl.executeTool` 的 finally 已经做了，别忘了在新的
   `ChatToolExecutor` 里也做）。

5. **`confirm_required` 发完不关流，前端永远转圈**
   这是本文档反复强调的那条契约。`askAndWait` 里 `emit` 之后必须 `detach`。

6. **resume 时先 `answer` 再 `bind`，会丢事件**
   顺序必须是「先绑新流，再唤醒线程」。否则线程醒来第一句话写在 `null` 上，前端就少了开头几个字——
   这种 bug 极难复现（要看运气）。

7. **`SseEmitter` 超时时间**
   `application.yml` 里 `spring.mvc.async.request-timeout: -1` 已经是「不超时」。
   但构造 `new SseEmitter(300_000L)` 又设了 5 分钟——**两者取小**。等确认的场景 5 分钟够用，
   如果你的模型很慢，把这个数调大或直接用 `new SseEmitter()`。

8. **SQLite 写锁**
   `application.yml` 里 Hikari 连接池设成 1，就是为了避免 `database is locked`。
   所以：**不要在事件回调里做重查询**（每条 token 都查一次库，必卡）。轨迹出口已经跳过了 `token`。

9. **`ObjectMapper` 不认 record 的 `@JsonProperty`？**
   认。Spring Boot 自带的 `ObjectMapper` 配置了 `ParameterNamesModule`，record 能正常反序列化。
   但如果你自己 `new ObjectMapper()`，就一定不认——**永远注入，不要 new**。

10. **前端 `dispatchChatEvent` 是白名单**
    你发任何没登记的 `event:` 名字，前端**静默丢弃**。排查「前端没反应」时，第一件事是
    `console.log` 事件名，第二件事是回来查第 2.2 节的表。
