## 2. 影响主流程的未开发任务

> 本文把「主流程」定义为：
> **设置模型 → 多轮对话 → 工具执行 / 确认 → 会话管理 → 轨迹与用量查看。**
> 下面按「是否阻断主流程」排序。

### 2.1 P0 · 多轮上下文没有回填（当前最影响体验）

**现状**

`ChatServiceImpl#runTurn` 里读历史只是为了数条数：

```java
// 2) 读历史并补种上下文（第一版可以只读条数，不真的补进模型）
List<ChatMessage> history = chatMessageRepository.findBySessionIdOrderByIdAsc(sessionId);
sessionBus.emit(sessionId, chatEvents.thinking(sessionId, "history",
        System.currentTimeMillis() - startedAt, history.size(),
        "已载入 " + history.size() + " 条历史消息"));
```

真正调模型时只传了本轮输入：

```java
assistant.chat(request.message())
```

而 `Assistant` 接口只有一个 `chat(String userMessage)`；`AiServices.builder(...)` 也没有配置
`.chatMemoryProvider(...)` 或任何 `ChatMemory`。

**影响**

- 第二轮开始，模型**看不到上一轮说过什么**；
- 前端历史记录、侧边栏、导出都正常，所以肉眼看起来“有历史”，但模型实际是失忆的；
- 用户会感觉「刚说过的它就不记得」，这是聊天类应用最核心的体验缺陷。

**要做什么（二选一，推荐 A）**

- **A. 用 LangChain4j 的 `ChatMemory`**：给每个 `sessionId` 建一个 `MessageWindowChatMemory`，
  首次进入会话时把数据库里的最近若干条消息灌进去，再让 `AiServices` 自动带上；
  注意这要求 `Assistant` 方法带 `@MemoryId` 参数（当前只有 `chat(String)`，需要一并调整）；
- **B. 显式传消息列表**：把 `history + 当前消息` 组装成消息列表，
  调整 `Assistant` 接口与 `AiServices` 调用来接收整段消息；
  具体签名以当前 LangChain4j 版本支持为准，核心是「历史必须进入请求」。

无论选哪种，都必须先解决「历史太长」的问题（见 2.4 上下文压缩），否则长会话会直接超窗。

**验收**

- 第一轮问「我叫什么？记住我叫小明」，第二轮只问「我叫什么？」；
- 模型回答「小明」；轨迹里能看到第二轮请求带上了上一轮消息。

### 2.2 P0 · 自定义供应商没有接入注册表

**现状**

- 设置里已经声明了两项：
  - `llm.custom_providers`：自定义 OpenAI 兼容端点；
  - `llm.custom_models`：给内置供应商补充清单外的模型。
- `OpenAiCompatibleLlmModelFactory.supports()` **已经支持** `custom-*` 前缀；
- 但 `LlmProviderRegistry.listProviders()` 直接 `return BUILTIN_PROVIDERS;`，
  `findProvider()` 也只在内置清单里找；
- `ChatServiceImpl#buildModelSpec:507` 与 `MemoryServiceImpl#buildModelSpec:1014` 都调用
  `findProvider(providerId)`，找不到就抛 404。

**影响**

- 用户在设置页新增自定义端点后，`GET /api/llm/providers` 不返回它，**模型选择器里根本看不到**；
- 如果绕过 UI 把 `llm.provider` 写成 `custom-xxx`，对话和记忆抽取都会直接 404；
- `llm.custom_models` 虽然能让对话“碰巧”用上清单外的模型名（`buildModelSpec` 不强制精确匹配），
  但 `/llm/probe` 的 `resolveModel()` 会拒绝，且拿不到 `context_window` / 单价。

**要做什么**

1. 让 `LlmProviderRegistry` 注入 `SettingsRegistry`，每次 `listProviders()` / `findProvider()` 时
   把 `llm.custom_providers` 解析后追加到内置清单：
   - `id` 加 `custom-` 前缀；
   - `label` 用用户填的名字；
   - `base_url` 用条目里的地址；
   - `secret_key` 用 `custom-<id>.api_key`（与前端 `ModelSection.vue` 的约定一致）；
   - `requires_key = true`、`is_custom = true`；
   - `models` 从 `llm.custom_models` 里按 `provider` 过滤出来。
2. `resolveModel()` / `findProvider()` 都要基于合并后的清单工作。
3. `ChatServiceImpl` / `MemoryServiceImpl` 的 `buildModelSpec()` 调整 baseUrl 优先级：
   **自定义供应商优先用它自己的 `base_url`**，不要被全局 `llm.base_url` 覆盖；
   内置供应商仍保持「全局配置优先」。
4. 把 `llm.custom_models` 合并进内置供应商的 `models`，让 probe、上下文窗口、单价都能命中。

**验收**

- 设置页新增 `custom-myapi` → `GET /api/llm/providers` 里出现该供应商；
- 选中后能正常对话；
- 自定义模型的 `context_window` 能被后续压缩逻辑读到。

### 2.3 P0 · 「测试连接」不可用（字段名 + 密钥来源）

**现状**

前端 `frontend/src/services/settings.ts` 的请求体是：

```ts
export interface LlmProbeRequest {
  provider: string
  model?: string | null
  base_url?: string | null
}
```

`ModelSection.vue:254` 也只传 `provider / model / base_url`。

后端 `LlmDtos.ProbeRequest` 读的却是：

```java
@JsonProperty("provider_id") String providerId,
@JsonProperty("api_key") String apiKey
```

同时 `DefaultLlmService#probe` 在 `requiresKey = true` 时，只从 **请求体** 的 `apiKey` 取值，
没有注入 `SecretStore`：

```java
if (provider.requiresKey() && isBlank(request.apiKey())) {
    throw new ApiException(400, "尚未配置 " + provider.label() + " 的 API 密钥");
}
```

**影响**

- 前端发 `provider`，后端读到的是 `providerId = null` → 报「未知的模型供应商：null」；
- 即使字段名对上，用户已经在设置页保存过密钥，前端也不会把明文 Key 再发一次，
  后端又不去密钥库读 → 云端供应商（DeepSeek / OpenAI / Anthropic / Gemini）
  **「测试连接」必然失败**；
- 只有 Ollama 这种 `requires_key = false` 的供应商能测通。

**要做什么**

1. 统一 wire 字段：按项目约定（前端类型沿用后端字段名）把前端改成 `provider_id`，
   或后端加 `@JsonAlias("provider")` 兼容；二选一，不要两边各写各的。
2. `DefaultLlmService` 注入 `SecretStore`：请求体 `api_key` 为空时，
   用 `provider.secretKey()` 从密钥库读取；请求体只作为本地调试的显式覆盖。
3. 自定义供应商同样走这套逻辑（依赖 2.2）。

**验收**

- 在设置页保存 DeepSeek Key，点「测试连接」→ `ok=true`；
- 故意填错 Key → `error_kind = "secret"`；
- 不填 Key 直接测 → 提示去设置页配置，而不是「未知供应商」。

### 2.4 P1 · 上下文自动压缩未实现

**现状**

设置里已经有完整的三项：

- `context.auto_compress`：是否自动摘要压缩；
- `context.compress_threshold`：占用窗口多少比例触发（默认 0.7）；
- `context.keep_recent_n`：压缩时保留最近多少条（默认 10）。

但 `ChatServiceImpl` 里 **没有任何压缩 / 截断 / token 估算逻辑**；
`LlmDtos.ModelInfo.contextWindow` 在 Java 侧也没有被任何业务代码读取。

**影响**

- 2.1 修好之后，历史会真正进入模型；长会话会很快超过模型窗口，
  表现为供应商报 context length 错误，或请求直接失败；
- 当前第 2.1 节没修时，这个问题被“失忆”掩盖了，修完就会暴露。

**要做什么**

1. 在组装消息前估算 token（字符数粗估即可，教学项目不必上 tokenizer）；
2. 超过 `contextWindow × compress_threshold` 时：
   - 保留最近 `keep_recent_n` 条；
   - 把更早的消息摘要成一段 `system` / 摘要消息（可复用当前模型或更便宜的模型）；
   - 摘要结果落库或作为会话级缓存，避免每轮重复摘要。
3. `contextWindow` 的来源要覆盖自定义模型（依赖 2.2 合并 `llm.custom_models`）。

**验收**

- 构造一段超过窗口的会话，仍能继续对话；
- 轨迹或日志里能看到「触发了压缩、保留了最近 N 条」。

### 2.5 P1 · `\doc` 知识库指令模式未实现

**现状**

- 前端已经把 `\doc` 做成了完整入口：输入栏候选、`\doc -l / -d / -i / -h` 占位提示、
  `mode = 'doc'` 与 `doc_top_k` 都会发给后端；
- 后端 `ChatDtos.ChatRequest` 能解析 `mode` / `docTopK`，`withDefaults()` 也补了默认值；
- 但 `ChatServiceImpl#runTurn` **从未读取 `request.mode()` 或 `request.docTopK()`**，
  也没有任何 `\doc` 解析代码。结果就是整条 `\doc ...` 被当成普通用户消息发给模型。

**影响**

- 用户输入 `\doc -l` 想看文档列表，模型却拿到一串它不认识的指令；
- 删除文档、导入文档、帮助这些确定性命令都退化成“让模型猜”，既慢又不可靠。

**要做什么**

1. 在 `runTurn` 进入模型之前按 `mode` 分支：
   - `mode = "doc"` → 解析 `\doc` 子命令；
   - `-l` 调 `RagService.listDocuments`；
   - `-d <name>` 调按来源删除；
   - `-i <name>` 调索引文件；
   - `-h` 返回用法；
   - 其余情况按 `doc_top_k` 做检索问答。
2. 这些分支不走模型（或只在检索问答时走模型），直接发 `token` / `done` 事件即可。

**验收**

- `\doc -l` 不请求模型就能返回文档列表；
- `\doc -h` 返回用法；
- `\doc 某个问题` 按 `doc_top_k` 检索后回答。

### 2.6 P1 · 记忆 / 技能没有接入对话主链路（自动注入、自动抽取未实现）

**现状**

- `MemoryServiceImpl` 的 10 个方法（列表、搜索、增删、抽取、清理、重建）都已经完成，
  `SkillServiceImpl` 的清单 / 详情也已经完成；
- 但 `ChatServiceImpl` 里**没有注入 `MemoryService`，也没有注入 `SkillService`**：
  - 系统提示词只在启动时从 `classpath:prompts/system-prompt.md` 读一次，之后不再拼任何动态内容；
  - `runTurn` 结束后没有调用记忆抽取；
  - 没有把「技能名 + 描述」拼进系统提示词。
- 结果是这些设置项目前是“死配置”：
  - `memory.inject_enabled`（新对话注入记忆）；
  - `memory.extract_enabled`（每轮结束自动抽取）；
  - `memory.top_k` / `memory.min_importance`（注入条数与门槛）；
  - `skill.auto_inject`（自动提示可用技能）。

**影响**

- 记忆页本身能管理记忆，但**对话不会自动记住，也不会自动回忆**；
- 技能仍可通过 `list_skills` / `read_skill` 工具显式调用，所以不是完全不可用；
- 不影响基础问答，但「工作空间记忆」这个卖点在主流程里没有生效。

**要做什么**

1. 组装系统提示词时，按当前 workspace + 用户消息检索记忆，
   把 `top_k` 条、重要度达标的记忆追加到系统提示词（受 `memory.inject_enabled` 控制）；
2. `finishTurn` 之后异步调用 `MemoryService.extract(...)`（受 `memory.extract_enabled` 控制，
   失败只记日志，不影响本轮对话）；
3. 可选：按 `skill.auto_inject` 把技能名 + 描述拼进系统提示词。

**验收**

- 新对话里问「我之前说过什么偏好」，模型能引用已保存的记忆；
- 完成一轮对话后，记忆列表出现新抽取的条目（达到抽取条件时）。

### 2.7 P2 · 会话用量未落库（token / 费用恒为 0，预算熔断也拿不到数据）

**现状**

- `ChatServiceImpl#usage:810` 只统计助手消息条数，其余字段写死 0；
- `done` 事件里其实已经带了 LangChain4j 的 `TokenUsage`（`runTurn` 的
  `onCompleteResponse` 会 `recorder.setUsage(...)`），但**没有落库**；
- `ChatMessage` 实体只有 `id / session_id / role / content / created_at / mode / tool_calls /
  finish_reason / elapsed`，没有 token / cost / model 字段。

**影响**

- 会话用量面板始终显示 0 token、0 费用；
- `ToolBudgetRegistry#addUsage(...)` 虽然写好了，但**没有任何调用方**，
  所以 `cost.max_tokens_per_task` / `cost.max_cost_per_task` 两个预算维度永远不会累积，
  只剩时长维度可能生效（取决于 `cost.guard_enabled` 的当前实现）。

**要做什么**

1. `chat_message` 表补列：`input_tokens`、`output_tokens`、`cost`、`model`；
2. `finishTurn` 把 `TurnRecorder` 里的 usage 一并落库；
3. `runTurn` 的 `onCompleteResponse` 里顺手调用
   `ToolBudgetRegistry#addUsage(sessionId, ...)`，把 token / 费用喂给预算熔断；
4. `usage()` 改成按会话聚合，并返回按模型分组（前端 `SessionUsage` 已预留列表字段）。

**验收**

- 完成一轮后 `GET /api/chat/history/sessions/{id}/usage` 返回非 0 token；
- 数值与 `done.usage` 一致。

### 2.9 P2 / 可选 · LangGraph4j 图未落地

**现状**

### 2.11 顺手修 · 审计按工具过滤无效

**现状**

`AuditServiceImpl#list:32-34`：

```java
if (tool != null && !tool.isBlank()) {
    spec.and(eq("tool", tool));   // ← 返回值没有赋回 spec
}
```

`Specification.and()` 返回新对象，不修改原对象，所以 `tool` 条件被静默丢弃。

**影响**

- 审计页按工具筛选时，返回的仍是全部记录；
- 不影响对话主流程，但属于明确的逻辑 bug，修复成本约 1 行。

**顺带**

- 该文件目前缺少模块说明、import 注释，`HashMap` 也可能是无用 import；
  按 `AGENTS.md` 的 R1~R3 补注释时一并清理。
