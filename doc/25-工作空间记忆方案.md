# 工作空间记忆方案（独立模块 MEM）

> 本模块**独立成册、独立开发、可独立开关**：不侵入现有 RAG 与 chat 的核心逻辑，只在 chat 里留两个 hook 点。
> 对应总计划里的 **MEM 工作空间记忆**，是 M1（工作区 + Provider）之后即可并行开发的能力模块。
>
> **状态：✅ 已落地（M4.5）**。实现与本文的三处有意偏离（不建独立 FAISS 索引 / 去重阈值 0.85 / 不叫 scheduler 而用 `create_task`）
> 见文末 §13「落地记录」。

---

## 1. 目标

1. **每轮对话自动抽取**关键信息（决策 / 偏好 / 事实 / 待办），存进**按工作区隔离**的记忆库。
2. **新对话先本地检索**：开场时把用户问题在记忆库里检索，命中记忆注入上下文。
3. **开放接口**：记忆检索、记忆问答以**新 REST 接口**注册进路由（见 §6），前端/其它工具都能调。
4. **可独立**：独立 entity / service / controller / FAISS 索引，设置里一键关闭后零影响。

---

## 2. 现状结论（已核查）

- 无任何 memory / 记忆 / 抽取 / 反思相关实体或服务。
- 现有对话历史（`chat_history_service.py`）只**原样落库**，不做抽取。
- 现有 RAG（`rag_store_service.py`）只服务**用户手动导入的文档**，与对话记忆是两回事。
- **可复用的现成底座**：`services/embedder.py`（BGE-m3 向量化）+ `services/faiss_store.py`（向量检索）+ `agents/rag_agent.py` 的裸 `model`（抽取用 LLM）。

---

## 3. 总体数据流

```
一轮对话 done ──► [异步抽取] 裸模型跑「记忆抽取」prompt ──► JSON 记忆列表
                      │
                      ▼
              [去重] 与同工作区已有记忆做相似度过滤
                      │
                      ▼
         ┌────────────┴─────────────┐
         │ SQLite `memories` 表(真相源) │  +  embedder 向量化 → 独立 FAISS 索引(加速检索)
         └───────────────────────────┘

新会话第一条消息 ──► embed 用户问题 → FAISS 检索 top-K ──► 注入系统提示词(「相关记忆」段)
```

两条链路完全解耦：**抽取**（写）与**检索**（读）互不阻塞，都可独立开关。

## 5. 抽取（写）

- **触发**：`chat_controller.py` 在 `_finish_turn`（done/stopped/error 都算一轮结束）之后，`asyncio.create_task(memory.extract_and_store(...))` **异步、非阻塞**——抽取失败只记日志，绝不影响本轮对话。
- **抽取器**：用裸模型（`rag_agent.model`，不挂工具）跑固定 prompt，输入本轮 user + assistant 原文，要求输出 JSON 数组：

```text
从下面这段对话里抽取「对未来对话有帮助、值得记住」的信息，输出 JSON 数组（没有则 []）：
- content: 一句话陈述事实（不要"用户说/助手说"前缀）
- category: preference | decision | fact | todo
- importance: 1~5 整数
只输出 JSON，不要解释。
```

- **去重**：新记忆与同工作区已有记忆做余弦相似度，> 0.9 跳过（首版可先简化，后续加）。
- **空结果**：无价值轮次返回 `[]`，不落库。

## 6. 检索与注入（读）+ 开放接口

### 6.1 检索（本地，不调 LLM）

复用 `embedder` + `faiss_store`：embed 查询 → FAISS 检索 → 返回 top-K 记忆（含 category/importance 元数据），按 `importance × 相似度` 加权排序。

### 6.2 注入

新会话第一条消息（或会话无历史时），取 top-K=5 记忆，拼成系统提示词附加段（**只给模型看，不向用户复述**）：

```text
【本工作区相关记忆】（来自历史对话，仅供参考）
- [decision] 已决定用 SQLite 做会话持久化
- [preference] 用户偏好中文注释
```

### 6.3 开放接口（新接口注册）

> **「大模型查询开放接口」的答案：可以。** 记忆检索与「检索 + 大模型回答」都开放成 REST 接口，
> 按项目既有「新增接口推荐流程」注册进 `api/router.py`（与 health/chat/setting 同级）。

新增 `backend/app/controllers/memory_controller.py`（`prefix="/memory", tags=["memory"]`），并在 `api/router.py` 加一行：

```python
# 记忆：/api/memory/*（抽取、本地检索、检索问答、列出、删除）
api_router.include_router(memory_controller.router)
```

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/memory` | 列出工作区记忆（query: workspace_id / category / limit） |
| POST | `/api/memory/search` | **本地记忆检索**（body: workspace_id, query, top_k）→ 命中记忆列表 |
| POST | `/api/memory/query` | **检索 + 大模型回答**（body: workspace_id, query, top_k）→ SSE 流式回答 |
| POST | `/api/memory` | 手动新增/编辑一条记忆（body: workspace_id, content, category, importance） |
| DELETE | `/api/memory/{id}` | 删除一条记忆 |
| POST | `/api/memory/extract` | 手动触发对某会话的抽取（body: session_id, workspace_id，调试用） |
| POST | `/api/memory/prune` | **整理**：按 `memory.ttl_days` 与 `memory.max_per_workspace` 淘汰低价值旧记忆（M6 新增，body: workspace_id） |
| POST | `/api/memory/reindex` | **重建向量**：补算缺失/维度不符的 embedding（M6 新增，body: workspace_id, force） |

- `search` 是「新对话先本地检索」的直接接口；`query` 是「检索→拼 prompt→LLM 回答」的完整开放接口（与现有 `\doc` 检索问答同构，但对象是记忆）。
- 响应统一走 `ApiResponse[...]` 外壳；`query` 复用 SSE（可参考 `chat_controller` 的 `_sse`/StreamingResponse）。

## 13. 落地记录（实现与本文的偏离）

### 13.1 不建独立 FAISS 索引，向量直接存表

本文 §6.1 写的是「复用 `embedder` + `faiss_store` 建独立索引」。实际落地改成**向量 BLOB 存 `memories.embedding`，检索时按 workspace 取出来做一次 numpy 内积**。

原因：
1. `FaissStore` 的加载 / 对账逻辑（`_db_chunk_ids` / `_rebuild` / `_ids_of`）**硬编码在 `chunks` 表上**，
   复用要么改一处不该改的地方，要么把索引管理代码复制一份；
2. 记忆量级完全不同——单工作区通常几十到几百条，暴力内积是毫秒级；
3. 少一个索引就少一整类问题（索引与真相源不一致要重建、维度换了要重建、进程重启要重新加载）。

约定与 RAG 保持一致：**SQLite 是唯一真相源，向量是可重算的派生字段**。
向量化复用 `rag_store_service.vectorize`（字符 2-gram 哈希 + L2 归一化），纯本地、无网络、可测试。
换真 embedding 时只需改 `memory_service._vectorize` 一处，并把已有行的 `embedding` 清空重算。
（**已于 M6 兑现**：改由 `memory_embedding.embed_one` 决定后端，清空重算这一步被 `POST /api/memory/reindex` 自动化了，见 §14。）

### 13.2 去重阈值默认 0.85（不是 0.92）

本文 §5 写的是「> 0.9 跳过」。实测九组样本的余弦分布：

| 类型 | 相似度区间 | 处置 |
| --- | --- | --- |
| 几乎重复（只差语气词 / 标点 / 一个"写"字） | 0.90 ~ 0.97 | 应当去重 |
| 同一主题但信息不同（该保留） | 0.50 ~ 0.60 | 绝不能去重 |
| 完全无关 | 0.02 ~ 0.38 | —— |

0.85 落在这条清晰的分界线上。最初按 0.92 实现，测试里那对 0.896 的近重复没被挡住——所以这个数是**量出来的**，不是拍的。
用户可在设置里调（`memory.dedup_threshold`，0.5~1.0）。

### 13.3 抽取不做 scheduler，用 `asyncio.create_task`

本文 §5 写「触发：`_finish_turn` 之后 `asyncio.create_task(...)`」，落地即如此——没有引入后台任务队列，
因为抽取是**每轮一次、可丢失、失败无副作用**的任务，为它加一套调度器不划算。

两个细节：
- 任务句柄放进 `chat_controller._BACKGROUND_TASKS`（`asyncio` 只持弱引用，不留强引用可能被 GC 掉）；
- 三种情形直接跳过：`mode == "doc"`（文档列表/检索结果，没有可沉淀结论）、
  `finish_reason == "error"`（回答多半是报错文案）、回答 < 20 字（"好的""已完成"没有信息量）。

### 13.4 注入点：只在新对话首条消息，且进 `model_message`

本文 §7 的读 hook 写「会话无历史时 `memory.search(...)`，命中拼进 system prompt」。
落地时**没有改 system prompt**（它在 agent 建图时就被缓存了，改它要失效重建，代价大且会打乱别的缓存指纹），
改为把记忆块**前置到本轮用户的 `model_message`**——与 `/技能名` 展开是同一个做法，跨 provider 都安全。

两个关键约束：
- 判断 `is_new_session` 必须在 `_start_turn` **之前**（它会把用户消息 append 进 `sess.messages`）；
- 注入只改 `model_message`，`effective_message` 保持干净——后者还要喂给复杂度判定与任务拆分，
  塞进去的"本工作区相关记忆…决策…任务…"会命中 `looks_complex` 的信号词造成误判。

## 14. MEM 增强落地记录（真 embedding / 记忆合并 / 过期淘汰，2026-10-23）

本文 §13.1 留了一句「换真 embedding 时只需改 `memory_service._vectorize` 一处，并把已有行的 `embedding` 清空重算」。
这一节就是兑现这句话的三件事：**向量从哪来**、**重复怎么办**、**旧记忆何时清掉**。

### 14.1 真 embedding：双后端 + 整批降级

新增 `app/services/memory_embedding.py`（约 300 行），`memory_service._vectorize` 改成只调 `memory_embedding.embed_one(text)`。

| 后端 | 取值 | 维度 | 特点 |
| --- | --- | --- | --- |
| 本地哈希 | `local` | 512（沿用 `rag_store_service.VECTOR_DIM`） | 字符 2-gram + L2 归一化，快、免费、离线，但**只认字面** |
| 远端接口 | `remote` | 由模型决定（`text-embedding-3-small` 为 1536） | 调 `POST {base}/embeddings`，懂语义；要密钥与网络，按条计费 |

关键实现约定：

- **端点解析复用现有链路**：provider 留空时跟随当前对话模型的 provider，base_url 剥掉 `/chat/completions`、`/completions`
  后缀再拼 `/embeddings`；密钥复用 `app.llm.factory._resolve_api_key`（显式 > 钥匙串 > `.env`），
  这样用户在设置页填一次密钥，对话与 embedding 都能用。
- **失败整批降级，不混用向量**：任一请求失败（超时 10s / 非 200 / 响应缺向量）都抛 `RuntimeError`，
  `embed_many` 捕获后**整批**回退本地哈希。理由：本地 512 维与远端 1536 维的向量不在同一空间，逐条混用会让余弦相似度变成噪声，
  而这种错误不会报错、只会让检索结果悄悄变差——宁可整批降级，可由 `GET /api/memory/stats` 的 `embedding` 字段看出当前实际用的是哪套。
- **结果归一化后落库**：远端返回未归一化，`_normalize` 统一做 L2 归一化，检索侧才能直接用内积当余弦。
- **进程内 LRU 缓存（256 条）**：键是 `f"{describe()}::{text}"`。抽取每轮都要给同一条内容算向量，
  不缓存就对同一句话反复付费；键里带后端描述，换后端时旧向量不会命中。

> 为什么做成「设置可切」而不是「直接换成远端」：这个项目要能在没网、没密钥的机器上跑通全部测试。
> 切远端是**能力升级**，不是**前置条件**；默认 `local` 保证 `pytest` 与首次启动都不依赖外部服务。

### 14.2 重复不再丢弃，而是合并

原行为（§13.2）是「相似度 ≥ 阈值就 `return None`」，问题在于：它把**更细的那句**当成废物扔了。
`用户偏好中文注释` 与 `用户偏好中文注释，不要写英文注释。` 相似度 0.896，前者信息量明显更少，但顺序反过来就会丢掉"不要英文"这个约束。

现在的 `add_memory` 分三段：

1. `content_hash` 完全相同 → 仍然 `return None`（这才是真重复，没必要动数据库）；
2. 相似度 ≥ `memory.dedup_threshold` 且 `memory.merge_enabled` 为 on → **合并进旧行**（`_merge_into`）；
3. 否则新建（返回体带 `merged: False`，合并则带 `merged: True`）。

`_merge_into` 的合并规则：

| 字段 | 规则 | 理由 |
| --- | --- | --- |
| `content` | 取**较长**的那个（等长保留已有） | 长度是"信息量"最便宜又最稳的代理；不做拼接是为了保持一句话可读 |
| `category` | 已有是 `fact` 且新分类非 `fact` 时才升级 | 用户给出的是"偏好/决策"比自动抽取的"事实"更有价值，不该被覆盖回去 |
| `importance` | 取 `max` | 两次独立判断里取更高的一次，避免信息被稀释 |
| `merged_count` | `+1` | 记忆面板里显示"合并 N 次"，让用户看出这条是被反复确认的 |
| `content_hash` / `embedding` | 重算 | 正文变了，两个派生字段都必须跟着变，否则下次去重会失效 |
| `created_at` / `source` / `session_id` | 不动 | 这三者记录"这条最早从哪来"，合并是同一段记忆的演化，不是新来源 |

关掉 `memory.merge_enabled` 即回到老行为（直接丢弃），方便对比与回滚。

### 14.3 生命周期：先记录"被用过"，才有资格谈淘汰

要淘汰就得知道"哪条还有用"。原来 `search` 只读不写，于是所有记忆在库里看起来一样新。

- `search()` 命中后调 `_touch_usage(ids)`：**一条批量 UPDATE** 写 `last_used_at = now`、`use_count = use_count + 1`。
  异常只 `log.debug` 吞掉——使用记录写失败不该让检索失败。
  返回体里同步把 `use_count` 手动 +1、`last_used_at` 写成刚取到的时间（实体是查询快照，省一次回查）。
- `prune()` 两个维度，二者相互独立、都能用 0 关闭：
  - **时间维度** `memory.ttl_days`（默认 180）：删 `importance <= 2` 且 `COALESCE(last_used_at, created_at) < cutoff` 的行；
  - **容量维度** `memory.max_per_workspace`（默认 500）：超限时按 `(importance, 是否用过, created_at, id)` 升序删到上限——关键度低、从没用过、创建最早的先走。
- 调用时机：`extract_and_store` 存完新记忆后顺手 `prune(workspace_id)`，失败只 `log.warning`（整理失败不能影响刚保存的记忆）。
  也可由用户点「整理」手动触发 `POST /api/memory/prune`。

> 为什么只敢删 `importance <= 2`：`>= 3` 是用户明确认可过的结论（决策/偏好），自动删掉比留一堆噪声更糟。
> 宁可少删，也不能让用户"昨天说过的话今天就没了"。

### 14.4 重建向量：换后端不必清库

`POST /api/memory/reindex`（`reindex()`）先算一条探针向量拿到目标维度，再挑出
「`embedding` 为空」或「`dim` 与目标维度不符」的行批量重算；`force=true` 则整区重算。
返回 `{total, updated, skipped, dim, embedding}`，前端据此提示"已重算 N 条向量（维度 D）"。

需要它的两个真实场景：① 从 `local` 切到 `remote`（512 → 1536，不重算就永远检索不到，因为维度不同无法比较）；
② 远端换了模型（同样是换向量空间）。`force` 之所以要点确认，是因为远端按条计费。

迁移 `0006_memory_lifecycle` 只做三列 `add_column`（`last_used_at` / `use_count` / `merged_count`，后两者 `server_default 0`），
不重算任何向量——历史行会因为没有 `dim` 记录而天然被 `reindex` 挑中，等用户点一次「全部重算」即可。

### 14.6 已知限制

1. **本地后端的相似度天花板**：2-gram 哈希对同义改写几乎无感（`注释要用中文` 与 `注释要用中文，不要英文注释。` 只有 0.6928），
   所以合并只对"字面高度重合"的句子生效。真语义合并不做，因为那要么多一次模型调用，要么必须先切远端 embedding。
2. **降级是静默的**：远端失败只在日志里留一行，用户只能从 `stats.embedding` 的「已降级」提示看出异常。
   不弹窗是刻意的——每轮抽取都弹窗会淹没对话。
3. **合并不可撤销**：`_merge_into` 直接改旧行，没有保留被合并的原文。要追溯只能看 `merged_count` 与列表里那条更长的正文。
4. **`reindex` 是同步的**：单工作区几百条时是秒级，但如果用户把 `max_per_workspace` 调到上限 5000 又切远端，一次全量重算可能几十秒；
   接口没有分批与进度上报，前端只有 loading 态。
