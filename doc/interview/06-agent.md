### AG-01｜L2｜场景构思｜必答｜锚点 `/grilling`（轮次 + frontier + 「事实归 agent、决策归人」）

**题**：拿到一句「给外送培训统计加个导出」，你先写代码，还是先跟 agent 聊？如果先聊，你希望它问你什么、又绝不该问你什么？

**口语答案**：我先聊，而且第一句就声明这轮只做澄清、先别动代码。因为我吃过这个亏——直接让它写，它会自己替我把「导出 Excel 还是 CSV」「按人算还是按场次算」猜一个填进去，等我看 diff 才发现口径全错。聊的时候我要它按轮次来：一轮把当前能问的问题全问了，每条自己带推荐答案，我只回「对」或者「改成 X」。还有一条界线得划死：事实归它去仓库里查——表结构、现有接口、字段口径，不许拿来问我；决策归我——这份导出给谁看、超时了是报错还是给失败清单、要不要走审批，这些它猜不了。

**关键听到**：**先澄清再动手** · **一轮问全 + 自带推荐答案** · **事实归 agent、决策归人**

**追问**：它一轮问了 20 个问题怎么办？（答：让它分层，先问会改变方案的，剩下的等方案定了再问；问题多通常是它没先去读代码。）怎么知道聊够了？（答：能一句话说清「谁在什么场景点哪里、看到什么、失败时看到什么」，且没有悬着的决策。）

**常见错答**：「我写个详细 prompt 让它一把做完」——把澄清压进 prompt，等于你替它猜掉了所有决策。

### AG-02｜L2｜找坑｜抽答｜锚点 `docs/agents/domain.md:13-14`（缺席安静跳过）· `:24-28`（ADR 冲突显式指出）· `docs/adr/0001-limit-越界一律报错.md`

**题**：仓库里给 agent 看的领域文档规则写了两件相反的事：领域文档不存在时要安静跳过、不许提醒缺文件；但输出跟已有 ADR 冲突时必须显式指出。为什么这么定？

**口语答案**：因为这两件事的失败代价不一样。缺文件只是「还没有」，agent 每轮提醒你「仓库缺 GLOSSARY.md」纯是噪音，还会诱导它自己造一套词汇；所以规则是安静跳过，等真有术语要定的时候再由 `/domain-modeling` 去建。ADR 冲突不一样——那已经是历史决策，它静默按自己的写法走，等于把一次架构变更藏进一次普通改动里，以后没人知道哪条决策被推翻了。所以冲突必须显式说，哪怕最后照改，也要留一句「与 ADR-0001 冲突，理由是……」。

**关键听到**：**缺文件的噪音要压掉** · **已记录的决策不许静默覆盖** · **冲突要留可追溯的一句**

**追问**：它说「我按新方案做了，ADR 顺手也改了」呢？（答：改 ADR 是决策，得我先点头，它最多交一份 ADR 草稿。）`0001-limit` 那条对我这次需求意味着什么？（答：任何「超限就静默截断或降级」的写法默认违规，要么改 ADR，要么绕道走。）

**常见错答**：「文档缺就让它先建一份」——安静跳过是故意的，自造词汇比缺词汇更贵。

### AG-03｜L3｜设计｜加分｜场景：需求评审，一个 40 分钟就能讲完的小需求

**题**：同一场需求里，哪些决定你必须自己拍、哪些可以放手让 agent 定？给一条你实际在用的判据。

**口语答案**：我按可逆性分，不按重要性分。单向门我自己拍——表结构、对外接口契约、统计口径、金额和数量的算法，还有「做完之后判不出来对错」的那些，这类其实该继续拆而不是开工。双向门就丢给它：内部函数怎么拆、变量命名（在 `AGENTS.md` 约束内）、测试怎么写、注释怎么写、同义写法挑哪个。还有一条附加要求：它定的每件事都得留在 diff 里能被看见，不然「它自己做主」和「它偷偷改了」在评审时长得一模一样。

**关键听到**：**按可逆性分，不按重要性分** · **口径/契约/不可逆的我拍** · **它定的必须留在 diff 里可审**

**追问**：它擅自改了统计口径怎么办？（答：当流程缺陷处理——要么工单写得太宽，要么缺一条机器检查能拦住，骂它没用。）

**常见错答**：「重要的我自己写，不重要的给它」——重要性是主观的，可逆性才是可操作的。

### AG-04｜L2｜场景构思｜必答｜锚点 `/prototype`（抛弃式、一条命令能跑、状态要打出来）

**题**：需求里有一处聊不清：「导出进度」到底做成一条进度条，还是一个任务列表。你说走原型，那这个原型要满足什么条件才算合格？

**口语答案**：四条。一是抛弃式，第一天就标清楚它不是产品，放在将来要被替代的那个模块旁边，名字一眼能看出是原型。二是一条命令能跑，`pnpm <name>` 或者双击一个 HTML，不许有「先装依赖再改配置」的前戏。三是不持久化，状态放内存——持久化恰恰是要验证的东西，别让原型先假定它。四是每次操作后把完整状态打出来，不然我看不出「进度条 47%」背后到底算的是什么。最后一句：它回答的是「长什么样、感觉对不对」，不是「跑得动」；如果真正的问题是状态机，那就该走逻辑分支，别拿 UI 糊过去。

**关键听到**：**抛弃式且标记清楚** · **一条命令能跑、不持久化** · **状态必须可见，问题决定原型形态**

**追问**：原型里那版挺好，能直接拷进产品吗？（答：只能拷决策——状态机、类型形状、交互顺序；代码本身重写，原型留在一手材料分支上被引用，不进 main。）

**常见错答**：「先做个能跑的最小版本」——那是 MVP，不是原型；原型失败是成功，MVP 失败是事故。

### AG-05｜L2｜读代码｜抽答｜锚点 `/handoff`（新 harness / 新目录 / 同事 / 中途分叉）· `docs/agents/issue-tracker.md:9-13`

**题**：什么时候你会把上下文写成一份文件交给下一个会话，而不是在同一个会话里继续做？

**口语答案**：只有四种情况值得 handoff：换 harness、换目录（原型就活在自己的目录里）、交给同事、或者某个侧任务中途分叉出去。它买到的是**可移植**，代价是丢掉这个会话里的隐性上下文，所以默认不是它——阶段边界上五选一：继续、`/clear`、handoff、丢给 subagent、`/compact`，多数时候是继续或者 clear。真写的时候我会要求那份文件能让一个全新会话直接开工：目标、已定决策、还没定的、下一步、以及指回工单的路径。写完就从原会话退出去，别两边同时改同一批文件。

**关键听到**：**handoff 买的是可移植，不是省事** · **只在换环境/换人/分叉时用** · **文件要能让新会话直接开工**

**追问**：原型做完怎么回来？（答：结论链回原需求线程和工单，原型本体留在一手材料分支上，别在对话里抄代码。）

**常见错答**：「每个阶段都 handoff 一下更干净」——每 handoff 一次丢一次隐性上下文，还多一份会过期的文件。

### AG-06｜L1｜基础｜必答｜锚点 `/to-spec`（模板：不要写文件路径和代码片段）· `/to-tickets`

**题**：一个产出规格、一个产出工单，这两步的分工是什么？规格里为什么明确不写文件路径和代码片段？

**口语答案**：规格回答「做什么、为什么、边界在哪」——问题陈述、用户故事、实现决策、测试决策、明确不做什么；工单回答「分几步、谁等谁」。规格里不写路径和代码，是因为它们一改就过期，还会让实现者照着过期锚点改错地方。决策写进散文；长得像代码的只有一种例外——原型已经把这个决策说清楚了（状态机、reducer、类型形状），那就把那几行贴进来并注明来自原型，别贴一个能跑的 demo。

**关键听到**：**spec 说做什么，tickets 说怎么排队** · **路径和代码会过期，不进 spec** · **例外只有原型拍下来的决策片段**

**追问**：那实现者怎么知道改哪？（答：它在工单范围内自己去仓库找，加上 GLOSSARY 的词汇对齐；这正是「事实归 agent」。）

**常见错答**：「规格越详细越好，贴满代码」——贴满代码的规格是一份会腐烂的实现。

### AG-07｜L3｜设计｜加分｜锚点 `/to-tickets`（vertical-slice-rules · expand–contract）

**题**：一个需求要动表结构、接口、前端三处。你怎么切工单？为什么不能按「先改表、再改接口、最后改前端」切？

**口语答案**：按竖切，每张单穿过所有层、单独可 demo，尺寸控制在「一个新窗口装得下」。横切的问题是中间那几张单永远是红的，谁也不知道什么时候能绿，也没法单独验收一张。但有一类例外：大范围机械改动，比如一张表改名，改一下几千个调用点全炸；这种不能硬切竖片，走 expand–contract——先加新形态让旧的还能用，再按爆炸半径分批迁，最后删旧的。另外任何 pre-factor 排在最前面：先让改动变容易，再改。

**关键听到**：**每张单穿全层、单独可 demo** · **横切会让中间态一直红** · **大范围机械改动走 expand–contract**

**追问**：一张单要做三天？（答：不是切得不够细，就是它其实是一个「大范围改动」伪装成的单张单。）

**常见错答**：「按技术分层切最清楚」——清楚的是人，坏掉的是可验收性。

### AG-08｜L1｜基础｜抽答｜锚点 `docs/agents/issue-tracker.md:6-13`（目录约定）· `:23-39`（claim / resolve / frontier）

**题**：工单落在 `.scratch/<feature-slug>/` 下、一张一个文件，文件里有 `Status:` 和 `Blocked by:`。这两个字段是给谁看的？agent 又怎么决定今天做哪张？

**口语答案**：主要给 agent 看，人顺手也能看。`Blocked by` 是阻塞依赖，不是优先级——它列的单没全 resolved 之前这张不许开工；`Status` 用来表达未认领/已认领/已解决，动手前先写 claimed，免得两个会话抢同一张。选单的算法很土：扫一遍 issues 目录，取「没关、没被阻塞、没被认领」的，编号小的先，这就是 frontier。土但可执行——agent 不需要理解全局计划，只要会读文件。

**关键听到**：**Blocked by 是依赖不是优先级** · **claim 先写状态，防两个人抢** · **frontier = 未关/未阻塞/未认领，编号小的先**

**追问**：忘了写 Blocked by 会怎样？（答：两张单都以为自己能开工，最后改到同一批文件冲突；所以出单时就得把边想清楚，别等冲突爆出来再收拾。）

**常见错答**：「工单是给人看的，agent 只要读描述」——依赖和状态才是不打架的那一半。

### AG-09｜L2｜找坑｜必答｜锚点 `/ask-matt`（Context hygiene · Phase boundaries）

**题**：一个人用 agent 做完一个中型需求，上下文窗口怎么安排？哪些阶段必须挤在同一个窗口，哪些必须换新窗口？

**口语答案**：澄清、规格、拆单这三步挤在同一个窗口里别清，因为它们相互回指——澄清出来的决策要进规格，规格里的决策决定工单怎么切，中间清一次就得把话重讲一遍。到实现就反过来，每张工单一个新窗口，因为工单本身是自包含的，上一张的上下文可以丢。判据不是「窗口还剩多少」，是阶段边界在哪；真到边界了再五选一：继续、`/clear`、handoff、丢 subagent、`/compact`，默认是继续。还有个量化提醒：模型大概过 15 万 token 以后明显变钝，别硬撑到快满，在最近的边界上压。

**关键听到**：**澄清→规格→拆单同一窗口** · **实现每张单换新窗口** · **按阶段边界决定，不按剩余空间**

**追问**：实现到一半发现需求漏了一条？（答：回原窗口补规格和工单，别在新窗口里临场加戏。）

**常见错答**：「满了就 `/compact`，然后照样干」——压缩会丢细节，得在边界上压才安全。

### AG-10｜L2｜设计｜抽答｜锚点 `AGENTS.md`（R1~R3 注释硬约束）· `doc/java_langchan_doc/04-AI代码生成规范.md`

**题**：`AGENTS.md` 里那三条「每个字段、每个方法、每条 import 都要有注释」的硬规矩，你怎么让 agent 每次都真的遵守？靠每轮提醒？

**口语答案**：不靠提醒，靠环境。第一，规矩写在 agent 每次都会读到的位置——`AGENTS.md`，Java 侧再点一份 `doc/java_langchan_doc/04-AI代码生成规范.md` 给示例和禁止清单。第二，把它变成能红能绿的检查：评审按三条逐项过，漏了就是不合规；能自动化的部分进检查脚本，比人在 diff 里一行行找可靠。第三，同一类错误反复出现，说明缺的不是提醒而是工具——老忘给 import 写注释，就把模板和校验固化成确定性的一步。我不太信「再说一遍它就会记住」。

**关键听到**：**写进环境，不靠口头重复** · **机械错误变确定性检查** · **判断类的东西变规范**

**追问**：它写 `/** 获取数据 */` 这种零信息注释算过吗？（答：不算，规范里明确禁止同义反复；检查要看的是「为什么用它」。）

**常见错答**：「我在每轮开头贴一遍要求」——占上下文，而且必然漏。

### AG-11｜L3｜设计｜加分｜锚点 场景：三个 agent 并行做同一个需求的工单

**题**：你要让三个 agent 并行做同一个需求的工单。怎么保证它们不打起来、产出还能合得回去？

**口语答案**：三件事。一，写作用域不重叠——每张单说清它摸哪些文件或目录，重叠的不许并行；这条只能靠约定加人盯，因为共享文件系统上机器拦不住。二，依赖用 `Blocked by` 表达，只放「真的必须先完成」的边，宁可排松一点也别造假依赖，能并行的自然会浮到 frontier 上。三，验收权在人手里，谁实现谁不能自己盖「通过」——尤其不能既写工单又判工单过。再加一条实操：并行期间别让它们同时干会互相影响的事（改依赖、起同一个服务、跑全量测试）。

**关键听到**：**写作用域不重叠才并行** · **Blocked by 只写真依赖** · **实现者不能自我验收**

**追问**：三个人同时改了同一个文件怎么发现？（答：靠最后统一看 diff 加跑测试；所以并行粒度宁粗勿细，别把同一层拆给三个人。）

**常见错答**：「并行就是多开窗口，越快越好」——并行只省墙钟时间，不省冲突成本。

### AG-12｜L2｜设计｜必答｜锚点 `/code-review`（Standards + Spec 两轴）

**题**：评审为什么一定要两轴？只跑测试、只看 diff 干不干净，为什么都不算验收？

**口语答案**：因为两类失败完全不相交。测试通过只说明「它以为的行为对」，说明不了这份 diff 有没有按本仓库的规范写——注释、命名、snake_case、错误码，这些测试不测；Spec 轴反过来，只查「当初要做的是不是真做了、边界是不是这个边界」，不查风格。两轴分开跑还有个好处：报告能分开审，规范问题退给作者，spec 偏离退回去对齐需求和边界，不会混成一句「改一下」。另外评审要对着一个固定起点（commit、分支、merge-base），否则 diff 会漂。

**关键听到**：**Standards 与 Spec 是两类失败** · **测试只覆盖行为，不覆盖规范与意图** · **评审要有固定起点**

**追问**：两轴都过了能上线吗？（答：不能，还缺部署前确认和回归；评审通过只是必要条件。）

**常见错答**：「测试绿了、lint 过了就是验收」——那只是机器能判的那一小部分。

### AG-13｜L3｜找坑｜加分｜锚点 `/to-tickets`（工单模板的 `Acceptance criterion` 勾选）· 场景：验收标准写成「导出体验流畅」

**题**：工单里的验收标准写着「导出体验流畅」。你是实现者会怎么处理？当评审者呢？

**口语答案**：当实现者我先把它退回去改——「流畅」没法判，做完之后谁都能说通过或不过。改写就两条路：给可判的阈值（一万行多久出首帧、进度多久刷一次、失败时至少有哪几条可读信息），或者给状态集合（成功、部分失败、全失败、超时，各自看到什么）。当评审者我只认能红能绿的判据，判不了就说明这条需求还没到能开工的程度，不是「做完再说」。agent 场景下这条更要紧：它不会替你质疑标准，只会照着含糊的标准产出一个看起来达标的版本。

**关键听到**：**含糊标准等于没有标准** · **改成阈值或状态集合** · **agent 不会替你质疑标准**

**追问**：有些东西天生难量化（比如「看起来专业」）？（答：让它可比较——给两三个样例，验收时做对比判断，至少不靠感觉。）

**常见错答**：「先做，做完看着不对再改」——返工成本全压到最后一环。

### AG-14｜L2｜设计｜抽答｜锚点 `/ask-matt`（技能清单只给摘要）· `/to-spec` `/to-tickets` 的 `disable-model-invocation: true`

**题**：技能是磁盘上的文件，模型怎么知道什么时候该用哪个？既然正文都在，为什么不干脆全塞进系统提示词？

**口语答案**：塞不起，也没必要。技能进上下文的只有两样：`name` 和 `description`，所谓「路由」就是模型拿 description 跟当前任务比——所以 description 写得像不像「什么时候该用我」，直接决定它会不会被想起来。正文和引用文件是按需读的，用到哪个读哪个，这叫渐进披露。另有一个安全阀：标了 `disable-model-invocation: true` 的技能只能由人显式敲 `/xxx` 触发，模型自己不能调——像会写文件的 `/to-spec`、`/to-tickets` 就该这么管。

**关键听到**：**常驻的只有 name + description** · **description 就是路由条件** · **会写文件的技能要人显式触发**

**追问**：两个技能的 description 撞了会怎样？（答：模型乱挑，或者挑了更重的流程；要么改 description，要么合并。）

**常见错答**：「把技能细节全写进规则里更保险」——常驻内容吃掉上下文，真正的活就干不动了。

### AG-15｜L3｜找坑｜加分｜锚点 场景：本会话挂了 1 个 MCP server、24 个工具全在上下文里

**题**：接一个 MCP server 只是加一行配置，但代价不在那行配置上。什么情况下你会拒绝接？接了之后又怎么管它？

**口语答案**：先算成本——MCP 的工具名、描述、参数 schema 是常驻上下文的，一个 server 二十来个工具就吃掉几千 token，跟这次用不用它无关。所以我的默认是「需要才接、按项目接」，别全局挂一堆。再看信任边界：外部 server 能干什么你事先不知道，所以子 agent、只读调研这类场景我干脆不给 MCP——宁可少一个能力，也别让一个「只读」的子 agent 手里握着写盘和联网的工具。密钥走环境变量或专门的密钥存储，不进对话、不进工具参数。最后：能当「资源」读的别做成工具，工具是给模型动作的，混在一起白烧上下文。

**关键听到**：**工具 schema 是常驻成本** · **外部 server 能力未知 → 子 agent 不给** · **密钥不进对话、资源别做成工具**

**追问**：server 从配置里删了，工具会不会留着？（答：会，得按前缀把它注册过的那批清掉，否则幽灵工具还在策略表和上下文里。）

**常见错答**：「MCP 就是插件，越多越强」——每个 server 都收租，收的是上下文和信任面。

### AG-16｜L2｜实操｜必答（动手）｜锚点 `docs/agents/issue-tracker.md`（工单布局）· `docs/agents/domain.md`（术语与 ADR）

**题（现场题）**：现场给你一个真实小需求（例如「导出的失败清单要能重试」）。15 分钟，从澄清走到出一张 `.scratch/<slug>/issues/01-*.md`，边做边说。

**口语答案**：我先花三分钟只干一件事——把「重试」这个词的歧义问掉：重跑整批还是只补失败那几条、失败清单留多久、重复提交怎么去重。同一时间我自己去仓库里读现有导出实现和失败记录落在哪，不拿这个问面试官。然后在 `.scratch/export-retry/` 下写 `01-export-retry-failed-items.md`：`Status: ready-for-agent`，`Blocked by: None`，正文写「用户点重试后只补失败项，并给出一份新的失败清单」，验收标准写成能判的三条——已成功的项不重导、部分成功也返回成功并带失败计数、超时给出可重试标记。最后补一句写作用域：这张单只碰导出服务和它的测试，别顺手改前端。

**评分点（4 条，现场打勾）**：

- [ ] 先问决策、自己查事实（有没有真的打开仓库读现有实现）
- [ ] 切出来的是竖片、能单独 demo，验收标准写成可判据
- [ ] 文件落对位置，`Status:` / `Blocked by:` 写对（无依赖就写 None）
- [ ] 该留一手材料（原型 / ADR 指针）时留了，没硬凑

**关键听到**：**先问歧义、自己查事实** · **竖片 + 可判验收** · **落位与状态字段正确** · **声明写作用域**

**追问**：这张单要动三张表怎么办？（答：说明切大了，拆成「expand：加列/加表不影响旧的」和「切换：读写切过去」两张，第二张 `Blocked by` 第一张。）

**常见错答**：上来就写实现步骤（「先改 service 再改 controller」）——那是实现计划，不是工单。
