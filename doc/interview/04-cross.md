### X-01｜L2｜设计｜加分｜锚点 `frontend/src/services/types.ts` · `backend/app/main.py:158` · `backend_java/.../common/ApiResponse.java:12`

**题**：同一个「创建会话」接口，Python 和 Java 两套后端都要提供，前端只有一套类型定义。你靠什么保证三端字段不漂移？

**口语答案**：靠两条硬约定加一条机器校验。约定一是字段一律 snake_case、前端不改名（仓库 `AGENTS.md` 就是这么定的），Java 侧驼峰字段用 `@JsonProperty` 显式映射，别让框架默认转换替你做决定。约定二是响应外壳统一 `{code,message,data}`，Python 的异常处理器和 Java 的 `ApiResponse` 工厂方法产出的必须是同一个形状。校验就是契约测试：两侧各写一条断言同一份样例 JSON 的测试，字段名对不上直接红。

**关键听到**：**snake_case 不转换** · **`@JsonProperty` 显式映射** · **契约测试锁字段**

**追问**：Java 的 record 加字段很方便，先加后改前端会怎样？（答：多余字段前端忽略不报错，所以「少字段」比「多字段」更危险，契约测试要校验必填集合）

**常见错答**：「两边都按文档写就行」——没有机器校验，漂移只是时间问题。

### X-02｜L3｜找坑｜加分｜锚点 `backend/app/controllers/chat_controller.py:1067-1100` · `backend_java/.../chat/runtime/StreamingTurn.java:73-107`

**题**：Python 侧用户点「停止」时能 `cancel()+aclose()` 直接掐断，Java 侧 `TokenStream` 没有 `cancel()`。同一份前端停止按钮，两套后端的行为会有什么不一样？用户会看到什么？

**口语答案**：Python 侧能立刻断流，前端收到结束事件就收尾；Java 侧只能「标记取消 + 等当前工具/当前帧返回」，所以停止有延迟。如果前端按 Python 的时延写死 3 秒兜底，Java 侧正常停止的请求会被误判成失败去强断，反而丢掉已经生成的内容。正确做法是两侧都发同一个「已停止」终态事件，前端只认事件、把强断当兜底而不是主路径。

**关键听到**：**两侧停止语义不同** · **前端不能按一侧时延写死** · **统一终态事件 + 强断只兜底**

**追问**：怎么验证这个差异？（答：同一组用例跑两套后端，断言「最后一条消息内容 + 终态事件顺序」一致）

**常见错答**：「停止就是 abort 请求」——忽略服务端能否真的中断，结果库里有半条记录。

### X-03｜L2｜设计｜加分｜锚点 `backend/app/main.py:158` · `backend_java/.../common/GlobalExceptionHandler.java:44` · `frontend/src/services/request.ts:40`

**题**：Python 用统一异常处理器兜所有异常，Java 用 `@RestControllerAdvice` 按异常类型分 9 类。前端只认一套 `{code,message,data}`。这三层怎么对齐才不出现「同一个错误两种码」？

**口语答案**：先定错误码清单，再让两侧都往里映射。清单要有三类：参数错、业务错、系统错；每一类的 code 必须跨语言同值、同含义。Python 侧在异常处理器里做映射，Java 侧在 advice 里做，不要各自随手造码。前端只按 code 分支，不去解析 message 文案，message 只给人看。

**关键听到**：**先定错误码清单** · **两侧映射而非各自造码** · **前端只认 code**

**追问**：业务异常在 Python 是抛异常、Java 是返回错误对象，怎么统一？（答：都归一成同一份错误码表，异常只是语法，不是语义）

**常见错答**：「HTTP 500 就是系统错」——大量业务错误被 HTTP 状态盖住，前端无法区分。

### X-04｜L3｜找坑｜加分｜锚点 `backend/app/services/settings_registry.py:259-370` · `backend_java/.../settings/SettingsRegistry.java`

**题**：Python 侧设置项声明在 `settings_registry.py`（约 259~370 行一大片），Java 侧有 `SettingsRegistry` + `SettingsServiceImpl` 从 DB 设置表读模型参数。同一份产品配置声明了两遍，会怎么坏？怎么防？

**口语答案**：最直接的坏法是「改了一边忘另一边」——比如 `llm.max_tokens` 默认值一边是 0 一边是别的，或者一边新增 `context.keep_recent_n` 另一边没有，界面上就出现保存不生效。更隐蔽的是校验规则不一致：Python 允许 0（语义是「不传」），Java 把 0 当非法。防法是「单一事实来源 + 生成」：用一份声明（JSON/YAML）生成两侧注册表，或者至少让两侧的默认值与取值范围跑同一份契约测试。

**关键听到**：**双份声明必漂移** · **默认值/取值范围先漂移** · **单一事实来源或共享契约测试**

**追问**：`0` 表示「不传」还是「0 个 token」？（答：语义必须写进字段说明，否则两侧实现必然分歧）

**常见错答**：「以 DB 为准就不会不一致」——DB 里存的只是值，声明与校验还是在两侧代码里。

### X-05｜L3｜设计｜加分｜锚点 `backend/app/tools/budget.py:82-84` · `backend_java/.../tools/ToolBudgetRegistry.java:156` · `backend_java/.../tools/PathPolicy.java:92`

**题**：两侧都有「三维预算」（token / 金额 / 时长）和「路径白名单」。如果产品要求「同一任务在两套后端上的花费和可达路径必须一致」，你怎么设计？

**口语答案**：把「预算」和「路径策略」从业务代码里抽成同一份规格：维度、单位、超限后的行为（拒执行还是只报警）、路径的 read/write/exec 三档规则，都要有唯一来源。然后两侧各实现同一规格，用同一组边界用例验证：刚好超线、跨维度同时超、路径软链/相对路径绕过。做不到一致时，宁可让一侧直接拒绝该任务，也不要让两侧行为不同。

**关键听到**：**规格单一来源** · **超限行为要一致** · **边界用例必须跨实现共用**

**追问**：两侧精度不同（金额浮点 vs 定点）会怎样？（答：都会在线附近抖动，金额必须定点/整数分，别用浮点）

**常见错答**：「各算各的，反正都是限额」——同一任务两套后端结果不同，排障会变成玄学。
